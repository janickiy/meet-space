# Административная панель MeetSpace

Админка — отдельная сборка `admin/`. Она включена в образ существующего `proxy`,
не связана со сборкой пользовательского frontend и использует прежние PostgreSQL,
Redis и API. Администраторы входят по логину и паролю; пользовательский аккаунт
и его сессия не дают доступа в панель.

## Адрес и изоляция

```dotenv
ADMIN_ENABLED=true
ADMIN_HTTPS_PORT=8081
ADMIN_HTTP_PORT=8082
ADMIN_PUBLIC_URL=https://meet.example.com:8081
ADMIN_BIND_ADDRESS=0.0.0.0
```

Замените домен своим. `ADMIN_PUBLIC_URL` должен совпадать с адресом в браузере,
включая порт: он используется для проверки Origin. Его можно оставить пустым
(так устроены `.env*.example`): приложение возьмёт hostname из `PUBLIC_FRONTEND_URL`
и добавит `ADMIN_HTTPS_PORT`. Тогда изменение порта не требует дублировать его
в URL. Если URL задан явно, при смене порта обновите оба значения; несовпадение
останавливает API с ошибкой конфигурации. Мастер установки записывает явный
URL, уже содержащий выбранный порт. В Compose внутренний HTTP-порт
API закреплён на `8082` и **не публикуется**. Nginx принимает HTTPS на внутреннем
`8081`; `ADMIN_HTTPS_PORT` выбирает порт хоста. Сертификат тот же, что у приложения:
`/run/certs/fullchain.pem` и `/run/certs/privkey.pem`. Локальная Compose-конфигурация
использует сертификаты из `dockers/https/certs`.

Публичный HTTPS-порт `443` возвращает `404` для `/api/v1/admin` и вложенных путей.
Административный HTTPS-сервер проксирует только `/api/v1/admin/` на `api:8082`.
Клиентские `Forwarded`/`X-Forwarded-*` не передаются как доверенные значения;
Nginx задаёт собственный адрес клиента. Настройте `HTTP_TRUSTED_PROXIES` только
для доверенной сети/адресов прокси. Мастер использует отдельную закрытую подсеть
своего Compose-проекта. В общей сети с посторонними контейнерами предпочтительнее
закрепить адрес Nginx и доверять только ему. Не задавайте `0.0.0.0/0`, `::/0` или
произвольные адреса из пользовательских заголовков. Если список пуст, IP-заголовки
прокси не считаются доверенными: в журнале может быть адрес самого прокси.
Браузер не обращается к БД, брокеру или Docker.

При `ADMIN_ENABLED=false` Go не поднимает admin listener, а стартовый скрипт
Nginx удаляет его server-конфигурацию. Применяйте переключатель пересозданием
контейнеров API и proxy через используемый deployment workflow. Публикация порта
остаётся зарезервированной в Compose, но на нём нет административного TLS/HTTP
сервера. Основное приложение продолжает работать. В `.env*.example` админка
выключена по умолчанию, чтобы обновление не открывало новый интерфейс автоматически.

Для ограничения доступа можно поставить `ADMIN_BIND_ADDRESS=127.0.0.1` и работать
через VPN/туннель либо указать адрес интерфейса VPN. При прямом внешнем доступе
ограничьте порт административными IP средствами firewall. В shared-host overlay
при отсутствии `ADMIN_BIND_ADDRESS` административный порт привязан к loopback;
значение из `.env` имеет приоритет. Основной HTTP-прокси
за Apache сохраняет прежний адрес `127.0.0.1:19080`.

## Первая установка

`install.sh` сохраняет существующий workflow: скачивает проверенный пакет образов
или собирает выбранный коммит, затем запускает `scripts/install/wizard.py`.
Нужен новый выпуск, в котором API содержит `/app/meetspace-admin`, а proxy — сборку
админки; исторический upstream-образ Nginx этих возможностей не имеет.

Мастер запрашивает HTTPS-порт админки, применяет миграции и вызывает CLI `status`.
Только если администраторов ещё нет, он запрашивает логин, пароль и подтверждение.
Логин: 3–40 латинских букв, цифр, `.`, `_`, `-`, первый символ — буква или цифра;
регистр нормализуется. Пароль: 12–128 символов, минимум буква и цифра, до 512 байт
UTF-8. Пароль вводится без эха и передаётся CLI JSON через stdin. Он не записывается
в `.env`, installation.json, временные файлы, аргументы процесса или вывод мастера.
Если безопасный скрытый ввод недоступен, установка останавливается.

При продолжении прерванной установки `status` обнаруживает существующего
администратора: повторный ввод и сброс пароля не выполняются. Ошибка миграции,
создания аккаунта или проверки HTTPS не позволяет отметить установку завершённой.
Мастер проверяет локальный TLS с реальным hostname/SNI, страницу панели (`200`),
неавторизованный `/api/v1/admin/auth/me` (`401`) и запрет этого пути на `443` (`404`).
После успеха выводятся URL приложения, URL панели и логин; пароль не выводится.
Локальная проверка не подтверждает проходимость внешнего firewall.

## Обновление существующей установки

1. Выполните принятую процедуру остановки записи/дренирования и резервного
   копирования БД и объектов. Сохраните прежний manifest и конфигурацию вне репозитория.
2. Соберите и проверьте полный новый выпуск. `scripts/release/build.sh` теперь
   собирает proxy вместе с admin SPA и для classic, и для hardened layout.
   `package.sh` не переиспользует proxy из старого infrastructure manifest:
   его содержимое связано с версией приложения.
3. Через существующий `release.sh migrate` примените миграции, затем выполните
   `release.sh deploy` с теми же проектом, томами и учётными данными сервисов.
   Существующие approvals и проверки выпуска сохраняются. Не запускайте новый
   установщик в существующий каталог для обновления: он предназначен для первой
   установки и её продолжения.
4. Проверьте `/app/meetspace-admin status` внутри API-контейнера. Если в установке
   ещё нет администраторов, выполните `bootstrap` через защищённый stdin, как ниже.
   Если аккаунты уже существуют, не выполняйте сброс пароля.
5. Установите `ADMIN_ENABLED=true`, фактический URL и порт в конфигурации релиза;
   пересоздайте API и proxy. Проверьте TLS, вход и запрет маршрута на публичном порту.

Миграции должны оставаться совместимыми с пользовательским приложением. При
откате к выпуску без админки сначала выключите её, верните прежние образы и
конфигурацию proxy. Сохраняйте таблицы администраторов и аудит: удаление таблиц
или восстановление старого снимка БД может потерять аккаунты и новые данные.
Проверка совместимости конкретного старого выпуска и репетиция восстановления
резервной копии остаются обязательной частью процедуры обновления.

## CLI и восстановление доступа

CLI доступен только оператору сервера через Docker; публичного recovery endpoint нет.
В установке нового мастера:

```bash
sudo /opt/meetspace/manage.sh reset-admin-password
```

Команда интерактивно запрашивает логин, новый пароль и подтверждение, передаёт
JSON по stdin и отзывает предыдущие сессии. Логин и пароль не принимаются в argv.

Для ручного Compose-развёртывания используйте **те же `--env-file`, `-f`, `-p`**,
что и для работающей установки. Контракт бинарника:

| Команда | Вход | Выход |
|---|---|---|
| `status` | Без stdin | JSON `exists`, `username` при наличии |
| `bootstrap` | stdin JSON `username`, `password`, необязательное `name` | JSON с `username`; существующие аккаунты не перезаписываются |
| `reset-password` | stdin JSON `username`, `password` | JSON результата; предыдущие сессии отзываются |

Пример безопасного ввода для ручного восстановления (подставьте аргументы своего
Compose-проекта в последней строке; пароль не вставляйте в команду):

```bash
set -o pipefail
python3 - <<'PY' | docker compose exec -T api /app/meetspace-admin reset-password
import getpass, json, sys, warnings
warnings.simplefilter('error', getpass.GetPassWarning)
with open('/dev/tty', 'r') as terminal, open('/dev/tty', 'w') as prompt:
    prompt.write('Логин администратора: ')
    prompt.flush()
    username = terminal.readline().strip()
password = getpass.getpass('Новый пароль: ')
repeat = getpass.getpass('Повторите пароль: ')
if not username or password != repeat:
    raise SystemExit('Логин пуст или пароли не совпадают; пароль не изменён.')
json.dump({'username': username, 'password': password}, sys.stdout)
PY
```

Для создания первого администратора замените последнюю команду CLI на `bootstrap`;
предварительно вызовите `status`. Не используйте `echo '{...пароль...}'`, аргументы
`--password`, переменные окружения с паролем или сохранённые JSON-файлы.
Python не гарантирует стирание строк из памяти; процессы ввода и CLI завершаются
сразу после операции. Не включайте shell trace при работе с секретами.

## Реализованные ограничения

Аудит от 5 ноября 2026 добавляет миграцию **40** с двумя trigram GIN-индексами
для поиска пользователей и журнала. Индексы создаются внутри транзакции:
на крупной базе заранее измерьте время и выполняйте обновление в окне обслуживания.
Проверки, замеры, исправленные ошибки и оставшиеся ограничения приведены в
[ADMIN_AUDIT_RU.md](ADMIN_AUDIT_RU.md). Новые audit actions `*_failed` фиксируют
отклонённые значимые операции без payload и секретов; при отказе самой БД
долговременная запись такого события не гарантируется.

- Административные сессии действуют до 12 часов; на учётную запись допускается
  не более 20 сессий. При входе просроченные записи сессий очищаются порциями
  до 500 строк. Dashboard кеширует агрегаты на 10 секунд, поэтому показатели
  могут обновляться с этой задержкой.
- Блокировка пользователя сохраняет его данные и запрещает последующие
  авторизованные запросы. На текущем экземпляре API общие WebSocket-соединения
  закрываются сразу; на других экземплярах проверка блокировки выполняется
  приблизительно каждые 5 секунд. Конференционные соединения проверяются при
  следующем pong, то есть задержка зависит от `WS_PING_INTERVAL`. Старый SSE-поток
  перепроверяет доступ приблизительно каждые 15 секунд. Завершение медиасоединений
  проходит через существующую очистку соединений; одномоментное отключение всех
  участников на всех репликах не гарантируется.
- Настройки в текущей версии доступны **только для чтения** из действующей
  конфигурации. Панель не копирует `.env` в БД и не предлагает сохранять параметры,
  для которых нет подтверждённого механизма безопасного применения. Изменения
  выполняются через принятую серверную процедуру; секреты не раскрываются в UI.
- Раздел «Система» использует проверки API, Media Worker, Record Worker,
  Product Worker, PostgreSQL, Redis и RabbitMQ. CPU, RAM и ёмкость файлового
  хранилища не подменяются приблизительными числами: при отсутствии источника
  метрик API возвращает `null`, интерфейс показывает «Нет данных».
- Конференции доступны для просмотра; принудительного завершения нет. Для чатов
  доступны агрегаты, без чтения личных сообщений. Журнал аудита нельзя изменять
  или удалять через панель.

Прежний endpoint операционных агрегатов `/api/v1/admin/summary` перенесён в
`/api/v1/platform/summary`; его вызов в пользовательском frontend обновлён.
Существующий `users.is_admin` сохраняется только для доступа к этим агрегатам
и не превращает пользователя в администратора новой панели. Пространство
`/api/v1/admin/` целиком принадлежит отдельным административным аккаунтам и
остаётся закрытым на публичном порту `443`.

## Проверки исходников

```bash
python3 -m unittest discover -s scripts/install -p 'test_*.py'
bash -n install.sh scripts/release/build.sh scripts/release/package.sh
sh -n dockers/production/25-admin-config.sh
cd admin && npm ci && npm run build
```

Из корня репозитория можно отдельно проверить listener и маршрутизацию в
одноразовых Nginx-контейнерах без публикации портов хоста (образ
`nginx:1.30.6-alpine` должен быть предварительно загружен):

```bash
RUN_ADMIN_PROXY_TESTS=1 python3 -m unittest discover -s scripts/install -p 'test_admin_proxy.py'
```

Для проверки уже собранного proxy-образа добавьте `ADMIN_PROXY_TEST_IMAGE=имя:тег`:
тогда тест проверяет упакованные SPA, JavaScript и стартовый скрипт, а не fixtures.

При подготовке этого изменения выполнены полный набор Go-тестов, PostgreSQL
integration suite, frontend-тесты и production-сборка админки. Проверки мастера
охватывают сохранение существующих аккаунтов, передачу пароля только через stdin,
ошибки bootstrap и TLS-проверку. Compose проверен с нестандартным портом `9443`
для всех поддерживаемых сочетаний конфигураций; внутренний `8082` не публикуется.
Отдельно собран реальный proxy-образ и проверены его SPA/JavaScript, запрет admin
API на `443` и отсутствие listener при `ADMIN_ENABLED=false` в одноразовых
контейнерах с тестовым сертификатом.

5 ноября 2026 выполнен отдельный rollout существующего хоста
`meeting.janickiy.com`: внешние TLS/HTTP и браузерные проверки прошли.
Результаты, исправление исторических checksums и оставшиеся шаги создания
администратора/публикации описаны в [ADMIN_AUDIT_RU.md](ADMIN_AUDIT_RU.md).
Полная установка на чистом Linux-хосте и восстановление резервной копии БД
не выполнялись; этот rollout не заменяет такие проверки.
