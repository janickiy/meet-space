# Производительность MeetSpace: проверенные сравнения

Дата: 2026-11-06. Исходник `1e27a55`, исправления в `codex/full-optimization-20261106`.
Нет измеренного процента ускорения всей системы. Ниже отдельные запросы и пути
с одинаковыми fixtures/версией runtime; разброс указан явно.

## PostgreSQL: видимость уведомлений

Изолированный PostgreSQL 16 Alpine, Docker arm64, лимит 2 CPU/1 GiB,
512 MiB tmpfs для данных. Две синтетические учётные записи, личный диалог,
30 000 сообщений и 100 уведомлений последних сообщений. Индексы только из
существующих миграций. `ANALYZE` после загрузки fixture. Реальный
`NotificationRepository.List` делает страницу 50+1 и unread count.

Тест перехватывает SQL репозитория, исполняет пять `EXPLAIN (ANALYZE, BUFFERS,
FORMAT JSON)` каждого запроса. Исходная версия повторно проверена **тем же конечным
тестом** через Go `-overlay`, подставляющий только исходный `chat_notifications.go`.
После исправления команда без overlay. Ни production, ни пользовательская БД
не использовались. Время — execution time PostgreSQL; HTTP/JSON/network вне замера.

| Запрос | До, min / median / max, ms | После, min / median / max, ms |
|---|---:|---:|
| Страница уведомлений | 186.720 / 211.765 / 239.986 | 0.791 / 1.012 / 1.035 |
| Счётчик непрочитанных | 311.136 / 318.192 / 414.298 | 0.730 / 0.756 / 0.852 |

| Работа с `conversation_messages` | До | После |
|---|---|---|
| План | Seq Scan, фильтрация UUID как текста | Index Scan по `conversation_messages_pkey` |
| Страница | 51 обход, примерно 29 948 отфильтрованных строк на обход, 41 306 shared-hit blocks | 100 индексных lookup, 300 shared-hit blocks |
| Счётчик | 100 обходов, 29 950 отфильтрованных строк на обход, 80 997 shared-hit blocks | 100 индексных lookup, 300 shared-hit blocks |

Планировщик вправе выбирать другой план на иных данных. Тест защищает сценарий
большой истории; время не используется как нестабильный PASS/FAIL-порог.
Регрессия до исправления падает по отсутствию ID в Index Cond, после проходит.
Семантика проверена сравнением исходного и нового SQL, включая некорректные JSON ID
и изменения доступа к личным, групповым и конференционным сообщениям.

Повторить проверки на созданной скриптом пустой БД:

## Realtime: событие комнаты с двумя адресатами

Go 1.26.10, darwin/arm64, Apple M5. Один процесс, остальные локальные сокеты
принадлежат другой комнате. Пять прогонов одинакового benchmark:

```sh
go test ./internal/usecase/realtime -run TestEntries -bench BenchmarkEntriesSmallRoom -benchmem -count=5
```

|---|---:|---:|---:|---|
| 100 | 896 → 24 | 1 → 2 | 506.7 → 441.8 | 482.9–517.2 / 434.9–455.5 |

## SFU: запись RTP и закрытие ресурсов

`BenchmarkRecordPacket`, RTP payload 1 200 B, пять прогонов по 500 ms:

```sh
go test ./internal/infrastructure/sfu -run '^TestRecordPacketPreservesMediaAndOwnership$' -bench '^BenchmarkRecordPacket$' -benchmem -benchtime=500ms -count=5
```

| Путь | ns/op min–max; median до | После | B/op; allocs/op |
|---|---|---|---|
| Запись выключена | 5.980–6.847; 6.474 | 5.185–5.350; 5.254 | 0; 0 в обеих версиях |
| Запись включена | 194.7–196.8; 196.0 | 187.8–196.3; 191.3 | 1 280; 1 в обеих версиях |

Аллокации не снизились: Go уже размещал короткий slice на стеке. Диапазоны активной
записи перекрываются, достоверное ускорение записи **не заявляется**. Упрощён
ненужный fanout единственной эксклюзивной подписки, сохранено владение RTP-буфером.

После lifecycle-исправления выполнены 800 join/leave циклов, 40 срезов:
комнаты/peers/tracks/subscriptions пусты, contexts отменены, PeerConnection закрыты;
во всех срезах по 2 goroutine. HeapAlloc 363 312 → 571 712 B с прогревом runtime;
последняя серия 570 848 → 571 712 B. Это синтетический жизненный цикл,
не длительная нагрузка реальным медиатрафиком.

TCP-regression до исправления: успешный Shutdown, но незарегистрированное
STUN-соединение продолжает жить и чтение завершается только timeout 250 ms.
После исправления соединение и ожидающее первое чтение закрываются; проверено
20 повторениями с race detector. Это подтверждение владения ресурсом,
а не заявка об отсутствии всех сетевых утечек.

## Frontend: стартовый JavaScript

Node 24.22.1, Vite production build, одинаковые зависимости/настройки,
новый Chrome context, `/login`, ожидание networkidle. Из PerformanceResourceTiming
взяты действительно загруженные JS chunks, затем подсчитаны размер файлов и
`zlib.gzipSync` с уровнем по умолчанию. Не измерялись TTI или задержки сети.

загрузки рабочего приложения. Проверены тексты,
H1, title, description, canonical, JSON-LD на 17 публичных маршрутах и переход
из login в документацию с поиском. Обычная и marketing-only сборки проходят.

## Память браузера и ограничения

Админка не менялась: bundle 393 179 B / 117 656 B gzip. В изолированных HTTP fixtures:

- 100 переходов, 50 модальных циклов, 10 login/logout: DOM 426 → 426,
  listeners 184 → 184, documents 1 → 1, JS errors 0; post-GC heap
  2 977 048 → 5 109 152 B. Рост может включать прогрев маршрутов/кешей;
  retaining paths не исследованы, причина роста не установлена.
- 180-секундный Dashboard soak: 13 HTTP-запросов; DOM/listeners/documents стабильны,
  JS errors 0. Post-GC heap: 3 045 292, 3 232 832, 3 394 712, 3 474 824 B.
  Прирост **429 532 B**. Длительное плато не доказано, нужен 30–60-минутный
  прогон с retaining paths; считать этот рост исправленной утечкой нельзя.

Нет замеров p50/p95/p99/RPS всей платформы, production CPU/RSS/fd, packet loss/jitter
и end-to-end latency. Не выполнен полный media/recording soak через реальные
устройства, TURN и S3. Для этих задач нужен отдельный согласованный нагрузочный
стенд; локальные цифры выше не являются прогнозом ёмкости сервера.
