# Выпуск неизменяемых артефактов

> При обновлении старой установки сначала выполните [переход на record-worker и миграцию 000037](operations/speech-removal-upgrade.md). Миграция необратимо удаляет данные функций речи; требуются проверенная резервная копия и остановка старых процессов. Простой откат образов после неё не поддерживается.

Порядок выпуска: исходники → проверка кода и безопасности → сборка → проверка
образов, SBOM и упаковка → проверочный стенд → ручная проверка и наблюдение →
решение оператора → рабочее окружение → проверка либо откат.
Отчёт проверок заполняют для конкретного выпуска и окружения.

**Область применения команд:** общий процесс выпуска из
`scripts/release/common.sh`. Для установки через `install.sh` сначала прочитайте
[различия Compose-топологий](DEPLOYMENT.md#выбор-процедуры-по-типу-установки).
`manage.sh` не обновляет приложение; `release.sh` не использует автоматически
дополнительные файлы Compose, созданные мастером. Архив выпуска и конфигурация
запущенных служб — отдельные характеристики; при обновлении учитывают обе.

## Версия, артефакты и CI

Формат тегов — `vX.Y.Z`; допустимы предварительные версии, например `v1.2.3-rc.1`.
Первая цифра (major) обозначает несовместимые изменения контрактов, вторая (minor) —
совместимые возможности, третья (patch) — совместимые исправления. Даже для patch
отдельно проверяют совместимость SQL и конфигурации. Описание выпуска составляют
по [шаблону](RELEASE_NOTES_TEMPLATE.md).

Каждый выпуск связан с полным SHA коммита Git, временем UTC и отпечатком исходников.
Для выпуска в реестр нужна чистая рабочая копия. Упаковщик сверяет версию, коммит
и отпечаток исходников с метками OCI; проверочный и рабочий стенды требуют
`sourceFingerprintVerified:true`. `--allow-dirty-local` допускается только
для локальной репетиции и фиксируется `sourceDirty:true`. Это не выпуск для рабочего окружения.
Публичные `/version` и `/version.json` сверяются с манифестом, а не с изменяемым тегом.

Текущий [процесс GitLab CI](../.gitlab-ci.yml):

| Этап | Проверки |
| --- | --- |
| Проверка кода | gofmt, vet, staticcheck, синтаксис скриптов выпуска; проверка стиля интерфейса, TypeScript и сборка для рабочего окружения |
| Безопасность | govulncheck; npm audit с блокировкой high/critical |
| Сборка | Исполняемые файлы приложения |
| Упаковка версии по тегу | Сборка Docker, SBOM и проверка всех образов выпуска; high/critical блокируют пакет; публикация по дайджесту |

CI проверяет код, сборку и безопасность. Пользовательские сценарии, браузеры,
доступность и нагрузку проверяют отдельно по [чеклисту](operations/RELEASE_CHECKLIST.md).

`release-package` требует отдельного исполнителя Docker и учётных данных реестра и
проверенного `TRIVY_IMAGE=…@sha256:…`. `deploy-dev` синхронизирует исходники
и пересобирает окружение разработки; для рабочего окружения используется описанная
ниже процедура с неизменяемыми артефактами.

## Сборка и упаковка один раз

Примеры выполняются из корня рабочей копии с подготовленными инструментами и
Docker. Каталоги/версии выбираются новыми; существующий тег выпуска не перезаписывается.

```bash
RELEASE_VERSION=v1.2.3
RELEASE_COMMIT="$(git rev-parse HEAD)"
ARTIFACT_DIRECTORY=/absolute/artifacts/v1.2.3
bash scripts/release/build.sh --version "$RELEASE_VERSION" --commit "$RELEASE_COMMIT" --registry registry.example.org/team/meet --output "$ARTIFACT_DIRECTORY/build"
bash scripts/release/package.sh --build "$ARTIFACT_DIRECTORY/build/build.json" --output "$ARTIFACT_DIRECTORY/package" --mode registry
```

Это начальный пакет для первого развёртывания. При обычном обновлении приложения
добавьте к команде упаковки `--infrastructure-manifest
/absolute/artifacts/previous/release.json`. Пакет сохранит **точно те же** образы
S3-хранилища, PostgreSQL, Redis, RabbitMQ, Coturn, proxy, Prometheus
и Grafana (только classic); новыми
будут только шесть служб приложения, указанных в описываемой редакции.
Количество компонентов после удаления речевых сервисов сверяйте с актуальным
[техническим руководством](MEETSPACE_TECHNICAL_GUIDE_RU.md). Отдельно собранный новый образ S3 в этом
случае не используется. Предыдущий манифест должен быть проверен оператором и
иметь тот же режим (`local`, `registry` или `archive`) и совместимую топологию
classic/hardened; смена формата S3-тома этим флагом не выполняется. Его SHA-256 записывается в новый
манифест, а проверка уязвимостей повторяется и для сохранённой инфраструктуры.

В CI передайте предыдущий манифест через защищённую File variable
`RELEASE_INFRASTRUCTURE_MANIFEST`; задание автоматически добавит этот флаг. Только
для первого развёртывания оставьте File variable пустой и явно задайте
`RELEASE_BOOTSTRAP=true`. Без выбранного режима задание останавливается до сборки;
одновременно включать оба режима нельзя. Автоматически выбирать «последний» тег или менять инфраструктуру
вместе с кодом приложения запрещено. Изменение дайджеста любого инфраструктурного образа
оформляется отдельным обслуживанием с резервной копией, проверкой совместимости данных и
собственным планом отката. Обычный `release.sh deploy` такое изменение отклоняет.

Замените адрес реестра из примера. Учётные данные Docker login получают из
хранилища секретов или CI; пароль передают через stdin, а не аргумент командной
строки. До упаковки задайте `TRIVY_IMAGE`, закреплённый дайджестом.
Флаг телеметрии интерфейса `CLIENT_TELEMETRY_ENABLED=true` задают перед сборкой
только при явном решении включить отправку. По умолчанию она отключена.

Для локальной репетиции: собственный префикс, например `meet-release-local`,
при необходимости `--allow-dirty-local` при сборке, `--mode local` при упаковке.
`--skip-security-local` разрешён только локально и означает **непроверенный**
пакет. Локальный пакет сохраняет ID образов, `images.tar`, `release.json`,
`SHA256SUMS`; пакет реестра сохраняет дайджесты образов, отчёты проверки и SBOM.
Неполную сборку после ошибки не считайте готовым пакетом и не дописывайте поля
`securityScanned` вручную. Неизменяемость манифеста не делает неизвестный
источник автоматически доверенным.

Административные исполняемые файлы также заранее собирают в CI или на сервере
сборки и проверяют для архитектуры целевой машины. Их не собирают во время
аварийного отката. Образы включают утилиты миграции и резервного копирования. Режим `--mode archive` создаёт проверенный переносимый архив и
принимается проверочным и рабочим окружениями при чистых исходниках и успешной
проверке безопасности;
`local` предназначен только для репетиции. `build.sh --layout hardened-shared-host`
выбирает hardened-образы с SeaweedFS; по умолчанию сборка и CI используют classic.
В режиме сборки `install.sh` создаёт защищённый архив hardened, проверяет его
и применяет конфигурацию отдельного сервера через `wizard.py`.
Актуальный режим по умолчанию см. в [INSTALLATION.md](INSTALLATION.md).
При переносе локального архива сначала сверяют `SHA256SUMS`, затем загружают
архив Docker. Во время инцидента старый коммит не пересобирают.

## Миграции

В описываемой редакции набор состоял из 35 `.up.sql`; это историческое число,
не количество миграций текущей версии. В установке мастером тот же мигратор вызывается
сервисом `migrate` с её полным Compose-контекстом; приведённые ниже команды
`release.sh migrate` относятся к общему процессу выпуска.

Один назначенный оператор или задание CI выполняет `release.sh migrate` **до** запуска
нового приложения. В Compose рабочего окружения `AUTO_MIGRATE=false`: при запуске проверяется
журнал миграций, но не выполняет DDL. `release_schema_migrations` содержит имя файла,
SHA-256 точных байтов, время применения и продолжительность. Применённый SQL нельзя
переименовывать, переводить комментарии или редактировать: добавляется новая миграция.

Одновременное выполнение миграций исключается advisory lock PostgreSQL.
Задание использует транзакцию, `lock_timeout=15s` и общий срок выполнения 5 минут.
При ошибке набор изменений откатывается и выпуск прекращается. Старая БД без
журнала миграций один раз проходит имеющиеся идемпотентные up-файлы;
заполнение журнала без выполнения миграций не предусмотрено. Измеряйте
длительность и блокировки на представительной копии, включая индексы миграции
`000021`. Не переносите короткий локальный замер на большую БД рабочего окружения.

Рискованные изменения выполняют поэтапно: расширение схемы (Expand) → совместимое
развёртывание → заполнение и проверка данных → удаление старой структуры (Contract)
в отдельном последующем выпуске. Откат приложения не выполняет обратные миграции БД.
Журнал допускает более новые миграции, но не подтверждает совместимость старого
кода с их смыслом; её проверяют на репетиции и описывают в примечаниях к выпуску.

`000022_remove_raised_hands` удаляет счётчик и время последнего поднятия руки
из аналитики. Функция исключена из API, обмена событиями в реальном времени и интерфейса. Перед применением
нужна резервная копия: down-скрипт восстанавливает только колонки, не прежние значения.
Старый API несовместим с этой схемой; обновление требует окна обслуживания:
остановить старые экземпляры API, применить миграцию, запустить новую версию.
Не смешивайте версии при последовательной замене экземпляров. Откат старого API возможен только
после согласованного восстановления схемы; при необходимости прежних счётчиков —
из резервной копии. Старые временные ключи Redis истекают по часовому TTL и новой версией
не читаются и не создаются; очищать весь Redis не нужно.

## Проверка и продвижение

На проверочном стенде зафиксируйте исходные показатели, приостановите изменение
данных и создайте резервную копию. Выполните миграцию, развёртывание нового пакета,
служебные и ручные проверки, принудительное подключение через TURN/TURNS и запись.
Проверьте запись через ffprobe, воспроизведение и S3, затем выполните откат
и повторно разверните тот же пакет. Сохраните результаты, время, версии,
ограничения и ошибки. Процедура резервного копирования:
[backup-restore.md](operations/backup-restore.md); команды развёртывания —
[DEPLOYMENT.md](DEPLOYMENT.md).

После установки пакета оператор выполняет проверки существующими аккаунтами:

1. Сверить публичные `/version` и `/version.json` с точными версией и коммитом выбранного
   манифеста. Проверить HTTP-ответ главной страницы и загрузку её ресурсов.
2. Через закрытый доступ проверить `/health/live` и `/health/ready` каждого
   изменённого сервиса; готовность должна быть подтверждена, режим завершения работы — выключен.
   Проверить очереди, БД/Redis/S3 и отсутствие роста ошибок в метриках/логах.
   Не открывайте внутренние проверки состояния, метрики и управление в публичном прокси.
3. С согласованным существующим обычным аккаунтом вручную проверить вход,
   `auth/me`, capabilities, ICE config, запрет admin и изменённые экраны.
   Не сохраняйте JWT, cookies и пароли в отчёт или общедоступные файлы.
4. С согласия участников проверить WebSocket, медиа, принудительную ретрансляцию через TURN/TURNS и доступ к
   ранее созданным записям/материалам. Новые встречи или записи создавать только
   как отдельную явно согласованную проверку функционала, не автоматически при выпуске.
5. Записать фактические версии, результаты, время и ограничения в отчёт.
   Успешные проверки состояния и версии не подтверждают реальную работу RTP, TURN,
   FFmpeg, файлов, зала ожидания или всех сценариев браузера; их проверяют отдельно.

Пример безопасных публичных GET-проверок (сопоставление с манифестом обязательно):

```bash
curl --fail --silent --show-error https://meet-staging.example.org/version
curl --fail --silent --show-error https://meet-staging.example.org/version.json
curl --fail --silent --show-error --output /dev/null https://meet-staging.example.org/
```

## Разрешение на выпуск в рабочее окружение

Для каждой операции, изменяющей рабочее окружение, нужен существующий JSON-файл
`--evidence`, указанный абсолютным путём, и `RELEASE_PRODUCTION_APPROVAL`, точно
равный версии выбранного манифеста. Отчёт должен описывать **реальные** проверки
и содержать:

```json
{
  "version": "v1.2.3",
  "commit": "FULL_40_CHARACTER_SHA",
  "manifestSHA256": "SHA256_OF_EXACT_RELEASE_JSON",
  "migrationCompatible": false,
  "backupVerified": false,
  "rollbackReady": false,
  "stagingSmokePassed": false,
  "mediaSmokePassed": false,
  "securityPassed": false,
  "applicationRollbackCompatible": false,
  "approvedBy": "",
  "evidenceReferences": []
}
```

Этот пример намеренно не проходит проверку. Для deploy/migrate/drain/resume нужны
первые шесть подтверждений: совместимость, резервная копия, готовность отката,
проверочный стенд, медиа и безопасность. Для rollback вместо трёх последних
проверяется `applicationRollbackCompatible`.
`stagingSmokePassed` и `mediaSmokePassed` означают документированные проверки
проверочного стенда и медиа. Непроведённые проверки остаются `false`.
`approvedBy` и `evidenceReferences` обязательны. Коммит и хеш манифеста должны
совпасть побайтно. Скрипт проверяет структуру утверждений, не истинность подписанта
и не подлинность стороннего отчёта; проверка отчёта остаётся ответственностью оператора.

```bash
export RELEASE_PRODUCTION_APPROVAL=v1.2.3
bash scripts/release/release.sh deploy --environment production --project recorder-production --env-file /srv/meet/config/production.env --manifest /srv/meet/releases/v1.2.3/release.json --evidence /srv/meet/evidence/v1.2.3.json
unset RELEASE_PRODUCTION_APPROVAL
```

## Поэтапное включение и наблюдение

В приложении нет встроенного выбора пользователей для пилота или распределения
части трафика на новую версию. Флаги конфигурации действуют на всё развёртывание.
Минимальный порядок: проверьте выпуск в отдельном изолированном или пилотном
окружении, затем вручную включите согласованный набор функций в целевом env-файле
и пересоздайте совместимые процессы. Экземпляры одного сервиса должны использовать
согласованные флаги и контракты провайдеров. Отключение флага не удаляет созданные данные.

После развёртывания проверьте HTTP, авторизацию, WebSocket, подключение медиа,
ICE/TURN, завершение записей, очереди RabbitMQ и заданий PostgreSQL, БД, Redis, S3,
ошибки провайдеров и клиентов.
Предлагаемый порядок наблюдения и SLI — [инструкция по эксплуатации](operations/README.md).
Системные ошибки авторизации, медиасвязи или WebSocket, повреждение/недоступность записи, несовместимость
схемы или неконтролируемый рост ресурсов блокируют продвижение и требуют
решения об отключении вспомогательной функции либо [отката](ROLLBACK.md).
