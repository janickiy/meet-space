## Область проверки и трактовка результатов

Проверялась существовавшая локальная копия с незакоммиченными изменениями, а не чистый образ выпуска или рабочая установка. Изменения `frontend/src/components/RealtimePanel.tsx` и `frontend/src/pages/conference.css` сохранены в обеих сборках веб-клиента. Тесты использовали loopback-серверы, имитации ответов API браузера и синтетические серверные данные. Рабочий трафик, учётные данные, аккаунты, записи и реальные встречи не использовались.

Подтверждены ограничение владения ресурсами и корректное поведение при перегрузке, а не рост пропускной способности приложения. Настройка производительности без подтверждающих измерений не выполнялась. Отсутствие измерения нельзя считать прохождением критерия приёмки.

## Измерения ресурсов браузера

### Соединения отклонённых потоков уведомлений

`tools/audit/notification-stream-browser.mjs` выдаёт исходный и исправленный API-модуль с локального HTTP-сервера и возвращает незавершённые тела ответов. Пять последовательных запросов каждого сценария не достигают обычного браузерного предела HTTP/1 в шесть соединений. После отказа запросов сценарий ждёт, принудительно запускает сборку мусора и считает открытые ответы на сервере.

| Сценарий | Открытые ответы исходной версии после GC | Открытые ответы исправленной версии после GC |
| --- | ---: | ---: |
| Пять ответов HTTP 503 | 5 / 5 | 0 / 5 |
| Пять ответов HTTP 200 с неверным типом SSE | 5 / 5 | 0 / 5 |

Явная отмена тела освобождает соединения, ранее переживавшие сборку мусора. Это предотвращает накопление при ошибках переподключения уведомлений, но не устанавливает рабочую задержку, экономию RSS и пропускную способность. Связанный модульный тест получил 0 отменённых потоков из 50 до исправления и 50 из 50 после; все семь тестов уведомлений прошли.

Итоговый повтор браузерной проверки сохранён в `tmp/web-audit-20261026/evidence/notification-stream-browser-final.log`.

Пять дополнительных Node-тестов запускают настоящий медиаклиент конференции с синтетическими браузерными примитивами. ## Ограничение серверных вычислений пароля

У исходного сервиса авторизации не было общего предела одновременного вычисления хешей. Управляемая блокирующая имитация провайдера воспроизвела три активные операции при ожидаемом пределе в две. Это не измеренный пик рабочей системы.

Исправление предоставляет два общих слота, получаемых немедленно при регистрации, входе и удалении с подтверждением пароля. При заполнении слотов запрос получает существующую ошибку ограничения частоты/HTTP 429 вместо попадания в неограниченную очередь. Отменённые запросы не начинают вычисление; успешные и ошибочные завершения освобождают слот.

Настроенный рабочий объём Argon2 — 64 MiB на вычисление. Поэтому два вычисления дают **расчётный предел активной памяти Argon2 в 128 MiB на экземпляр сервиса авторизации**. Это не измеренный предел RSS всего процесса: накладные расходы среды, другие запросы, уже выделенная или ещё не собранная память и другие экземпляры приложения не входят в него. Тест использует блокирующую имитацию, а не реальные выделения Argon2. Параметры стойкости пароля не ослаблены.

При параллельной нагрузке авторизации намеренно допускается больше HTTP 429 вместо неограниченного хеширования. p50/p95/p99 обычного входа, устойчивая пропускная способность, общий RSS, конкуренция за CPU и оптимальное для установки число слотов не измерялись. Фиксированное число слотов нельзя считать универсально оптимальным.

## Профилирование Go/SFU и проверки БД

Короткий локальный тест жизненного цикла SFU создал профили CPU и кучи в `tmp/web-audit-20261026/evidence/sfu-*`:

- Длительность профиля CPU — **201.89 ms**, всего выборок CPU — **10 ms**. Они пришлись на криптографию генерации сертификата. Выборка слишком мала, а сценарий слишком узок для выводов об узком месте и оптимизации.
- Выборочный объём используемой кучи — **2,051.01 KiB**, отнесённый к созданию потоков/таймеров среды выполнения. Это не RSS всего сервера, не характерная удерживаемая память медиасессии и не сравнение до/после.
- Тест не определяет пропускную способность аудио/видеопакетов, повторную передачу, производительность TURN, джиттер, задержку и стоимость кодирования/записи.

Подтверждающие файлы в указанном каталоге: `sfu-profile.log`, `sfu-cpu-top.txt`, `sfu-heap-top.txt`, `sfu-cpu.pprof`, `sfu-heap.pprof`. Настройки по этим малым профилям не менялись.

Интеграционные проверки прав PostgreSQL использовали изолированные синтетические данные. Они проверяют доступ, а не скорость БД. Характерные планы, `EXPLAIN (ANALYZE, BUFFERS)`, число запросов, ожидание пула, эффективность индексов, влияние N+1, насыщение и процентили времени транзакций **не измерялись**. Изменения производительности БД на этом основании не вносились.

## Воспроизведение и дальнейшие проверки

Из корня репозитория, с Node 24.19.0 в `PATH`, запустите регрессионные тесты:

```sh
node --experimental-transform-types --test frontend/tests/*.test.mjs
```

Из каталога `frontend/` соберите текущий веб-клиент в отдельный каталог:

```sh
npm run build -- --outDir ../tmp/web-audit-20261026/frontend-after-dist
```

Если автоматический поиск пакета/браузера их не находит, укажите `PLAYWRIGHT_MODULE_PATH` как точку входа Playwright и `CHROME_EXECUTABLE_PATH` как исполняемый файл Chromium. В этом запуске использовались `dependencies/node/node_modules/playwright/index.mjs` из комплектного окружения и `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`.

```sh
node tools/audit/notification-stream-browser.mjs
AUDIT_NAVIGATION_WARMUP=50 AUDIT_NAVIGATION_CYCLES=100 \
  node tools/audit/frontend-browser-smoke.mjs \
  tmp/web-audit-20261026/locked-baseline-dist \
  tmp/web-audit-20261026/frontend-after-dist
AUDIT_NAVIGATION_WARMUP=50 AUDIT_NAVIGATION_CYCLES=100 \
  AUDIT_HEAP_SNAPSHOTS=1 \
  node tools/audit/frontend-browser-smoke.mjs \
  tmp/web-audit-20261026/frontend-after-dist
node tools/audit/compare-heap-snapshots.mjs \
  tmp/web-audit-browser/frontend-after-dist-heap-0.heapsnapshot \
  tmp/web-audit-browser/frontend-after-dist-heap-100.heapsnapshot
```

Сценарий SSE читает исходный модуль из `HEAD`. После коммита исправления для исторического сравнения нужна отдельная исходная версия. Браузерный сценарий по умолчанию использует `tmp/web-audit-browser`; задайте `AUDIT_OUTPUT_DIR`, чтобы разделить результаты запусков. Снимки кучи, сборки и локальные подтверждения не предназначены для рабочей публикации.

Приоритетные измерения до дальнейшей оптимизации:

1. Подготовить изолированную многопользовательскую нагрузку с ограниченными ресурсами: авторизованная навигация, сообщения, вход/выход из конференции, реальные медиа и запись. Снять задержки, CPU, удерживаемую кучу, горутины, FD и метрики пакетов.
2. Измерить последовательность холодной/повторной начальной загрузки и Web Vitals с фиксированными устройством/сетью до изменения общих зависимостей и загрузки изображений.
3. Профилировать длинную историю чата. Сейчас загруженные страницы не ограничены и не виртуализированы; повторная загрузка каждые 15 секунд может увеличивать работу вместе с историей. Это гипотеза по коду, а не измеренное узкое место.
4. Проверить долгие сессии субтитров и звонков, чтобы оценить множества/словари устранения дублей, живущие вместе с сессией, до изменения правил их хранения.
5. Использовать характерный объём синтетической БД и планы запросов до добавления индексов, изменения кэша, пулов и настройки пагинации.

Подтверждённое освобождение соединений и предел вычислений пароля — адресные исправления устойчивости. Общая готовность к рабочей нагрузке требует недостающих характерных измерений; этот отчёт её не удостоверяет.
