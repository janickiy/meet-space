# Уведомления, почта и календари

Актуализировано 29 октября 2026 года. `product-worker` выполняет фоновые задания
доставки уведомлений, приглашений, напоминаний и синхронизации календарей.
Настройки SMTP необязательны: без них email не отправляется. Их можно добавить
после установки в закрытую конфигурацию.

## Архитектура обработки

Расписание и новые уведомления создают задания `background_jobs` в PostgreSQL
в той же транзакции, что и исходное изменение. Отдельные ограниченные пулы
обрабатывают доставку уведомлений и календарь. RabbitMQ используется для команд
записи конференций и не заменяет эту очередь.

`FOR UPDATE SKIP LOCKED` выдаёт одно задание одному обработчику. UUID аренды, срок аренды и поколение результата проверяются при сохранении. Истёкшая последняя попытка может быть захвачена для фиксации окончательной ошибки, но не для дополнительного вызова провайдера. Ошибки сети, 408, 429 и 5xx допускают ограниченное число повторов с экспоненциальным увеличением задержки и случайным отклонением (jitter). Остальные отказы провайдера и нарушение схемы считаются постоянными ошибками. `Retry-After` ограничен часом. Максимум попыток определяется меньшим из бюджета строки и текущего операторского лимита.

Доставка во внешнюю систему выполняется по модели at-least-once: повтор одной операции возможен. Шлюз (gateway) обязан сохранять `Idempotency-Key`, иначе повтор после потерянного ответа может повторить письмо или внешнюю операцию. Календарный шлюз также обязан отклонять более старый `sourceVersion`: локальная сериализация и проверка версии защищают базу, но не могут отменить уже принятый внешней системой запрос.

## Настройка и безопасные значения по умолчанию

Мастер установки предлагает настроить SMTP и проверить защищённое подключение.
Приглашённому по email отправляется отдельное письмо со ссылкой на встречу,
включая получателей без аккаунта. Для запланированной встречи второе письмо
ставится в очередь за 3 часа до начала (`REMINDER_OFFSETS=3h`). Если приглашение
отправлено позже этого момента, остаётся только первое письмо. Перенос встречи
отменяет доставку по старому времени; отмена или начало встречи также прекращают
ожидающее напоминание. Для зарегистрированных участников учитываются выключенные
напоминания, отключённые уведомления встречи и выход/исключение из неё.
Обычное уведомление в приложении сохраняется, но второе email-напоминание через
общий канал не дублирует отдельное письмо приглашённому.

Существующие установки сохраняют явно заданный `REMINDER_OFFSETS`. Чтобы получать
одно напоминание за 3 часа, замените старое значение `24h,15m` на `3h` в закрытой
конфигурации API и `product-worker` и примените её при обновлении. Пароли SMTP
не должны попадать в репозиторий. Настройка SPF/DKIM и разрешённого отправителя
выполняется у почтового провайдера; успешный приём SMTP не гарантирует папку «Входящие».

API и `product-worker` должны получать одинаковые настройки. Примеры находятся в `.env.example` и `.env.production.example`. Для каждого из `EMAIL`, `PUSH`, `CALENDAR` доступны `*_PROVIDER_MODE=noop|mock|http`, `*_PROVIDER_ENDPOINT`, `*_PROVIDER_TOKEN`.

Для email также доступен `EMAIL_PROVIDER_MODE=smtp`: он отправляет письма напрямую через SMTP и не требует HTTP-шлюза. Пример настройки Timeweb:

```dotenv
EMAIL_PROVIDER_MODE=smtp
PUBLIC_FRONTEND_URL=https://meet.example.com
SMTP_HOST=smtp.timeweb.ru
SMTP_PORT=465
SMTP_TLS_MODE=tls
SMTP_USERNAME=sender@example.com
SMTP_PASSWORD=<пароль почтового ящика, только в закрытом env-файле>
SMTP_FROM=MeetSpace <sender@example.com>
SMTP_TIMEOUT=15s
```

Вместо 465 можно выбрать `SMTP_PORT=587` и `SMTP_TLS_MODE=starttls`. [Официальная инструкция Timeweb](https://timeweb.com/ru/docs/virtualnyj-hosting/cms/otpravka-pochty-s-sajta-cherez-smtp/) указывает оба варианта и авторизацию PLAIN. Логин — полный адрес ящика, отправитель должен быть разрешён этим ящиком. Значение `tls` включает TLS сразу после подключения; `starttls` требует расширение STARTTLS до авторизации. В обоих режимах проверяются сертификат и имя сервера, минимальная версия TLS — 1.2. Незащищённая отправка и отключение проверки сертификата не предусмотрены.

`SMTP_TIMEOUT` ограничивает всю отправку, включая подключение, TLS, авторизацию и приём письма; допустимы значения от 1 секунды до 1 минуты. API и `product-worker` получают эти переменные через существующий `env_file` Compose. Для production секреты задаются в закрытом env-файле вне Git. Проверяйте доступность исходящих портов SMTP с рабочего хоста: наличие корректной конфигурации не устраняет блокировку исходящего трафика.

Письма содержат обычный текст и HTML в UTF-8, а `Message-ID` остаётся одинаковым при повторе одного задания. SMTP не гарантирует дедупликацию на стороне почтового сервера: потерянный ответ после приёма письма может вызвать повторную доставку. Положительный ответ на DATA считается успехом даже при последующей ошибке QUIT. Временные ответы 4xx и сетевые ошибки допускают повтор; постоянные отказы 5xx, неверный сертификат и отсутствие STARTTLS прекращают доставку с безопасным техническим кодом. Ответы SMTP, пароли и содержимое писем не попадают в ошибки или журналы.

`mock` разрешён только локально и в тестах. Он не отправляет реальные письма, не создаёт события в настоящем календаре. `http` использует описанный ниже универсальный шлюз (generic gateway), а не API произвольного производителя. Для рабочего сервиса нужен совместимый шлюз или другой адаптер интерфейса. SDK поставщиков не импортируются в domain/usecase.

Перед внешними интеграциями задайте `PUBLIC_FRONTEND_URL` и секрет каждого
HTTP-адаптера. Для push-уведомлений и календаря дополнительно нужен независимый
`PROVIDER_TOKEN_ENCRYPTION_KEY` — base64 от случайных 32 байт. SMTP сам по себе
этот ключ не требует: пароль SMTP передаётся через закрытый env. В production используются адреса HTTPS; перенаправления отключены. Не храните секреты в Git. Потеря ключа шифрования делает ранее сохранённые push/OAuth токены нечитаемыми; ротация с повторным подключением или отдельной процедурой перешифрования должна быть запланирована оператором.

Основные ограничения по умолчанию:

| Настройка | Значение |
| --- | --- |
| `REMINDER_OFFSETS` | `3h`, от 1 до 8 разных интервалов в пределах 1 минуты — 7 суток |
| `PRODUCT_DELIVERY_CONCURRENCY` | 2 задания доставки на процесс |
| `PRODUCT_CALENDAR_CONCURRENCY` | 1 задание календаря на процесс |
| `PRODUCT_MAX_ATTEMPTS` | 5 попыток |
| `PRODUCT_POLL_INTERVAL` | 5 секунд |
| `PROVIDER_TIMEOUT` | 15 секунд |

Добавление реплик увеличивает число одновременных внешних запросов; учитывайте
ограничения провайдеров и PostgreSQL.

## Уведомления и напоминания

### Явные приглашения участников

Организатор может пригласить до 20 адресатов через форму после создания встречи или на её странице. Допускаются email и выбранные пользователи системы; поиск по имени/email доступен при вводе от двух символов и возвращает до 20 постоянных аккаунтов. Активный соорганизатор также может приглашать. Обычный участник и гость могут поделиться публичной ссылкой.

API: `GET /api/v1/conferences/:id/invitation-users?query=...`, `POST /api/v1/conferences/:id/invitations` с `{emails?: string[], userIds?: string[]}`. Ответ POST — HTTP 202, элементы со статусом `queued` или `already_invited`. Поля пользователя не включают чужие настройки или токены. На поиск действует лимит 60 запросов в минуту, на отправку — 10 запросов в минуту на аккаунт.

Транзакция сохраняет `conference_invitations`, задание `integrations.invitation` и личное уведомление зарегистрированного адресата. Встреча появляется в его кабинете без фактического подключения: членство создаётся со статусом `left`, допуском `admitted` и пустым `joined_at`. Уже имеющееся членство сохраняется; исключённого или отклонённого участника повторное приглашение не восстанавливает. Повтор email в одной встрече не создаёт второе письмо или уведомление. После окончательной ошибки отправки повтор запроса возвращает существующее задание в очередь.

Письмо содержит название, организатора, время с явным UTC и публичную ссылку `/i/:code`; регистрация для перехода не требуется. Явное приглашение отправляется независимо от выключенного общей настройки email-уведомлений, поскольку его адресат выбран организатором. Обычные уведомления по-прежнему следуют настройкам пользователя. Перед отправкой обработчик повторно проверяет состояние встречи и допуск адресата; отменённая/завершённая встреча и исключённый участник не получают отложенное письмо. Форма подтверждает постановку в очередь, а не доставку письма.

Категории приглашений, напоминаний и записей включены по умолчанию для уведомлений внутри приложения; email и push выключены. Изменение настроек влияет на новые события и проверяется повторно перед внешней доставкой. Письмо содержит HTML и обычный текст, пользовательское название экранируется.

Планировщик работает с UTC и одной общей периодической проверкой, а не таймером на встречу. Задания будущих напоминаний имеют `available_at`; ключ включает конференцию, версию расписания и интервал. Перенос или отмена делает старые задания неактуальными. Уже прошедшие интервалы не отправляются пачкой сразу после создания поздней встречи: для этого остаётся приглашение.

Рассылка обрабатывается порциями по 100 адресатов; задания продолжения сохраняются в базе. Повторная проверка допуска при вставке и доставке защищает исключённых участников. Push-токены хранятся с AES-GCM и привязкой к пользователю и устройству; API никогда их не возвращает. Регистрация устройства имеется, но получение токена через реальный SDK веб- или мобильного клиента не реализовано в текущем веб-интерфейсе.

## Календарь и OAuth

Синхронизируются создание, изменение и отмена расписания владельца (create, update, cancel). Сопоставление (mapping) хранит конференцию, подключение, провайдера, внешний календарь и event ID, версию, статус и время последней синхронизации. При переносе обновляется событие с тем же event ID. Повтор create использует неизменный ключ. Если ответ внешней системы относится к прежней версии расписания, выполняется update того же события.

Ссылка приглашения соответствует маршруту веб-клиента `/i/:inviteCode`. Email других участников не передаются в календарь автоматически: отдельной модели их согласия на раскрытие адреса внешнему календарю пока нет. Обратные изменения из внешнего календаря и webhooks отсутствуют.

OAuth использует `provider=generic`, authorization code, S256 PKCE и одноразовый state, привязанный к пользователю и провайдеру на 10 минут. В базе лежат хеш state и зашифрованный verifier. Обработчик возврата в веб-клиенте (callback) удаляет code/state из адреса и передаёт их через авторизованный POST; access/refresh токены остаются на сервере. Задайте все `CALENDAR_OAUTH_*` адреса, client ID/secret, redirect URL и минимальные разрешения (scopes), подходящие вашему шлюзу. Адрес перенаправления должен вести на `/app/settings/calendar/generic/callback` публичного веб-клиента. OAuth start ограничен 5 запросами в минуту, callback — 10 на пользователя; регистрация устройств и изменения подключений также ограничены Redis.

Обновление токена (refresh) не восстанавливает отозванное подключение: результат сохраняется только при активном статусе и неизменном разрешении (grant). Отключение (disconnect) сначала удаляет локальные токены, затем пытается отозвать доступ у провайдера (revoke). Недоступность провайдера не восстанавливает доступ. Если внешний отзыв не выполнен, разрешение нужно отозвать вручную в аккаунте провайдера.

Журналы доступа Nginx используют `$uri` без параметров URL. Для callback веб-клиента отключён вывод ошибок upstream, способных раскрыть code/state при недоступности веб-клиента; `Referrer-Policy: no-referrer` предотвращает передачу исходного адреса через Referer. Уже выполняющийся внешний запрос нельзя гарантированно отозвать одновременно с disconnect, но его поздний ответ не восстанавливает grant и не сохраняет активное сопоставление.

## HTTP-контракты провайдеров

Все запросы используют серверный `Authorization: Bearer` и стабильный `Idempotency-Key`; тела не журналируются. Классификация ошибочного ответа не должна раскрывать секреты. Платные провайдеры не нужны для CI.

Почтовый шлюз принимает `POST <endpoint>/email/send` с `{idempotencyKey,to,subject,html,text}`. Push — `POST <endpoint>/push/send` с `{idempotencyKey,token,title,body,url}`. Успех — любой 2xx; JSON результата для этих операций не требуется.

Календарный шлюз принимает POST на `calendar/create`, `calendar/update`, `calendar/cancel`, `calendar/get`. Тело содержит `{event,accessToken}`; event включает `idempotencyKey`, внешний `id`, `calendarId`, `title`, `joinUrl`, UTC `startsAt` и `endsAt`, `sourceVersion`, опциональный список `attendees`. Create/update/get должны вернуть объект event с непустым `id`. Cancel может вернуть пустой 2xx. Лимит ответа — 1 MiB. Требования к дедупликации и отклонению старой версии обязательны для шлюза.

## API и права доступа

Адреса ниже относительны к `/api/v1` и требуют Bearer JWT. Настройки
пользователя, устройства и подключения доступны только их владельцу.
Состояние календаря встречи доступно допущенному организатору или соорганизатору.
Проверки выполняются сервером.

| Маршрут | Назначение |
| --- | --- |
| `GET/PUT /notifications/preferences` | Собственные категории и каналы |
| `GET/POST /notifications/devices` | Собственные регистрации push-устройств без токенов в ответе |
| `DELETE /notifications/devices/:deviceId` | Отзыв собственного устройства |
| `GET /integrations/capabilities` | Режимы адаптеров без секретов |
| `GET /integrations/calendars` | Собственные подключения |
| `POST /integrations/calendars/mock` | Только локальное или тестовое подключение |
| `GET /integrations/calendars/generic/connect` | Начало OAuth |
| `POST /integrations/calendars/generic/callback` | Одноразовый code/state |
| `DELETE /integrations/calendars/:connectionId` | Отзыв подключения |
| `GET /conferences/:id/calendar` | Сопоставление с внешним календарём для допущенного owner/co_host |
| `GET /search?q=...` | Поиск названий доступных встреч, `mode=keyword` |

## Поиск встреч

PostgreSQL индексирует названия конференций через `tsvector` с конфигурацией
`simple` и GIN. Допуск проверяется до подсчёта и выдачи результатов.
Поиск поддерживает `source=all|conference`, `mode=keyword`,
`membership=all|owned|participating`, `participantId`, `conferenceId`,
`from` и `to` в RFC3339, `limit` до 100 и `offset` до 10000.
Запрос ограничен 500 Unicode-символами и 2000 байтами. `snippet` — обычный текст,
не HTML. Ответ содержит `effectiveMode=keyword`. Поиск сообщений в чатах
работает отдельными маршрутами.

## Эксплуатация и сроки хранения

Обычный и production Compose запускают `product-worker`. Без него новые
фоновые задания остаются в PostgreSQL. Порт проверок состояния — 8092; `/metrics` и
`/operations/drain` защищены `METRICS_SECRET`. Для отправки почты и календарных
запросов FFmpeg и доступ к объектам записей не нужны.

Метрики: `recorder_product_jobs_total`, `recorder_product_job_duration_seconds`, `recorder_product_queue`, `recorder_product_provider_calls_total`, `recorder_product_provider_duration_seconds`, `recorder_search_requests_total`, `recorder_search_duration_seconds`. Метки ограничены значениями kind/state/channel/outcome; ID, URL и поисковый текст не используются. Показатели обращений к провайдеру отражают число попыток, а не стоимость или расход токенов: универсальный контракт этих данных не возвращает. Пороги готовых правил оповещения настраиваются под реальную нагрузку.

При ошибке проверьте готовность PostgreSQL, настройки внешнего провайдера,
безопасный код ошибки и очередь по kind/state. Не сбрасывайте попытки массовым
UPDATE: это обходит бюджет повторов. Журналы не должны содержать токены и тела
писем; журналирование SQL отключено.

| Данные | Текущее поведение и политика |
| --- | --- |
| Токены OAuth и push-уведомлений | AES-GCM; локальные зашифрованные данные удаляются при отзыве доступа. Старые резервные копии базы могут их содержать, поэтому для копий нужен отдельный срок хранения. |
| OAuth state и PKCE verifier | Срок доступа 10 минут; использованные/истёкшие строки убираются порциями до 1000 при общем запуске планировщика и начале новых OAuth-подключений. Физическое удаление не мгновенно, особенно при остановленном обработчике. |
| Завершённые задания и журналы доставки | Автоматической очистки нет; срок хранения задаёт оператор. Нельзя удалить задание, на которое ссылается запись доставки. |

Файлы записи имеют отдельную политику хранения: 7 суток после `ended_at`
(для старых задач — `stopped_at`, затем `updated_at`/`created_at`), очистка API при
старте и раз в минуту. Он удаляет S3-файлы и строки таблиц файлов и сегментов, помечает запись
`deleted_at`, но не очищает локальные каталоги незавершённых записей.
