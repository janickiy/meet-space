# Уведомления календарь расшифровки и поиск

Актуализировано 2026-10-22: email-приглашения, напоминания и настройка SMTP.

Документ описывает фоновые интеграции, обработку готовой записи, live субтитры
и поиск MeetSpace. `product-worker` выполняет постоянные задания PostgreSQL;
`live-worker` отдельно обрабатывает живое аудио из SFU. По умолчанию STT, live STT,
ИИ, embeddings и аналитика выключены; внешние адаптеры работают в режиме `noop`.

## Архитектура обработки

Расписание и новые in-app уведомления создают задания в PostgreSQL в той же транзакции, что и исходное изменение. Переход conference recording в `ready` транзакционным SQL trigger ставит
`content.transcribe` в `background_jobs` независимо от feature flag. При выключенном
STT/noop обработчик отмечает `processing_disabled` и завершает job как skipped
без внешнего вызова. Поддерживаются `composite`, `screen_focus`, `audio_only`,
`individual_tracks`: источником служит подтверждённый основной MP4, в том числе
аудио MP4; архив исходных дорожек не отправляется провайдеру. Сохранение готовой расшифровки атомарно создаёт событие уведомления и, при
включённом ИИ, задание summary; сохранение итогов создаёт следующее событие. Все эти задания хранятся в `background_jobs`.

Работник опрашивает постоянную очередь фиксированными пулами. Задания уведомлений, календаря, распознавания и ИИ имеют независимые ограничения. RabbitMQ продолжает обслуживать команды записи; продуктовый конвейер не требует дополнительной публикации после commit и не имеет разрыва между сохранением данных и постановкой задания.

`FOR UPDATE SKIP LOCKED` выдаёт одно задание одному работнику. UUID аренды, срок аренды и поколение результата проверяются при сохранении. Истёкшая последняя попытка может быть захвачена для фиксации окончательной ошибки, но не для дополнительного платного вызова. Ошибки сети, 408, 429 и 5xx допускают конечные повторы с exponential backoff и jitter; остальные отказы провайдера и неверная схема постоянные. `Retry-After` ограничен часом. Максимум попыток определяется меньшим из бюджета строки и текущего операторского лимита.

Доставка во внешнюю систему имеет семантику at-least-once. Gateway обязан сохранять `Idempotency-Key`, иначе повтор после потерянного ответа может повторить письмо или платную операцию. Для календаря gateway также обязан отклонять более старый `sourceVersion`: локальная сериализация и проверка версии защищают базу, но не могут отменить уже принятый внешней системой запрос.

## Настройка и безопасные значения по умолчанию

Мастер установки предлагает настроить SMTP и проверить защищённое подключение.
Приглашённому по email отправляется отдельное письмо со ссылкой на встречу,
включая получателей без аккаунта. Для запланированной встречи второе письмо
ставится в очередь за 3 часа до начала (`REMINDER_OFFSETS=3h`). Если приглашение
отправлено позже этого момента, остаётся только первое письмо. Перенос встречи
отменяет доставку по старому времени; отмена или начало встречи также прекращают
ожидающее напоминание. Для зарегистрированных участников учитываются выключенные
напоминания, отключённые уведомления встречи и выход/исключение из неё.
Обычное уведомление в приложении сохраняется, но второе email-напоминание через
общий канал не дублирует отдельное письмо приглашённому.

Существующие установки сохраняют явно заданный `REMINDER_OFFSETS`. Чтобы получать
одно напоминание за 3 часа, замените старое значение `24h,15m` на `3h` в закрытой
конфигурации API и `product-worker` и примените её при обновлении. Пароли SMTP
не должны попадать в репозиторий. Настройка SPF/DKIM и разрешённого отправителя
выполняется у почтового провайдера; успешный приём SMTP не гарантирует папку «Входящие».

API и `product-worker` должны получать одинаковые настройки. Примеры находятся в `.env.example` и `.env.production.example`. Для каждого из `EMAIL`, `PUSH`, `CALENDAR`, `STT`, `AI` доступны `*_PROVIDER_MODE=noop|mock|http`, `*_PROVIDER_ENDPOINT`, `*_PROVIDER_TOKEN`.

Для email также доступен `EMAIL_PROVIDER_MODE=smtp`: он отправляет письма напрямую через SMTP и не требует HTTP gateway. Пример настройки Timeweb:

```dotenv
EMAIL_PROVIDER_MODE=smtp
PUBLIC_FRONTEND_URL=https://meet.example.com
SMTP_HOST=smtp.timeweb.ru
SMTP_PORT=465
SMTP_TLS_MODE=tls
SMTP_USERNAME=sender@example.com
SMTP_PASSWORD=<пароль почтового ящика, только в закрытом env-файле>
SMTP_FROM=MeetSpace <sender@example.com>
SMTP_TIMEOUT=15s
```

Вместо 465 можно выбрать `SMTP_PORT=587` и `SMTP_TLS_MODE=starttls`. [Официальная инструкция Timeweb](https://timeweb.com/ru/docs/virtualnyj-hosting/cms/otpravka-pochty-s-sajta-cherez-smtp/) указывает оба варианта и авторизацию PLAIN. Логин — полный адрес ящика, отправитель должен быть разрешён этим ящиком. Значение `tls` включает TLS сразу после подключения; `starttls` требует расширение STARTTLS до авторизации. В обоих режимах проверяются сертификат и имя сервера, минимальная версия TLS — 1.2. Незащищённая отправка и отключение проверки сертификата не предусмотрены.

`SMTP_TIMEOUT` ограничивает всю отправку, включая подключение, TLS, авторизацию и приём письма; допустимы значения от 1 секунды до 1 минуты. API и `product-worker` получают эти переменные через существующий `env_file` Compose. Для production секреты задаются в закрытом env-файле вне Git. Проверяйте доступность исходящих портов SMTP с рабочего хоста: наличие корректной конфигурации не устраняет блокировку исходящего трафика.

Письма содержат обычный текст и HTML в UTF-8, а `Message-ID` остаётся одинаковым при повторе одного задания. SMTP не гарантирует дедупликацию на стороне почтового сервера: потерянный ответ после приёма письма может вызвать повторную доставку. Положительный ответ на DATA считается успехом даже при последующей ошибке QUIT. Временные ответы 4xx и сетевые ошибки допускают повтор; постоянные отказы 5xx, неверный сертификат и отсутствие STARTTLS прекращают доставку с безопасным техническим кодом. Ответы SMTP, пароли и содержимое писем не попадают в ошибки или журналы.

`mock` разрешён только локально и в тестах. Он не отправляет реальные письма, не создаёт события в настоящем календаре и возвращает явно обозначенные демонстрационные расшифровки и итоги. `http` использует описанный ниже generic gateway, а не API произвольного производителя. Для рабочего сервиса нужен совместимый gateway или другой адаптер интерфейса. Vendor SDK в domain/usecase не импортируются.

Перед внешними интеграциями задайте `PUBLIC_FRONTEND_URL` и секрет каждого
HTTP-адаптера. Push/calendar дополнительно требуют независимый
`PROVIDER_TOKEN_ENCRYPTION_KEY` — base64 от случайных 32 байт. SMTP сам по себе
этот ключ не требует: пароль SMTP передаётся через закрытый env. В production адреса должны быть HTTPS; redirects отключены. Не храните секреты в Git. Потеря ключа шифрования делает ранее сохранённые push/OAuth токены нечитаемыми; ротация с повторным подключением или отдельной процедурой перешифрования должна быть запланирована оператором.

Основные стандартные бюджеты:

| Настройка | Значение |
| --- | --- |
| `TRANSCRIPTION_ENABLED` и `AI_SUMMARY_ENABLED` | `false`, включаются независимо |
| `REMINDER_OFFSETS` | `3h` по умолчанию, от 1 до 8 разных интервалов |
| `TRANSCRIPTION_MAX_DURATION_SEC` | 7200 секунд |
| `TRANSCRIPTION_MAX_VIDEO_BYTES` | 1 GiB |
| `TRANSCRIPTION_MAX_AUDIO_BYTES` | 256 MiB |
| `TRANSCRIPTION_MAX_TEXT_BYTES` | 8 MiB |
| `TRANSCRIPTION_MAX_SEGMENTS` | 10000 |
| `TRANSCRIPTION_CONCURRENCY` и `AI_JOB_CONCURRENCY` | по 1 заданию на процесс |
| `TRANSCRIPTION_TIMEOUT` и `AI_SUMMARY_TIMEOUT` | 10 минут и 2 минуты на задание |
| `AI_CHUNK_RUNES`, `AI_MAX_CHUNKS`, `AI_CHUNK_CONCURRENCY` | 12000, 256, 2 |
| `PRODUCT_MAX_ATTEMPTS`, `PRODUCT_MAX_REPROCESS` | 5 попыток и 3 ручных повторных поколения |
| `PRODUCT_REPROCESS_COOLDOWN` | 5 минут |

Лимиты конкуренции действуют на процесс, а не на весь кластер. Добавление реплик умножает максимальное число внешних вызовов. Размер tmpfs и память должны покрывать одновременно загруженные MP4 и извлечённые WAV. Production Compose рассчитан на стандартный один STT job; повышение числа работников или byte limits требует пересчёта ресурсов.

## Live субтитры, аудио и аналитика

`cmd/live-worker` / [`internal/app/live.go`](../internal/app/live.go) используют
PostgreSQL leases и Redis media ownership. Worker открывает отдельный
`POST /internal/media/egress` с `purpose=captions`, `MEDIA_INTERNAL_SECRET` и
актуальной route; принимает NDJSON с base64 RTP. Это отдельный от recorder output.
Берутся только микрофонные аудиодорожки; Opus декодируется FFmpeg в mono 16 kHz
PCM16LE. При `LIVE_STT_ENABLED=true` и включённой сессии звук передаётся настроенному
`LIVE_STT_PROVIDER_MODE=websocket` endpoint (`wss` в production).

Промежуточные реплики доставляются через Redis/conference WS; финальные сохраняются
в PostgreSQL и доступны повторным чтением. Дорожка привязана к participant ID,
но это не биометрическая идентификация говорящего. Публикации screen audio
не распознаются этим микрофонным tap. Сбой/overflow live очереди даёт `degraded`
и ограниченные повторы, не должен блокировать media forwarding участников.

При `MEETING_ANALYTICS_ENABLED=true` live-worker также собирает наблюдения речи;
`product-worker` агрегирует аналитику. Если субтитры выключены, обработка для
аналитики может продолжаться без отправки аудио внешнему STT. `kind=direct_call`
исключён из автоматического захвата, записи и фоновой аналитики.

| Настройка | По умолчанию | Область |
| --- | --- | --- |
| `LIVE_MAX_CONFERENCES` | 2 | Параллельные комнаты на процесс |
| `LIVE_MAX_SESSIONS` | 10 | Параллельные микрофонные дорожки на процесс, суммарно по комнатам |
| `LIVE_AUDIO_QUEUE` | 100 | Очередь пакетов на дорожку |
| `LIVE_MAX_ATTEMPTS` | 3 | Бюджет захвата сессии |
| `LIVE_MAX_DURATION` | 2 h | Максимальное время обработки |
| `LIVE_PROVIDER_TIMEOUT` | 5 s | Тайм-аут провайдера |
| `LIVE_MAX_CAPTION_RUNES` / `LIVE_MAX_FINAL_CAPTIONS` | 2000 / 10000 | Размер реплики / число сохранённых финалов |
| `EMBEDDING_CONCURRENCY` / `EMBEDDING_BATCH_SIZE` | 1 / 16 | Задания на product-worker / batch текстов |
| `EMBEDDING_DIMENSIONS` / `EMBEDDING_CHUNK_RUNES` | 64 / 1200 | Размерность / размер текстового фрагмента |

Секреты `LIVE_STT_PROVIDER_TOKEN` и `EMBEDDING_PROVIDER_TOKEN` остаются на сервере;
операторские endpoints не принимаются из пользовательского запроса.
Настройки: [`meeting_intelligence.go`](../internal/config/meeting_intelligence.go).

## Уведомления и напоминания

### Явные приглашения участников

Организатор может пригласить до 20 адресатов через форму после создания встречи или на её странице. Допускаются email и выбранные пользователи системы; поиск по имени/email доступен при вводе от двух символов и возвращает до 20 постоянных аккаунтов. Активный соорганизатор также может приглашать. Обычный участник и гость могут поделиться публичной ссылкой.

API: `GET /api/v1/conferences/:id/invitation-users?query=...`, `POST /api/v1/conferences/:id/invitations` с `{emails?: string[], userIds?: string[]}`. Ответ POST — HTTP 202, элементы со статусом `queued` или `already_invited`. Поля пользователя не включают чужие настройки или токены. На поиск действует лимит 60 запросов в минуту, на отправку — 10 запросов в минуту на аккаунт.

Транзакция сохраняет `conference_invitations`, задание `integrations.invitation` и личное уведомление зарегистрированного адресата. Встреча появляется в его кабинете без фактического подключения: членство создаётся со статусом `left`, допуском `admitted` и пустым `joined_at`. Уже имеющееся членство сохраняется; исключённого или отклонённого участника повторное приглашение не восстанавливает. Повтор email в одной встрече не создаёт второе письмо или уведомление. После окончательной ошибки отправки повтор запроса возвращает существующее задание в очередь.

Письмо содержит название, организатора, время с явным UTC и публичную ссылку `/i/:code`; регистрация для перехода не требуется. Явное приглашение отправляется независимо от выключенного общего email preference, поскольку его адресат выбран организатором. Обычные уведомления по-прежнему следуют настройкам пользователя. Перед отправкой работник повторно проверяет состояние встречи и допуск адресата; отменённая/завершённая встреча и исключённый участник не получают отложенное письмо. Форма подтверждает постановку в очередь, а не доставку письма.

Категории приглашений, напоминаний, записей и итогов включены для in-app по умолчанию; email и push выключены. Изменение preferences влияет на новые события и проверяется повторно перед внешней доставкой. Письмо содержит HTML и plain text, пользовательское название экранируется, полный transcript не отправляется.

Планировщик работает с UTC и одной общей периодической проверкой, а не таймером на встречу. Задания будущих напоминаний имеют `available_at`; ключ включает конференцию, версию расписания и интервал. Перенос или отмена делает старые задания неактуальными. Уже прошедшие интервалы не отправляются пачкой сразу после создания поздней встречи: для этого остаётся приглашение.

Fanout идёт страницами по 100 адресатов с постоянными заданиями продолжения. Повторная проверка допуска при вставке и доставке защищает исключённых участников. Ошибки STT/ИИ направляются владельцу, а не всем участникам. Push-токены хранятся с AES-GCM и привязкой к пользователю и устройству; API никогда их не возвращает. Регистрация устройства имеется, но получение токена реальным web/mobile SDK не поставляется текущим frontend.

## Календарь и OAuth

Синхронизируются create, update и cancel расписания владельца. Mapping сохраняет conference, connection, provider, внешний календарь и event ID, версию, статус и время последней синхронизации. Перенос обновляет тот же event ID. Повтор create использует стабильный ключ; если внешний ответ относится к прежней версии расписания, выполняется update того же события.

Ссылка приглашения соответствует frontend `/i/:inviteCode`. Email других участников не передаются в календарь автоматически: отдельной модели их согласия на раскрытие адреса внешнему календарю пока нет. Обратные изменения из внешнего календаря и webhooks отсутствуют.

OAuth использует `provider=generic`, authorization code, S256 PKCE и одноразовый state, привязанный к пользователю и провайдеру на 10 минут. В базе лежат хеш state и зашифрованный verifier. Frontend callback удаляет code/state из адреса и передаёт их через авторизованный POST; access/refresh токены остаются на сервере. Задайте все `CALENDAR_OAUTH_*` адреса, client ID/secret, redirect URL и минимальные scopes, подходящие вашему gateway. Redirect должен вести на `/app/settings/calendar/generic/callback` публичного frontend. OAuth start ограничен 5 запросами в минуту, callback — 10 на пользователя; регистрация устройств и изменения подключений также ограничены Redis.

Refresh не может восстановить отозванное подключение: запись условна на активный статус и прежний grant. Disconnect сначала стирает локальные токены, затем пытается выполнить внешний revoke. Недоступность провайдера не восстанавливает доступ; внешний grant при неуспешном revoke следует отозвать вручную в аккаунте провайдера.

Access logs Nginx используют `$uri` без query. Для frontend callback отключены upstream error logs, способные раскрыть code/state при недоступности frontend; `Referrer-Policy: no-referrer` предотвращает передачу исходного адреса через Referer. Уже выполняющийся внешний запрос нельзя гарантированно отозвать одновременно с disconnect, но его поздний ответ не восстанавливает grant и не сохраняет активный mapping.

## Контракты HTTP провайдеров

Все запросы используют серверный `Authorization: Bearer` и стабильный `Idempotency-Key`; тела не журналируются. Ошибочный ответ не должен содержать секретов в своей классификации. Платные провайдеры не нужны для CI.

Email gateway принимает `POST <endpoint>/email/send` с `{idempotencyKey,to,subject,html,text}`. Push — `POST <endpoint>/push/send` с `{idempotencyKey,token,title,body,url}`. Успех — любой 2xx; JSON результата для этих операций не требуется.

Calendar gateway принимает POST на `calendar/create`, `calendar/update`, `calendar/cancel`, `calendar/get`. Тело содержит `{event,accessToken}`; event включает `idempotencyKey`, внешний `id`, `calendarId`, `title`, `joinUrl`, UTC `startsAt` и `endsAt`, `sourceVersion`, опциональный список `attendees`. Create/update/get должны вернуть объект event с непустым `id`. Cancel может вернуть пустой 2xx. Лимит ответа — 1 MiB. Требования к дедупликации и отклонению старой версии обязательны для gateway.

STT выполняет POST непосредственно на настроенный endpoint: streaming multipart с полем `language=auto` и файлом `audio` с именем `meeting.wav`. Передаётся приватно извлечённый mono 16 kHz PCM WAV, не огромный исходный MP4 и не подписанный URL. Content-Length известен, верхняя граница аудио — 2 GiB при явном увеличении конфигурации; ответ ограничен 10 MiB.

Ответ STT — `{language,segments:[{startMs,endMs,text,speakerLabel,speakerId,confidence}]}`. Сегменты проверяются по количеству, размеру, UTF-8, времени и confidence. Сервер назначает собственные IDs и очищает `speakerId`: label диаризации не доказывает личность участника.

ИИ получает POST JSON `{model,promptVersion,schemaVersion,instructions,input,merge,responseFormat,tools:[]}`. `input` содержит `segments` либо проверенные `partials`; instructions отделены от недоверенных данных. HTTP input ограничен 1 MiB, ответ — 256 KiB. Ответ должен быть ровно `{summary,keyPoints:[],actionItems:[],topics:[]}`. Каждый action содержит `{text,assignee:null|string,dueDate:null|YYYY-MM-DD,sourceSegmentIds:[]}`. Неизвестные поля, неверная схема и недопустимые ссылки на сегменты отклоняются.

## Обработка текста и безопасность ИИ

Prompt `meeting-summary-ru-en-v1` и schema `meeting-summary-v1` сохраняются вместе с результатом. Текст разбивается детерминированно по Unicode-символам с сохранением исходных IDs; частичные итоги объединяются ограниченным иерархическим reduce. Есть общий deadline и ограничение числа chunks. Если частичные ответы расширяются так, что не помещаются или не сокращаются, обработка завершается `ai_merge_limit`, а не бесконечными вызовами.

Transcript — недоверенные данные. Контракт не предоставляет инструментов, выполнения команд и сетевых действий; команды и URL внутри встречи не становятся инструкциями. Это уменьшает поверхность prompt injection, но не доказывает истинность любого текста, сгенерированного моделью. Итоги требуют человеческой проверки.

Для корректной пустой расшифровки сохраняется пустой итог локально, без платного вызова ИИ и выдуманных фактов; provider metadata обозначает отсутствие внешней обработки.

Исполнитель сохраняется только при буквальном маркере `ответственный:`, `исполнитель:` или `assignee:` с именем в цитируемом сегменте. Срок — при `срок:`, `deadline:`, `due:` или `до` с точной ISO-датой. Простое упоминание имени или даты встречи не считается доказательством; сомнительные поля становятся null. Это консервативное правило может пропустить естественно сформулированные поручения и не является полной NLP-проверкой связи действия и исполнителя.

## API и права доступа

Все адреса ниже относительны к `/api/v1`, требуют Bearer JWT; private text responses имеют `private, no-store`. Доступ к истории имеют допущенные участники со статусом `joined` или `left`; waiting, rejected, kicked и посторонние не получают текст. Ручные дорогие операции доступны owner/co_host и ограничены поколениями и cooldown. Проверки выполняются на сервере, а UI использует capability flags.

| Маршрут | Назначение |
| --- | --- |
| `GET/PUT /notifications/preferences` | Собственные категории и каналы |
| `GET/POST /notifications/devices` | Собственные push регистрации без токенов в ответе |
| `DELETE /notifications/devices/:deviceId` | Отзыв собственного устройства |
| `GET /integrations/capabilities` | Режимы адаптеров без secrets |
| `GET /integrations/calendars` | Собственные подключения |
| `POST /integrations/calendars/mock` | Только локальное/test подключение |
| `GET /integrations/calendars/generic/connect` | Начало OAuth |
| `POST /integrations/calendars/generic/callback` | Одноразовый code/state |
| `DELETE /integrations/calendars/:connectionId` | Отзыв подключения |
| `GET /conferences/:id/calendar` | Mapping для допущенного owner/co_host |
| `GET /conferences/:id/recordings/:recordingId/transcript` | Nullable status и canRetry |
| `GET .../transcript/segments?limit=100&offset=0` | Сегменты, максимум 200 на страницу |
| `POST .../transcript/retry` | Пустой `{}`, новое ограниченное поколение |
| `GET .../summary` | Nullable current-generation итог и canRegenerate |
| `POST .../summary/regenerate` | Пустой `{}`, асинхронное новое поколение |
| `GET /search?q=...` | Поиск `mode=keyword\|semantic\|hybrid` с проверкой доступа |
| `GET/PUT /conferences/:id/captions` | Чтение/управление live сессией; управляет допущенный joined owner/co_host |
| `GET /conferences/:id/captions/segments` | Сохранённые финальные реплики |
| `GET /conferences/:id/analytics` | Разрешённая аналитика встречи |
| `POST .../recordings/:recordingId/search/reindex` | Ограниченная повторная индексация |

Расшифровка и итог имеют `queued`, `processing`, `ready`, `failed`. Ошибка STT не меняет запись; ошибка ИИ не меняет расшифровку. Повторное поколение заменяет текущий результат: это не архив всех редакций.

## Поиск и интерфейс

PostgreSQL `tsvector` с конфигурацией `simple` и GIN индексирует название, сегменты и итоговые summary/key points/actions/topics. Он поддерживает RU/EN токены без языкового stemming: разные словоформы не обещаются как один результат. Вектор обновляется в той же транзакции с текстом, дополнительной асинхронной переиндексации нет. Проверка допуска входит в SQL до count, rank и страницы.

Дополнительно реализованы `semantic`/`hybrid` через `internal/usecase/search`,
`content.embed` в `background_jobs`, настроенный embedding gateway и pgvector.
`EMBEDDINGS_ENABLED=false` по умолчанию; это не внешняя отправка текста без настройки.
Embedding контракт требует фиксированную размерность, модель и версию. Смена
модели/размерности требует согласованной переиндексации, а не смешивания векторов.
При выключенных embeddings, недоступном pgvector/провайдере или занятом query slot
поиск возвращается к keyword, указывая `effectiveMode` и `fallbackReason`. Для
`semantic` с `source=conference|summary` тоже используется keyword: семантический
индекс строится по фрагментам расшифровки.

Фильтры: `source=all|conference|transcript|summary`, `membership=all|owned|participating`,
`participantId`, `conferenceId`, `from`, `to` в RFC3339, `limit` до 100, `offset` до 10000. Дата относится к finished/scheduled/created времени встречи, не к времени генерации текста. Поисковая строка ограничена 500 Unicode-символами и 2000 байтами. Snippet — plain text с квадратными скобками, а не HTML. Результат сегмента содержит recording/transcript/segment UUID и `startMs`.

В UI доступны настройки каналов и календаря, поиск с фильтрами, приватный видеоплеер, вкладки расшифровки и итогов, processing/error/retry состояния. Переход по времени ищет соответствующий момент записи. Подписанный URL не меняется при каждом status poll; после истечения его можно обновить явно. Подписанная ссылка остаётся краткоживущим bearer доступом до истечения, даже после смены членства.

## Эксплуатация и сроки хранения

Обычный и production Compose запускают `product-worker`; `live-worker` вынесен
в необязательный профиль `live` и по умолчанию не запускается. Без product-worker
новые задания остаются в PostgreSQL; без live-worker живые
субтитры/наблюдения не обрабатываются. Порты health — 8092/8093, `/metrics` и
`/operations/drain` защищены `METRICS_SECRET`. FFmpeg нужен обоим worker,
а SFU не декодирует медиа.

Мастер установки и release-helper включают live-worker только при буквальном
`true` в `LIVE_STT_ENABLED` или `MEETING_ANALYTICS_ENABLED` в сохранённом env-файле.
Иначе его запуск, ожидание готовности и проверка метрик пропускаются. Отсутствие
live-worker не отключает чаты, видеозвонки, запись, email и обработку уже записанных
файлов. Полный установочный пакет сохраняет образ live-worker и его SBOM/проверки.

В установке новым мастером после настройки нужной функции используйте
`sudo /opt/meetspace/manage.sh start-live-worker`. Для выключения задайте оба флага
`false` и выполните `sudo /opt/meetspace/manage.sh stop-live-worker`: активная
обработка должна завершиться через drain, затем обновляется конфигурация метрик.
Команды не пересоздают API: изменение его флагов применяется отдельно в согласованное
окно обновления. Для ручного Compose нужен `--profile live`; при ручном production
запуске также укажите `LIVE_METRICS_TARGETS_FILE` на абсолютный путь к
`dockers/observability/live-targets.enabled.json`. По умолчанию используется пустой
`live-targets.disabled.json`, поэтому отключённый сервис не создаёт down-тревог.

Новый мастер работает и со старыми проверенными Docker-пакетами: он создаёт
отдельный Compose overlay и конфигурацию Prometheus, не изменяя исходные файлы,
контрольные суммы или образы пакета. Текущая версия мастера сохраняется в закрытом
`config/installer.py`, чтобы управление и продолжение установки не возвращались
к устаревшему мастеру внутри старого пакета.

Метрики: `recorder_product_jobs_total`, `recorder_product_job_duration_seconds`, `recorder_product_queue`, `recorder_product_provider_calls_total`, `recorder_product_provider_duration_seconds`, `recorder_search_requests_total`, `recorder_search_duration_seconds`. Labels — фиксированные kind/state/channel/outcome, без ID, URL и поискового текста. Provider usage показывает число попыток, не счёт или token usage: generic контракт не возвращает стоимость. Пороги предоставленных alert rules настраиваются под реальную нагрузку.

При ошибке сначала проверьте readiness PostgreSQL/S3, безопасный error code сущности и очередь по kind/state. Не сбрасывайте попытки массовым UPDATE: это обходит ограничения расходов. Повтор через API требует актуальных прав. Логи job содержат IDs для связи recording → transcript → summary, но не полные тексты, токены или payload. SQL logger выключен.

| Данные | Текущее поведение и политика |
| --- | --- |
| Расшифровки, сегменты, итоги | Автоматического TTL нет. Soft deletion записи скрывает их в API/поиске; предикат времени retention recording API здесь отдельно не повторяется, поэтому до `deleted_at` текст может оставаться доступным. Физически текст остаётся до согласованной процедуры удаления. FK RESTRICT не допускают случайный каскад. |
| Временные MP4/WAV | Удаляются на успехе и ошибке; private случайный каталог. SIGKILL может оставить orphan. Production tmpfs очищается при пересоздании контейнера. Оператор чистит только подтверждённые неактивные каталоги `go-recorder-stt-*`, не весь temp root. |
| OAuth tokens и push tokens | AES-GCM, локальные ciphertext стираются при revoke. Старые DB backups могут содержать ciphertext и требуют отдельного срока хранения. |
| OAuth state и PKCE verifier | Срок доступа 10 минут; использованные/истёкшие строки убираются порциями до 1000 при общем scheduler tick и новых OAuth starts. Физическое удаление не мгновенно, особенно при остановленном работнике. |
| Завершённые jobs и delivery logs | Автоматического purge нет; срок хранения задаёт оператор. Нельзя удалить job, на который ссылается delivery row. |

Файлы записи имеют отдельный реализованный retention: 7 суток после `ended_at`
(для старых задач — `stopped_at`, затем `updated_at`/`created_at`), очистка API при
старте и раз в минуту. Он удаляет S3-файлы и file/segment rows, помечает запись
`deleted_at`, но не выполняет физическое удаление текста и failed recorder spool.
S3 service `minio` может быть MinIO или SeaweedFS в hardened-комплекте.

Для физического удаления записи и её текстовых производных нужна явная процедура: закрыть доступ, остановить относящиеся поколения, удалить согласованные summaries/segments/transcript, затем связанные storage/record данные и audit references в разрешённом порядке. Не применяйте каскадную миграцию как замену согласованию retention. Политика хранения и внешних передач описана в [DATA_FLOWS.md](DATA_FLOWS.md).
