# Установка MeetSpace

`install.sh` — интерактивный мастер для нового Linux-сервера. Он получает
готовые Docker-образы, собранные из [janickiy/meet-space](https://github.com/janickiy/meet-space)
в GitHub Actions для Linux x64 и ARM64. По умолчанию сервер **не компилирует**
приложение: мастер скачивает пакет выбранной архитектуры, проверяет SHA-256,
происхождение и отчёты безопасности, загружает образы в Docker, создаёт конфигурацию,
применяет миграции и запускает приложение. Все вопросы задаются в командной
строке; браузерный мастер не нужен. Go, Node, npm и Trivy на целевом сервере не нужны.

Публичный установщик закреплён за проверенным коммитом инструментов, но не
за версией приложения: `--release latest` используется по умолчанию. При каждом
запуске он выбирает последний по времени публикации совместимый релиз с
`prebuilt.json` и готовым пакетом для архитектуры сервера. Предварительные релизы
с готовыми образами тоже учитываются; черновики и релизы только с исходниками
пропускаются. Выбранные версия и коммит фиксируются на время этой установки.
Пакеты с образами опубликованы в GitHub Releases; исходники включены в пакет.
Архив исходников в разделе downloads остаётся дополнительной копией кода.
При недоступности готового пакета мастер выдаёт ошибку и не начинает долгую
сборку автоматически. Режим `--mode source` явно включает сборку на сервере.

## 1. Подготовьте сервер

Поддерживается Linux `amd64` или `arm64`. Автоматическая установка зависимостей
и Docker рассчитана на Ubuntu/Debian с `apt` и `systemd`; на других системах
зависимости необходимо установить самостоятельно. Нужны права `root` через
`sudo` и интерактивный SSH-терминал.

Для работы и записи рекомендуются **4 CPU, 8 ГиБ RAM и диск от 60 ГиБ**.
Установка готовых образов не требует ресурсов для компиляции. Для режима сборки рекомендуется
не менее **35 ГиБ свободного места** в `/var/tmp` и хранилище Docker; для установки
готового пакета — место под его копию и ещё **15 ГиБ** для Docker и данных.
Недостаток свободного места вызывает только предупреждение и не блокирует
продолжение. Если диск заполнится, сборка или установка может завершиться
ошибкой; это также может повлиять на другие службы на том же диске. Для записей,
вложений и резервных копий потребуется дополнительное место. Сборка может быть
длительной: её скорость зависит от CPU, диска и соединения с реестрами.

### Экономный режим сборки

При нехватке CPU/RAM мастер предлагает экономный режим по умолчанию. Его можно
выбрать явно: `sudo bash install.sh --mode source --build-mode low-memory`. Режим `auto`
показывает выбор в терминале, `standard` сохраняет обычную сборку без отдельного
ограничения памяти. Экономный режим работает медленнее и не гарантирует успешную
сборку на любом сервере.

Сборка выполняется в отдельном BuildKit-контейнере: один CPU, один этап за раз,
не более 2 ГиБ RAM. При меньшем объёме доступной памяти лимит снижается, чтобы
оставить запас системе. Go компилирует пакеты последовательно с `GOGC=20` и
мягкой целью `GOMEMLIMIT=768MiB`; Node получает heap до 768 МиБ. Именно лимит
контейнера ограничивает суммарную память: настройки Go сами по себе не являются
жёстким ограничением. Проверка безопасности также последовательная, в отдельном
контейнере с лимитом 1 ГиБ. Проверки HIGH/CRITICAL остаются обязательными.

Мастер проверяет поддержку и применение ограничений Docker; если они не
поддерживаются, экономная сборка не запускается без ограничений. Swap, службы
хоста и выбранный по умолчанию Docker-сборщик не меняются. Сборщик останавливается
после работы или ошибки; его отдельный кеш сохраняется для `--resume`. Кеш
прежнего стандартного сборщика автоматически в него не переносится, поэтому
первый запуск экономного режима может повторно скачать зависимости и потребовать
дополнительное место. Параллельная нагрузка других служб всё ещё может исчерпать
ресурсы хоста.

### Кеш и продолжение сборки

Пять Go-сервисов используют общий кеш модулей и скомпилированных пакетов внутри
выбранного Docker-сборщика. Кеш разделён по версии Go и архитектуре. Изменения
документации и frontend не инвалидируют слой исходников Go. Prometheus также
сохраняет кеш компиляции для повторной попытки. Первая сборка больших сторонних
проектов всё ещё требует времени; кеш ускоряет следующие сервисы и попытки.

После каждого готового образа мастер атомарно сохраняет `build-progress.json`
в каталоге сборки. Напечатанная команда `--resume` сохраняет прежнюю версию,
проверяет исходники, платформу, параметры, метки и неизменяемые ID готовых
образов, затем собирает оставшиеся. При несовпадении продолжение останавливается.
Если образ появился перед аварийным завершением, но ещё не попал в контрольную
точку, его тег не перезаписывается автоматически; потребуется отдельная проверка
или новая сборка. Каждый образ сопровождается временем выполнения, без
условного процента готовности всей установки.

Не удаляйте каталог сборки и кеш сборщика перед `--resume`. Новый запуск
`install.sh` создаёт отдельную сборку. Очистка кеша Docker может потребовать
повторной компиляции; установщик не выполняет такую очистку автоматически.
После сборки все 13 компонентов по-прежнему проходят проверку безопасности.
Подробности и ограничения замеров: [аудит](installer/DOCKER_INSTALL_AUDIT.md),
[результаты до и после](installer/DOCKER_INSTALL_BEFORE_AFTER.md).

Если сама сборка достигнет лимита, исправьте причину и используйте напечатанную
команду продолжения. Старые сохранённые каталоги запускают старую версию
установщика: чтобы получить исправление, скачайте новый `install.sh` и начните
новую сборку. Установщик не удаляет старые каталоги и кеш автоматически.
При создании конфигурации CPU-квоты приложения ограничиваются количеством CPU
сервера; меньшие квоты и лимиты памяти сохраняются.

Настройки опираются на [ограничения Docker-сборщика](https://docs.docker.com/build/builders/drivers/docker-container/)
и [параметры сборщика мусора Go](https://go.dev/doc/gc-guide/).

Нужен исходящий HTTPS-доступ к GitHub Releases и репозиториям системных пакетов.
Режиму `source` дополнительно нужны Docker Registry, Linux/Alpine, Go/npm и
база уязвимостей Trivy. Мастер предлагает установить
Python 3, Git, Bash, curl, jq, OpenSSL, tar, gzip, ripgrep, iproute2 и Docker.
Docker должен быть локальным, rootful, с Compose **2.24.4 или новее**.
Buildx нужен только для режима `source`.
Удалённый Docker context и rootless Docker не поддерживаются. Для OCI-экспорта
используется containerd image store; мастер не переключает хранилище уже
существующего Docker автоматически.

Подготовьте домен, например `meet.company.ru`, с единственной A-записью на
публичный IPv4 сервера. Этот IPv4 должен быть назначен непосредственно интерфейсу
Linux. Вводить IP вручную не нужно: мастер сопоставляет A-запись указанного домена
с публичными IPv4 сетевых интерфейсов сервера и показывает найденный адрес.
При нескольких адресах выбирается тот, на который указывает домен. NAT,
CDN-прокси, балансировщик и IPv6 требуют отдельной настройки: мастер
останавливается при несовпадении адресов, нескольких A-записях или наличии AAAA-записи.

Следующие порты должны быть свободны и разрешены во внешнем firewall:

| Порт | Назначение |
| --- | --- |
| `443/tcp` | Сайт, API, WebSocket, материалы через HTTPS |
| `80/tcp` | Выпуск и продление сертификата Let’s Encrypt |
| `3478/tcp`, `3478/udp` | TURN |
| `5349/tcp` | TURN через TLS |
| `50010/tcp`, `50010/udp` | Медиа SFU |
| `49160–49259/udp` | Ретрансляция TURN |

Мастер **не меняет firewall** и не открывает наружу PostgreSQL, Redis, RabbitMQ
или S3-хранилище. Сайт работает на HTTPS; постоянный HTTP-редирект с порта 80
не создаётся. Порт 80 нужен для режима Let’s Encrypt.

Это первая установка, а не обновление: существующие каталоги, Compose-проекты
и данные не перезаписываются. `--resume` продолжает незавершённую установку.
Повторный запуск сначала проверяет стандартный каталог `/opt/meetspace`.
Если в нём найдена проверенная незавершённая установка, мастер показывает её
домен и сохранённую версию и предлагает продолжение без новой сборки.
Продолжение использует прежний пакет, настройки, сертификат и данные, а не
заменяет приложение новым выпуском. Посторонние ресурсы не присваиваются.
Для работающей системы сначала определите её Compose-топологию по
[DEPLOYMENT.md](DEPLOYMENT.md#выбор-процедуры-по-типу-установки): общие
`release.sh` и `backup.sh` не подхватывают конфигурацию мастера автоматически.

## 2. Скачайте и запустите установщик

На новом сервере выполните HTTPS GET-запросы и проверьте контрольную сумму:

```bash
mkdir -p meetspace-setup && cd meetspace-setup
curl -fSL --proto '=https' --proto-redir '=https' \
  https://meeting.janickiy.com/downloads/install.sh -o install.sh
curl -fSL --proto '=https' --proto-redir '=https' \
  https://meeting.janickiy.com/downloads/install.sh.sha256 -o install.sh.sha256
sha256sum --check install.sh.sha256 && sudo bash install.sh
```

Запускайте скрипт только после результата `install.sh: OK`. Контрольная сумма
подтверждает целостность байтов; доверие к издателю также зависит от HTTPS и
адреса распространения. Недостающий `curl` установите вместе с
`ca-certificates` через пакетный менеджер.

Для явной сборки из GitHub на самом сервере:

```bash
sudo bash install.sh --mode source --ref main
```

Для конкретной опубликованной версии готовых образов: `sudo bash install.sh --release VERSION`.
Вернуться к автоматическому выбору: `sudo bash install.sh --release latest`.
Режим `--mode source --ref main` берёт текущий коммит `main`, а не последний
готовый релиз; компиляция и проверки выполняются на сервере и могут занять много времени.
Старые команды с `--ref` или `--build-mode` без `--mode` сохраняют режим сборки
для обратной совместимости. Указанная версия исходников должна содержать
`scripts/install/from-source.py`. Мастер
показывает фактически полученный коммит и сохраняет его вместе с установкой.
GitHub-токен и SSH-ключ для публичного репозитория не нужны. Режимы `--channel`
и `--bundle` не поддерживаются.

## 3. Пройдите интерактивные шаги

1. Подтвердите установку недостающих зависимостей и загрузку инструментов
   из GitHub. При отсутствии Docker мастер отдельно предложит официальный
   репозиторий Docker; конфликтующие пакеты автоматически не удаляются.
2. По умолчанию загружается готовый пакет образов для архитектуры сервера.
   Сборка и Trivy/SBOM выполняются заранее в GitHub Actions из чистого checkout;
   HIGH/CRITICAL блокируют публикацию. На сервере проверяются SHA-256,
   архитектура, происхождение и сохранённые отчёты. В режиме `source` сборка и
   сканирование выполняются на самом сервере. Проверки пропустить нельзя.
3. Укажите домен; публичный IPv4 определяется автоматически по DNS и интерфейсам
   сервера. Каталог `/opt/meetspace`, имя Compose-проекта `meetspace` и частная
   подсеть `172.30.240.0/24` подставляются автоматически. На вопрос
   «Изменить каталог, имя проекта или подсеть?» достаточно нажать Enter (`нет`).
   Ответ `да` открывает эти три настройки; в каждой Enter принимает указанное
   значение по умолчанию. Занятые проекты и пересечения подсетей проверяются
   и при стандартных параметрах. Для отдельной новой установки каталог
   должен быть новым, внутри `/opt` или `/srv`. Для проверенной незавершённой
   установки в выбранном каталоге предлагается продолжение с сохранёнными
   параметрами; повторно вводить имя проекта не нужно.
4. Выберите HTTPS: Let’s Encrypt либо каталог с готовыми `fullchain.pem` и
   `privkey.pem`. Для Let’s Encrypt нужны email и согласие с условиями центра
   сертификации. В вопросе о получении и автоматическом продлении сертификата
   по умолчанию выбрано «да»: Enter подтверждает согласие, «нет» отменяет установку.
   Готовый сертификат должен соответствовать домену и ключу,
   иметь доверенную цепочку и оставаться действительным; ключ — без пароля.
5. При необходимости настройте email-уведомления через SMTP. По умолчанию выбран
   ответ `нет`: Enter продолжает установку без почты. Для настройки нужны адрес
   сервера (например `smtp.example.com`, **не номер порта**), шифрование `tls`
   (обычно порт `465`) или обязательный `starttls` (обычно `587`), логин,
   пароль приложения и email отправителя, разрешённый вашим почтовым провайдером.
   Пароль вводится скрыто. Мастер проверит сертификат, защищённое соединение
   и вход; при желании отправит одно тестовое письмо на указанный вами адрес.
   При ошибке можно исправить параметры либо явно продолжить с непроверенными
   настройками. Отказ от обоих вариантов продолжает установку без почты.
   Если настройку SMTP пропустить, отправка писем будет отключена.
   Приглашённому пользователю письмо отправляется после приглашения и повторно
   за 3 часа до начала запланированной встречи (`REMINDER_OFFSETS=3h`).
   При приглашении позднее этого срока приходит только первое письмо.
   Напоминание не отправляется после отмены или начала встречи, исключения
   участника или его выхода; для зарегистрированного пользователя учитывается
   настройка напоминаний о встречах.
6. Проверьте параметры и нажмите Enter, чтобы начать установку, или Ctrl+C для отмены.
   Вводить слово подтверждения не нужно. Мастер создаст независимые пароли
   и ключи, сохранит конфигурацию, проверенные образы и исходники.
7. Дождитесь запуска зависимостей, применения миграций и запуска MeetSpace.
   Миграции выполняются отдельным шагом, не при обычном запуске приложения
   (`AUTO_MIGRATE=false`). Текущий набор содержит 35 `.up.sql`; применяется ledger
   `release_schema_migrations` с checksum файлов. Условная миграция pgvector
   не включает semantic search без отдельно установленного расширения.
8. После проверки HTTPS, `/version` и `/version.json` можно создать первый
   пользовательский аккаунт в терминале: email, имя и пароль со скрытым вводом.
   Это обычный аккаунт без дополнительных административных прав.

SMTP настраивается в мастере. Учётные данные сохраняются только в
`config/smtp.env` с правами `0600` и передаются службам `api` и `product-worker`.
Пароль не записывается в `installation.json`, не включается в исходники и не
выводится в журнал. Возобновление установки использует сохранённую конфигурацию
и не требует повторного ввода SMTP-пароля. Поддерживаются SMTP AUTH PLAIN поверх
TLS 1.2+ и доверенные сертификаты; незашифрованная доставка не поддерживается.
Принимающий SMTP-сервер ещё не гарантирует появление письма во входящих:
проверьте тестовое письмо, настройки SPF/DKIM/DMARC домена и папку «Спам».
Внешние push/calendar-провайдеры, распознавание речи и ИИ настраиваются отдельно.

### Включение email после установки

SMTP необязателен: на вопрос мастера можно нажать Enter (`нет`) и завершить установку
без почты. В этом случае письма с приглашениями и напоминаниями не отправляются;
уведомления внутри приложения работают независимо. Настроить почту позже можно
через файлы конфигурации, без повторной установки или пересборки образов.
Выполняйте следующие действия только после **успешного завершения** установки;
не редактируйте состояние незавершённого мастера.

1. Сохраните закрытую резервную копию `config/compose.json` и, если он уже есть,
   `config/smtp.env`. В root-редакторе создайте или измените
   `/opt/meetspace/config/smtp.env`; владелец — `root`, права — `0600`.
   Не вводите настоящий пароль в командную строку или журнал. Содержимое файла:

   ```dotenv
   SMTP_HOST="smtp.example.com"
   SMTP_PORT="465"
   SMTP_TLS_MODE="tls"
   SMTP_USERNAME="notifications@example.com"
   SMTP_PASSWORD="REPLACE_IN_PRIVATE_EDITOR"
   SMTP_FROM="MeetSpace <notifications@example.com>"
   SMTP_TIMEOUT="15s"
   ```

   Замените примеры своими параметрами. Для STARTTLS укажите `starttls` и порт,
   предоставленный провайдером (обычно `587`). В двойных кавычках Compose
   экранируйте обратный слеш как `\\`, кавычку как `\"`, доллар как `$$`;
   переносы строк в значениях недопустимы. Не добавляйте SMTP-пароль в общий
   `meetspace.env`, доступный другим службам.
2. В `config/compose.json` добавьте путь `/opt/meetspace/config/smtp.env` в
   `env_file` **только** для `services.api` и `services.product-worker`,
   сохранив существующие элементы. Для обеих служб добавьте
   `environment.EMAIL_PROVIDER_MODE` со значением `smtp`, не удаляя остальные
   параметры. Если `env_file` или `environment` ещё отсутствуют, создайте их.
   Итоговый фрагмент каждой из двух служб выглядит так (остальные ключи сохранить):

   ```json
   {
     "env_file": ["/opt/meetspace/config/smtp.env"],
     "environment": {"EMAIL_PROVIDER_MODE": "smtp"}
   }
   ```

   Этот JSON — фрагмент службы, а не замена всего `compose.json`.
   Сам файл `smtp.env` без подключения к службам отправку почты не включает.
3. Откройте root-shell и используйте полную функцию `compose` из раздела
   [«Compose-контекст установки мастером»](DEPLOYMENT.md#compose-контекст-установки-мастером).
   Для нестандартного каталога и имени проекта подставьте значения из
   `installation.json`. Проверьте конфигурацию без вывода секретов и пересоздайте
   только службы уведомлений:

   ```bash
   compose config --quiet && compose up -d --no-deps --force-recreate api product-worker
   compose ps api product-worker
   ```

Пересоздание API кратковременно переподключит клиентов, поэтому выберите удобное
время. `docker restart` недостаточно: он не перечитывает env-файлы. После запуска
создайте новое приглашение на принадлежащий вам email и проверьте доставку.
Письма, пропущенные пока SMTP был отключён, автоматически не воспроизводятся.
Для отключения почты поменяйте `EMAIL_PROVIDER_MODE` на `noop` у тех же двух
служб и пересоздайте их указанной командой. Исходники, база данных и сертификаты
при этих действиях не изменяются.

Установки из Android / Desktop используют тот же `config/smtp.env`, но основной
файл называется `config/server.env`, а `config/compose.json` содержит полный
состав служб. Сохраните `server.env` первым элементом `env_file`, добавив
`smtp.env` вторым только у `api` и `product-worker`. Точный Compose-контекст и
порядок действий для них описаны в `installer/README.md` репозитория Android,
раздел «Enable email later after skipping SMTP»; не используйте для них
CLI-стек `bundle/deployment` из команды выше.

## 4. Файлы, данные и управление

| Путь по умолчанию | Содержимое |
| --- | --- |
| `/opt/meetspace/config/meetspace.env` | Настройки и секреты, права `0600` |
| `/opt/meetspace/config/smtp.env` | SMTP-параметры и пароль при включённой доставке, права `0600` |
| `/opt/meetspace/config/` | Compose-настройки и HTTPS-прокси |
| `/opt/meetspace/certs/` | Сертификат и приватный ключ |
| `/opt/meetspace/secrets/` | Секреты мониторинга |
| `/opt/meetspace/storage/` | Рабочие файлы записи, владелец `1000:1000` |
| `/opt/meetspace/bundle/source/` | Исходники установленного коммита, без `.git` |
| `/opt/meetspace/bundle/` | Проверенные образы, отчёты, контрольные суммы и инструменты |
| `/opt/meetspace/installation.json` | Параметры, коммит и состояние установки |
| `/opt/meetspace/manage.sh` | Команды сопровождения |

Текущий мастер собирает hardened-вариант: сервис `minio` запускает **SeaweedFS**
(`weed mini`, S3-порт 9000). Имя службы и настройки `MINIO_*` сохранены для
совместимости клиента; консоли MinIO на 9001 здесь нет. Старый том MinIO нельзя
подключать к SeaweedFS: перенос объектов требует отдельной S3-процедуры.

Итоговый Compose объединяет `docker-compose.production.yml`,
`docker-compose.hardened.yml`, `config/compose.json` и `config/turn.yml`. Последний
включает Coturn в host network. Overlay `docker-compose.shared-host.yml` мастер
не подключает. Команды с полным контекстом — в [DEPLOYMENT.md](DEPLOYMENT.md).

Данные БД, очереди и S3-хранилища находятся также в Docker-томах проекта.
Одной копии `storage/` недостаточно: см. [резервное копирование](operations/backup-restore.md).
Не публикуйте конфигурацию и вывод полной Compose-конфигурации: они содержат
секреты. Prometheus доступен только на loopback-порту `19090`; Grafana в
устанавливаемом hardened-составе не запускается.

```bash
sudo /opt/meetspace/manage.sh status
sudo /opt/meetspace/manage.sh logs api
sudo /opt/meetspace/manage.sh logs worker
sudo /opt/meetspace/manage.sh create-account
```

`logs` выводит последние 100 строк службы (без имени — всех служб).
Автоматическое обновление и удаление данных этими командами не выполняются.

## 5. Продолжение после ошибки

При ошибке сборки мастер сохраняет отдельный каталог
`/var/tmp/meetspace-source-build.*` с исходниками, состоянием и отчётами и
печатает точную команду продолжения. Используйте именно её. Завершённые этапы
повторно проверяются; неполная сборка не подменяется чужими образами.
Этот каталог и сборочный кеш Docker не удаляются автоматически.

Если параметры установки уже сохранены, продолжите с теми же секретами:

```bash
sudo python3 -I /opt/meetspace/bundle/deployment/scripts/install/wizard.py \
  --resume /opt/meetspace
```

При другом каталоге используйте путь, который сообщил мастер. Завершённая
установка через `--resume` не обновляется. Не удаляйте каталог или Docker-тома
для обхода проверок. После успешной установки сохранённый рабочий каталог
сборки можно убрать отдельно, предварительно проверив установленную копию;
автоматической очистки чужих образов, кеша и данных нет.

## 6. Сертификат и проверка связи

Для Let’s Encrypt мастер включает `certbot.timer` и отдельный deploy-hook.
После продления он копирует сертификат, перечитывает Nginx и перезапускает
Coturn. Порт `80/tcp` должен оставаться доступным. Перезапуск Coturn может
кратковременно прервать звонки через TURN.

Для собственного сертификата обновите файлы в исходном каталоге и выполните:

```bash
sudo /opt/meetspace/manage.sh certificates
```

Если рабочие копии в `certs/` уже обновлены другим инструментом:

```bash
sudo /opt/meetspace/manage.sh reload-tls
```

После установки проверьте вход, сообщения, звонок и запись с двух устройств,
в том числе из другой сети. Проверки HTTPS и готовности контейнеров **не
подтверждают** прохождение реального аудио/видео через внешний firewall и TURN.
Локальная проверка сборки не заменяет полное испытание на чистом VPS.

## Для сопровождающего: готовые образы и публикация установщика

Workflow `.github/workflows/server-images.yml` запускается вручную из `main`
с новой неизменяемой версией. Два нативных GitHub runner собирают `linux/amd64`
и `linux/arm64`, сканируют все образы и собирают пакеты. Черновик GitHub Release
становится публичным только после успеха обеих архитектур; `prebuilt.json`
связывает архитектуры, исходный коммит, размеры и SHA-256 архивов.
Повторно публиковать ту же версию нельзя. Перед обновлением публичного
`install.sh` проверьте доступность обоих пакетов. `DEFAULT_RELEASE='latest'`
позволяет находить новые готовые релизы без перепубликации установщика; каждый
пакет по-прежнему привязан к точному коммиту и SHA-256. Удаление всех готовых
серверных релизов делает быструю установку невозможной — нужен новый пакет
или явный режим сборки из `main`.
Переносить файлы окружения, SMTP-пароли или приватные ключи в CI не требуется.

Сначала проверьте изменения и отправьте коммит в публичный GitHub. Затем из
чистого checkout этого коммита подготовьте четыре файла:

```bash
bash scripts/release/package-installer.sh \
  --commit "$(git rev-parse HEAD)" \
  --output /absolute/new-public-directory \
  --base-url https://meeting.janickiy.com/downloads
```

Упаковщик скачивает архив **из GitHub**, проверяет его структуру и получает
`install.sh` из этого же архива. В публикуемой копии `DEFAULT_REF` заменяется
полным SHA коммита. Результат:

- `install.sh` — установщик последнего совместимого готового релиза, с отдельным режимом `source`;
- `install.sh.sha256` — контрольная сумма установщика;
- `source.json` — репозиторий, коммит, адреса и SHA-256 архива исходников;
- `meetspace-source-COMMIT.tar.gz` — дополнительная копия публичных исходников.

Публикуйте только эти файлы в отдельном статическом HTTPS-каталоге. Не
публикуйте настоящие `.env`, состояние установки, ключи, записи или Docker-тома.
Раздел `/downloads/` не должен подменять скачивание HTML-страницей SPA.
Для установщика, checksum и `source.json` используйте `Cache-Control: no-cache`,
для неизменяемого commit-архива — длительное кеширование. Архивы старых
коммитов не заменяйте на месте.

После атомарного размещения скачайте все четыре файла GET-запросами и
проверьте их содержимое, размеры и SHA-256. Повторно проверьте доступность
публичного GitHub-коммита и отсутствие изменений работающего приложения.
