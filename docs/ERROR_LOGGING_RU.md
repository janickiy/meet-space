# Журнал технических ошибок MeetSpace

Журнал доступен в административном разделе `/errors`. Он собирает ошибки API,
media-worker, record-worker, product-worker, публичного сайта и самой админки.
Пользовательские отказы входа, блокировки, нарушения прав и ошибки валидации
не становятся техническими ошибками только из-за HTTP 4xx. Действия
администраторов сохраняются отдельно в журнале аудита.

## Срок хранения и предел

На каждой установке хранится до **20 000 агрегированных групп**, срок —
**14 дней**. Это предел групп, а не число отдельных повторений ошибки.

Группа определяется сервисом, уровнем, кодом, шаблоном маршрута, версией выпуска
и семейством браузера. Экземпляр сервиса и request ID не создают отдельные
группы. Повторения увеличивают `count`; `firstSeen` и `lastSeen` показывают
первое и последнее появление внутри текущего окна группы.

Срок отсчитывается строго от `firstSeen`. При его выходе за 14 дней группа
сразу исключается из API, даже если ошибка продолжает повторяться. Очередная
очистка удаляет её; новое появление создаёт свежую группу с новым ID и счётчиком.
При превышении 20 000 групп удаляются группы с самым старым `lastSeen`.

Очистка работает при пакетной записи и не реже раза в минуту при простое.
Транзакционная блокировка согласует очистку и записи всех Go-процессов
установки, поэтому конкурентные writers не расширяют предел.

## Что видно в админке

Список поддерживает фильтры по сервису, уровню, коду, периоду и request ID,
последовательную пагинацию курсором, открытие подробностей и автообновление.
Первая страница обновляется каждые 10 секунд при включённом автообновлении и
видимой вкладке; просмотр следующих страниц не переставляет текущий список.

Счётчики «Групп за час» и «Групп за сутки» — число сохранённых групп,
`lastSeen` которых попадает в соответствующий период с учётом фильтров.
Это не количество всех отдельных ошибок за час или сутки. «Всего групп»
также относится к агрегатам, прошедшим фильтры, до применения курсора.

В группе сохраняются только **последние** instance, request ID и координаты
JS-кадров. Поэтому фильтр `requestId` ищет последнее сохранённое значение,
а не всю историю запросов этой группы. Полная последовательность исходных
диагностических строк остаётся в stdout сервисов в пределах отдельной политики
хранения контейнерных логов.

## Безопасное содержимое

Постоянный журнал использует каталог безопасных описаний: например,
`http.5xx`, `server.panic`, `worker.failed`, `recording.failed` и клиентские
`client.uncaught_error`, `client.unhandled_rejection`, `client.react_render_error`.
Произвольный текст `error`, SQL-ошибка, panic value и исходное сообщение slog
в таблицу не переносятся.

Для неизвестного места вызова Go используется код вида `go.error.<digest>`:
короткий детерминированный digest места вызова и общее описание «Ошибка компонента».
Он разделяет разные источники, сохраняя приватные диагностические строки только
в исходном выводе сервиса. Привязка такого кода относится к конкретному выпуску.

Браузер передаёт только версию, разрешённый шаблон маршрута, фиксированную
категорию, семейство браузера и до пяти координат в JS-артефактах своего origin.
Сообщение исключения, имена функций, полный URL, query/hash, точный User-Agent,
пароли, токены, cookie, тела HTTP-запросов и переписка в отчёт не включаются.
Неизвестные JSON-поля отклоняются. Request ID нормализуется в канонический UUID.

## Доставка, очередь и сбои

Каждый Go-процесс имеет асинхронный сборщик. Вызов логирования не выполняет SQL
в обработчике пользовательского запроса. Вместимость — 256 событий в очереди
и не более одного дополнительного retry-пакета из 256 событий. Пакеты записываются
с интервалом около секунды; при недоступном хранилище выполняется максимум пять
попыток с тем же batch ID. После исчерпания попыток пакет отбрасывается.

На пакет действует deadline 3 секунды; внутри PostgreSQL установлены ограничение
ожидания блокировки 1 секунда и statement timeout 2,5 секунды. Завершение сборщика
отменяет текущую попытку и использует общий срок до 3 секунд для финального flush.
Сначала сборщик останавливается, затем закрывается его SQL-пул.

Таблица `error_event_batches` хранит квитанции batch ID. Квитанция, изменение
счётчиков и очистка фиксируются одной транзакцией: повтор после потерянного ответа
на commit не увеличивает счётчики дважды. Квитанции очищаются через 2 часа и также
имеют предел 20 000 строк. Это служебная таблица, её строки не входят в счётчик
групп интерфейса.

При переполнении очереди, длительном отказе PostgreSQL или завершении с исчерпанным
сроком часть новых событий может не попасть в админку. Потери отражаются метрикой
`dropped`; исходный stdout продолжает работать независимо. Сбой записи самого
журнала не порождает повторную ошибку в этот же журнал и не меняет готовность
приложения. Журнал не является гарантированной долговременной доставкой всех логов.

## Включение клиентской телеметрии

Для публичного сайта необходимы оба условия:

1. API запускается с `CLIENT_TELEMETRY_ENABLED=true`.
2. Публичный frontend собран с build argument `CLIENT_TELEMETRY_ENABLED=true`.

Публичный приёмник — `POST /api/v1/client-errors`. При выключенном серверном
флаге он возвращает 404. Размер отчёта ограничен 8 KiB; серверные лимиты —
30 запросов в минуту на IP и 300 в минуту на установку. Сам браузер отправляет
не более пяти отчётов в минуту и двадцати за время жизни страницы.

Телеметрия админки включена в её коде и принимается только за действующей
административной сессией, проверками Origin и CSRF через
`POST /api/v1/admin/client-errors`. Лимиты сервера — 30 отчётов в минуту
на администратора и 300 в минуту суммарно на API-процесс. Ограничитель идентичностей
также ограничен по памяти. Клиентские ограничения 5/мин и 20/страницу сохраняются.
Разделение сервисов `frontend` и `admin-frontend` видно в фильтре журнала.

## Административный API

API обслуживается отдельным административным listener и доступен через
административный HTTPS-порт установки, обычно `8081`. Публичный порт `443`
не публикует административные маршруты и возвращает 404. Публичный JWT
не заменяет административную сессию.

- `GET /api/v1/admin/errors` — список и сводка.
- `GET /api/v1/admin/errors/:id` — подробности существующей неистёкшей группы.

Параметры списка: `service`, `level`, `code`, `requestId`, `from`, `to`,
`cursor`, `pageSize`. Время передаётся в RFC3339; `from` не может быть позже `to`.
Размер страницы — от 1 до 100, по умолчанию 25. Курсор нужно брать из
`nextCursor` предыдущего ответа; пустое значение означает конец списка.
Неизвестные и повторяющиеся параметры отклоняются. Неверный запрос возвращает
422, отсутствующая или истёкшая группа — 404, отсутствие сессии — 401.

Ответ списка содержит `items`, `nextCursor`, `summary`, `retentionDays: 14`
и `maxRecords: 20000`. Маршрутов произвольного добавления серверных ошибок,
удаления группы или изменения её содержимого в API нет.

## Метрики

Метрики доступны только через существующую защищённую инфраструктуру наблюдения
сервиса, а не как публичный endpoint админки:

| Метрика | Значение |
| --- | --- |
| `recorder_error_events_accepted_total` | События, принятые локальной очередью |
| `recorder_error_events_written_total` | События успешно переданных пакетов |
| `recorder_error_events_dropped_total` | События, отвергнутые или отброшенные сборщиком |
| `recorder_error_events_queued` | Ожидающие события канала, без текущего retry-пакета |

`written` отражает успешную передачу в идемпотентный репозиторий; это не число
новых строк таблицы, поскольку повторы агрегируются. Counter-метрики локальны
процессу и сбрасываются при его перезапуске.

## Развёртывание и пределы покрытия

Нужна миграция **44**: `000044_error_events.up.sql`, затем обновление API,
media/record/product workers и admin proxy. Для браузерных событий публичного
сайта требуется также сборка/обновление frontend с включённым build argument.
Исторические migration checksums конкретного хоста должны сохраняться.
Весь выпуск сначала подготавливается с резервными конфигурациями и копией БД;
миграция запускается отдельной задачей после штатного graceful drain.

Сборщик запускается после подключения PostgreSQL и проверки миграций. Отказы,
из-за которых процесс вообще не смог дойти до этой стадии, остаются только
в stdout. Системный вывод Nginx, PostgreSQL, Redis, Docker и ОС автоматически
не импортируется: раздел собирает прикладные структурированные Go-ошибки и
валидированные клиентские отчёты.

Это описание реализации и операторского контракта. Результаты конкретного
развёртывания фиксируются отдельно после проверки рабочих хостов.

## Проверки реализации

Перед выпуском прошли Go race-тесты и PostgreSQL17 integration suite, `go vet`,
46 тестов публичного frontend, тесты административной телеметрии и браузерные
сценарии раздела. Для хранилища отдельно проверены идемпотентность повторов,
пагинация, фильтры, безопасное содержимое, строгий срок 14 дней, предел 20 000
групп при конкурентных writers и полный путь Go logger → очередь → PostgreSQL.
Для очереди проверены предел памяти, неблокирующее добавление, retries,
flush и конкурентное завершение; для UI — темы, узкий экран, детали,
пагинация и завершение административной сессии.
