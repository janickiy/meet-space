# Развёртывание MeetSpace

Для первой установки на новый сервер: [скачивание и запуск `install.sh`](INSTALLATION.md).
Ниже отдельно описаны сопровождение установки через мастер и общий процесс выпуска.

MeetSpace разворачивается на одном сервере Docker Compose. Перед приёмкой
проверьте DNS/TLS/TURN, межсетевой экран, связь с реальных устройств и нагрузку.
Состав сервисов и ограничения: [ARCHITECTURE.md](ARCHITECTURE.md).

## Выбор процедуры по типу установки

| Тип | Фактическая конфигурация | Как сопровождать |
| --- | --- | --- |
| Новый отдельный сервер через `install.sh` | Рабочая конфигурация + hardened + сгенерированные `config/compose.json` и `config/turn.yml`; собственный прокси на 443, TURN в сети хоста, SeaweedFS | `manage.sh` и Compose-функция ниже; автоматического обновления пока нет |
| Общий выпуск, `deploymentLayout=classic` | Рабочая конфигурация + дополнительный файл Grafana; MinIO | `scripts/release/release.sh`, отдельные проект, env-файл и манифест |
| Общий выпуск, `deploymentLayout=hardened-shared-host` | Рабочая конфигурация + hardened + дополнительный файл shared-host; существующий внешний TLS-прокси, SeaweedFS | Скрипт выпуска только после сверки внешнего прокси, подсети, портов и томов |
| Разработка | `docker-compose.yml`, `.env`, локальные каталоги, подключённые в контейнеры | [README](../README.md); не шаблон рабочего окружения |

В конфигурации разработки API, служебный HTTP сервиса записи, отладчики, PostgreSQL,
Redis и MinIO опубликованы только на `127.0.0.1`. Для удалённой отладки
используйте SSH-туннель. HTTPS и медиапорты остаются доступными для проверки
звонков с других устройств. Не открывайте отладчик или Redis в интернет;
рабочее окружение использует отдельный Compose-шаблон с приватными зависимостями.

Мастер выпускает архив с `deploymentLayout=hardened-shared-host`, но при установке
**заменяет дополнительный файл конкретного хоста** своей конфигурацией. Поэтому одного манифеста
недостаточно для выбора Compose-файлов. `release.sh`, `backup.sh` и
`restore-check.sh` используют `scripts/release/common.sh`: для hardened они
подключают `docker-compose.shared-host.yml`, не `config/compose.json` и `turn.yml`.
Не запускайте эти скрипты для установки мастера, указав только её env-файл
и манифест: могут быть выбраны другие сеть, прокси и пути томов. Продолжение через
`scripts/install/wizard.py --resume` также не обновляет завершённую установку;
В прежней редакции `install.sh` принимал только `--ref` и `--help`.
Актуальные режимы и параметры установщика описаны в [INSTALLATION.md](INSTALLATION.md).

### Compose-контекст установки мастером

Для стандартных каталога `/opt/meetspace` и проекта `meetspace` в оболочке с правами root
(`sudo -i`) задайте функцию. При других значениях сверяйте `installation.json`:

```bash
cd /opt/meetspace
compose() {
  docker compose --project-name meetspace \
    --env-file /opt/meetspace/config/meetspace.env \
    -f /opt/meetspace/bundle/deployment/docker-compose.production.yml \
    -f /opt/meetspace/bundle/deployment/docker-compose.hardened.yml \
    -f /opt/meetspace/config/compose.json \
    -f /opt/meetspace/config/turn.yml "$@"
}
compose --profile observability --profile migration config --quiet
compose --profile observability ps -a
compose exec -T api wget -qO- http://127.0.0.1:8085/health/ready
```

Эта функция далее используется в руководстве по эксплуатации и инструкции резервного копирования.
`manage.sh status`, `logs [service]`, `create-account`, `certificates`, `reload-tls`
используют тот же установленный контекст. Изменение env-файла требует пересоздания
использующей его службы; `docker restart` не перечитывает env-file. Перед заменой образов нужны
резервная копия, проверка совместимости миграций, готовый старый пакет и план
с **теми же** томами, сетью, TLS, прокси и ID образов. Переключение MinIO ↔ SeaweedFS — перенос данных,
а не обычное обновление образа.

## Окружения общего процесса выпуска

| Среда | Конфигурация / проект | Назначение и границы |
| --- | --- | --- |
| Разработка | `docker-compose.yml`, локальный `.env` | Разработка, локальная сборка и отладка; тестовые пароли и открытые порты не переносятся в рабочее окружение |
| Локальная репетиция выпуска | Compose рабочего окружения + `docker-compose.release-local.yml`; `recorder-release-rehearsal` или такой префикс с суффиксом | Отдельные тома/порты, `APP_ENV=test`, loopback, временный сертификат; допускаются локальные ID образов и явно отмеченные изменения исходников |
| Проверочный стенд (staging) | Compose рабочего окружения; `recorder-staging` или суффикс | Реальные адреса HTTPS/WSS/TURNS, отдельные секреты и данные, неизменяемые образы из реестра или архива, `APP_ENV=production`; состояние стенда проверяется для каждого выпуска |
| Рабочее окружение (production) | Compose рабочего окружения; `recorder-production` или суффикс | Собственные DNS/TLS/хранилища, проверенный манифест, отчёты проверок и явное решение оператора |

У каждой среды свои PostgreSQL, пространства имён Redis, RabbitMQ, бакет и данные S3,
учётные данные провайдеров и идентификаторы фоновых обработчиков. Нельзя направлять
локальные тесты в зависимости рабочего окружения. Внешние email-уведомления,
push и календарь по умолчанию отключены. Режим имитации запрещён в проверочном и рабочем окружениях. Матрица флагов и лимитов —
[API.md](API.md), шаблон — [`.env.production.example`](../.env.production.example).

Историческое ограничение прежней реализации: семантический поиск требовал pgvector,
а пакет использовал обычный образ PostgreSQL 16. Поэтому одного переключения
`EMBEDDINGS_ENABLED` было недостаточно: требовались отдельно согласованные
совместимые образ, расширение и проверка миграции. Нельзя было заменять закреплённый
образ БД при развёртывании приложения ради этой функции. Актуальный состав функций
описан в [техническом руководстве](MEETSPACE_TECHNICAL_GUIDE_RU.md).

## Подготовка хоста

Для общего процесса выпуска нужны Docker Engine и Compose 2.24.4+ с поддержкой `!override`, Bash, `jq`,
`openssl`, `ripgrep`, утилита SHA-256; для сборки операторских бинарников —
поддерживаемая версия Go из `go.mod`. Скрипты вызываются через `bash`, права
исполнения у файла не предполагаются. Команды ниже выполняются из корня репозитория.

Для проверочного и рабочего окружений заранее подготовьте:

- DNS, сертификаты HTTPS и TURNS, публичный IP SFU и согласованные порты межсетевого экрана и NAT из [архитектуры](ARCHITECTURE.md); один открытый порт не подтверждает работу ретрансляции.
- Абсолютный env-файл вне Git, права `0600`, секреты из внешнего защищённого
  источника; не выводите `docker compose config` без `--quiet` и не включать `set -x`.
- `TLS_CERT_DIR` и `TURN_TLS_CERT_DIR` с `fullchain.pem`/`privkey.pem`.
  Ключ Coturn должен читаться его пользователем, но не быть общедоступным.
- `RECORDER_STORAGE_DIR` с владельцем `1000:1000` и правами `0750`, запасом места;
  директории объектов и БД на диске с проверенным резервированием.
- `METRICS_TOKEN_FILE` вне Git с правами чтения контейнера; значение совпадает
  с `METRICS_SECRET`. Для classic также нужен `GRAFANA_PASSWORD_FILE`.
- Доступ к реестру образов, проверенный манифест выпуска из чистой рабочей копии
  и предыдущий манифест.
  Все операторы одного Docker-хоста используют общий абсолютный `RELEASE_LOCK_DIR`.
  Локальный каталог блокировок одного ноутбука не защищает от другого оператора.
- Обычные аккаунты для ручной проверки входа, прав и пользовательских сценариев.

Compose рабочего окружения не публикует БД, Redis, RabbitMQ и S3. Prometheus доступен
на loopback 19090. Grafana доступна на loopback 13001 только в classic-варианте;
hardened и текущая установка мастером её не запускают. Организуйте закрытый
доступ оператора. Внутренние HTTP/AMQP/Redis предполагают доверенную сеть одного хоста; перенос на разные
хосты требует отдельного решения TLS/mTLS/VPN.

## Локальная репетиция без изменения существующих проектов

Выберите новый абсолютный путь к каталогу. Скрипт инициализации создаёт отдельные
конфигурацию, секреты, сертификат и хранилище для репетиции.

```bash
LOCAL_RELEASE_DIR=/absolute/private/meet-rehearsal
bash scripts/release/init-local.sh --directory "$LOCAL_RELEASE_DIR"
```

Получатся `.env.local`, временный TLS-сертификат, секреты и хранилище. HTTP API
публикуется только на `127.0.0.1:28085`, HTTPS UI — `https://localhost:25482`,
SFU — `50220`, TURN — `23478` и диапазон ретрансляции `50300–50340`. Это локальная схема с
разрешённым loopback и без TURNS; её параметры нельзя считать шаблоном рабочего окружения.
Инициализация использует доступный контейнеру рабочий каталог записи;
для рабочего окружения обязательны
ограниченные права, указанные выше.

Для GET-проверки локального HTTPS явно укажите созданный CA, например
`curl --cacert "$LOCAL_RELEASE_DIR/certs/fullchain.pem" https://localhost:25482/version`.
Для ручной работы браузера настройте доверие сертификату только в выделенном
профиле стенда. В проверочном и рабочем окружениях проверяйте действительную цепочку
и имя сертификата.

После [сборки и упаковки](RELEASE_PROCESS.md) укажите существующий манифест:

```bash
LOCAL_MANIFEST=/absolute/artifacts/package/release.json
bash scripts/release/release.sh validate --environment local --project recorder-release-rehearsal --env-file "$LOCAL_RELEASE_DIR/.env.local" --manifest "$LOCAL_MANIFEST"
bash scripts/release/release.sh migrate --environment local --project recorder-release-rehearsal --env-file "$LOCAL_RELEASE_DIR/.env.local" --manifest "$LOCAL_MANIFEST"
bash scripts/release/release.sh deploy --environment local --project recorder-release-rehearsal --env-file "$LOCAL_RELEASE_DIR/.env.local" --manifest "$LOCAL_MANIFEST"
```

Скрипты принимают только разрешённый проект для выбранной среды. `migrate`
поднимает зависимости и запускает отдельное задание миграции. `deploy` не выполняет
DDL и не собирает образы. Если зависимости уже существуют, замена их образов
запрещается: обновление PostgreSQL/Redis/RabbitMQ/S3/Coturn — отдельное окно.

## Проверочное и рабочее окружения общего процесса выпуска

Перед выполнением команд замените все пути и адреса на проверенные реальные
значения. `validate` проверяет формат/Compose, но не доказывает доступность
DNS, сертификата, TURN, реестра образов и возможность восстановления данных.

```bash
STAGING_CONFIG=/srv/meet/config/staging.env
RELEASE_MANIFEST=/srv/meet/releases/v1.2.3/release.json
bash scripts/release/release.sh validate --environment staging --project recorder-staging --env-file "$STAGING_CONFIG" --manifest "$RELEASE_MANIFEST"
bash scripts/release/release.sh pull --environment staging --project recorder-staging --env-file "$STAGING_CONFIG" --manifest "$RELEASE_MANIFEST"
bash scripts/release/release.sh migrate --environment staging --project recorder-staging --env-file "$STAGING_CONFIG" --manifest "$RELEASE_MANIFEST"
bash scripts/release/release.sh deploy --environment staging --project recorder-staging --env-file "$STAGING_CONFIG" --manifest "$RELEASE_MANIFEST"
```

Для обновления существующего окружения перед `migrate` обязателен согласованный
[backup с write freeze](operations/backup-restore.md) и проверка миграций на копии.
Рабочее окружение использует те же операции с `--environment production`, проектом
`recorder-production`, собственным env-файлом, дополнительным разрешением и отчётами проверок
из [RELEASE_PROCESS.md](RELEASE_PROCESS.md). Нельзя подменять `production` на
`local` ради обхода обязательной проверки.

Обновление приложений идёт последовательно:
перед ним ограничьте новые запуски записей, дождитесь уже ожидающих `record.start`
и штатного завершения активных записей. `active=0` у процесса не означает пустую
очередь команд. Ограничения возврата команд в очередь и порядок завершения работы сервиса записи описаны в
[инструкция по эксплуатации](operations/README.md#health-и-завершение).

Порядок замены:
`media-worker → record-worker → product-worker → api → frontend → proxy`,
затем мониторинг. Сначала служба переводится в режим завершения работы;
после прекращения активности её заменяют и проверяют состояние.
При истечении времени ожидания процесс остаётся в режиме завершения работы;
принудительного перезапуска нет. Это управляемая замена служб на одном сервере
с возможным перерывом, а не гарантия непрерывной работы или постепенного
переключения доли трафика на новую версию.

При первом обновлении с удалением функций речи действует отдельное окно
обслуживания: [миграция 000037 и переименование сервиса](operations/speech-removal-upgrade.md).
Она требует проверенной резервной копии и остановки всех прикладных процессов.
Обычный последовательный порядок выше не заменяет это требование.

Для возобновления после завершения активной работы или резервного копирования существует `release.sh resume`
с тем же установленным манифестом: он пересоздаёт процессы с теми же образами.
Если выпуск остановился посередине и образовалась смесь версий, сначала
сверьте фактические ID образов каждого сервиса и процедуру [отката](ROLLBACK.md).
Не используйте `resume` с произвольным манифестом.

## Ротация секретов

Сохраняйте изменения в защищённом env-файле или хранилище секретов, а не в образе
или Git. Планируйте перезапуск использующих секреты служб. После каждой группы
изменений проверяйте `/version`, готовность, авторизацию, WebSocket, медиа и доставку.

| Секрет | Последствия и порядок |
| --- | --- |
| `JWT_SECRET` | Новый ключ отвергает старые JWT; потребители должны согласованно получить его. Выход отдельного пользователя из аккаунта не заменяет эту операцию |
| Билеты медиа и внутренние секреты медиа и сервиса записи | Согласованно обновить API и соответствующие обработчики. Старые билеты и вызовы могут перестать работать; понадобится повторное подключение |
| `METRICS_SECRET` | Согласованно обновить приложения и `METRICS_TOKEN_FILE`, затем проверить сбор метрик; режим завершения работы также использует этот секрет |
| `TURN_SHARED_SECRET` | Согласовать Coturn и выдачу учётных данных в приложении, учесть срок действия старых данных и проверить новые соединения через ретранслятор |
| Пароли PostgreSQL/Redis/RabbitMQ/MinIO | Сначала запланировать изменение учётной записи самой зависимости, затем всех клиентов; изменение env не меняет пароль в существующем постоянном хранилище автоматически |
| `PROVIDER_TOKEN_ENCRYPTION_KEY` | Не заменять вслепую: существующие зашифрованные данные станут нечитаемыми. Автоматического повторного шифрования и набора версий ключей нет. Нужен отдельный план переноса токенов либо отключения и повторного подключения; старый ключ следует сохранить для разрешённого восстановления резервной копии |
| Учётные данные провайдера/OAuth | Ротация у провайдера, затем в использующих их службах. Учесть повторы заданий, обновление и отзыв доступа, готовность внешнего шлюза |

Наличие инструкции не означает выполненную ротацию или проверенный выпуск в рабочем окружении. Итоговое решение принимается по [чеклисту запуска](PRODUCTION_LAUNCH_CHECKLIST.md).
