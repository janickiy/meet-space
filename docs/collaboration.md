# Совместная работа, чат и история встреч

Документ описывает действующие конференционные
сценарии. Личные и групповые переписки используют общий механизм сообщений,
но отдельные права: [PERSONAL_MESSAGES.md](PERSONAL_MESSAGES.md), [GROUP_CHATS.md](GROUP_CHATS.md).
Полный каталог HTTP — [API_REFERENCE.md](API_REFERENCE.md).

## 1 Возможности и доступ

Встреча сохраняет сообщения, ответы, файлы и отметки прочтения. Участники могут
использовать реакции, расписание, персональные уведомления и историю записей.
После завершения чат доступен для чтения допущенным участникам `joined|left`,
которые не были исключены и не вышли отдельно из чата.

Действующее приглашение даёт немедленный допуск (`admitted`) в открытую встречу,
даже при `waitingRoomEnabled=true`, включая ранее ожидавшего участника.
Явные `rejected`/`kicked` сохраняются. Join существующего участника без кода
не меняет прежний допуск. В запланированную встречу аккаунт добавляет членство,
но медиа появляется только после старта; новый гость до старта не входит.
Зал ожидания и admission API остаются для членств в состоянии `waiting`.

В конференции используется одно WebSocket-соединение для сигналинга и событий;
чат/реакции не заменяют медиасоединение. PostgreSQL, Redis и приватный MinIO
обслуживают постоянные данные, доставку и файлы соответственно.

## 2 Архитектурные решения

PostgreSQL остаётся источником постоянных данных. Изменения чата публикуются после
успешной транзакции. Redis обеспечивает присутствие, доставку событий и отдельные ограничения частоты запросов. Потерянные события чата
восстанавливаются чтением истории при переподключении и каждые 15 секунд.

Уведомления доставляются по отдельному авторизованному HTTP SSE-потоку, поэтому
работают на главной странице и в зале ожидания без доступа к комнате. Решения о
допуске и готовые записи создают задания в PostgreSQL в той же транзакции через
триггеры. Обработчик формирует уведомления, а `published_at` позволяет повторять
публикацию после сбоя. RabbitMQ продолжает обслуживать существующие команды записи;
продуктовые задания не направляются в очередь recorder-worker.

## 3 Миграции и схема базы

| Миграция | Изменения |
| --- | --- |
| `000012_stage_five_conferences` | Расписание, флаг зала ожидания, admission state и версия решения, индексы истории и очереди ожидания |
| `000013_chat_attachments_read` | `chat_messages`, `chat_attachments`, `chat_read_states`, индексы курсора, непрочитанного и очистки |
| `000014_notifications` | `notifications`, `notification_jobs`, индексы непрочитанных и необработанных заданий, транзакционные триггеры |

Миграции применяет общий runner проекта.
Отдельная таблица чатов не создаётся: одна конференция соответствует одному чату.
Внешние ключи используют `RESTRICT`, а не каскадное удаление истории.
Для `notification_jobs.conference_id` нет избыточного прямого внешнего ключа:
историю защищают связи задания с участником или записью. Это предотвращает
инверсию блокировок между завершением записи и остановкой конференции.

Порядок сообщений задаётся серверным `BIGSERIAL`; уникальный индекс имеет форму
`(conference_id, sequence DESC)`. Отдельный глобальный индекс sequence исключён:
он приводил к сканированию сообщений других конференций. Read state использует
одну строку на пользователя и конференцию, а не строку на каждое сообщение.

## 4 Состояния зала ожидания

| Состояние | Доступ и переход |
| --- | --- |
| `waiting` | Только собственное членство, ограниченные сведения о встрече и личные уведомления; организатор может допустить или отклонить |
| `admitted` | Чат и история по правилам членства; живые медиа требуют `joined` и открытой встречи |
| `rejected` | Нет медиа, чата, файлов и истории; повторный invite не обходит отказ |
| `kicked` | Доступ отозван, подключение закрывается, повторный вход запрещён |

Admission отделён от состояния подключения. Выход ожидающего участника даёт
`left + waiting`; повторный вход восстанавливает тот же запрос и UUID. Переподключение
не создаёт второго участника. Для ожидающих WebSocket-комната не открывается;
решение для аккаунта приходит через SSE; клиент также опрашивает собственное
членство. Гости не имеют доступа к персональному списку уведомлений.

Допуск разрешён `owner` и `co_host`, которые присоединились к активной встрече.
Обычная модерация не действует на ожидающих: для них есть отдельное отклонение.
Одновременные admit/reject сериализуются блокировкой конференции; повтор одного
решения идемпотентен, противоположное решение после завершённого перехода даёт 409.
Очередь ожидания не входит в снимки и события обычных участников.

## 5 API и протокол чата

Все пути в таблице начинаются с `/api/v1/conferences/:id` и требуют Bearer JWT.

| Метод и путь | Назначение |
| --- | --- |
| `GET /messages?before=cursor&limit=50` | Последние сообщения и следующие страницы истории |
| `POST /messages` | `{clientRequestId,text,replyTo?,attachmentIds?}` |
| `PATCH /messages/:messageId` | Редактирование собственного текста |
| `DELETE /messages/:messageId` | Мягкое удаление своего сообщения; модератор может удалить чужое |
| `GET /chat/read` | Текущий курсор и число непрочитанных |
| `PUT /chat/read` | `{messageId}` — продвижение курсора |

Сообщения содержат UUID, строковый sequence, автора, текст, ссылку ответа,
вложения, версию и временные отметки. Текст — обычный текст, максимум 4000 Unicode
символов. Без текста требуется хотя бы один файл. Ответ должен ссылаться на
существующее сообщение этой же конференции. Страница ограничена 100 сообщениями.

Уникальность `(conference_id,sender_user_id,client_request_id)` предотвращает
дублирование при повторной отправке. Повтор с другим содержимым даёт 409.
Редактирование и удаление используют одинаковый порядок блокировок; удалённый
текст нельзя восстановить запоздалым редактированием.

События: `chat.message.created`, `chat.message.updated`, `chat.message.deleted`,
`chat.read.updated`. Клиент объединяет страницы по UUID и версии, хранит sequence
без потери точности и объединяет обновления запросов в окно 200 мс.

### Дополнительные действия чата встречи

Префикс ниже — `/api/v1/conferences/:id/chat`. Чтение требует действующего
допуска и отсутствия отдельного выхода из чата. Полные поля/ошибки — в API-каталоге.

| Метод и путь | Запрос и результат |
| --- | --- |
| `GET /info` | id.<br>200: status,item: conferenceId,title,description,inviteUrl,participantCount,notificationsEnabled,canEdit,canInvite |
| `GET /members` | id; after cursor, limit 1–100 (50).<br>200: status,items: MemberView[],nextCursor |
| `PATCH /info` | id; JSON title 1–200 и/или description ≤1000; хотя бы одно поле.<br>200: status,item: ChatInfo |
| `GET /preferences` | id.<br>200: status,item: notificationsEnabled |
| `PUT /preferences` | id; JSON notificationsEnabled* bool.<br>200: status,item: notificationsEnabled |
| `DELETE /membership` | id; без тела.<br>200: status=success |
| `GET /messages/search` | id; q* 2–200 символов; before; limit 1–50 (20).<br>200: status,items: Message[],nextCursor |
| `GET /messages/:messageId/context` | id,messageId.<br>200: status,items,nextCursor,unreadCount,lastReadMessageId |
| `GET /materials` | id; kind*=image/file/link; before; limit 1–50 (20).<br>200: status,items: Material[],nextCursor |
| `GET /pins` | id; before; limit 1–50 (20).<br>200: status,items: Message[],nextCursor |
| `PUT /pins/:messageId` | id,messageId; без тела.<br>200: status=success |
| `DELETE /pins/:messageId` | id,messageId; без тела.<br>200: status=success; идемпотентно |

`PATCH /info` доступен owner; имя 1–200, описание до 1000 символов, хотя бы одно
поле. Изменение предпочтений и `pins` касается только текущего пользователя:
`important` — личная отметка, в отличие от общих закреплений conversation.
`DELETE /membership` — явный выход из чата: скрывает доступ и связанные папки;
обычный `/conferences/:id/leave` лишь завершает участие в звонке. Повторный
разрешённый join открытой встречи восстанавливает членство в чате.

Поиск конференционных сообщений использует `/chat/messages/search`; персональный
поиск использует `/conversations/:id/messages/search`. Не подменяйте эти пути
несуществующими `/conferences/:id/messages/search` или старым `/history/search`.

## 6 Вложения и хранение

Последовательность: `POST /attachments/init` → `PUT /attachments/:id/content`
с исходными байтами → `POST /attachments/:id/finalize` → отправка сообщения с ID
файла. Повторная финализация безопасна; повторная передача с другими байтами
отвергается. Файл привязывается к сообщению атомарно.

Допустимы изображения, PDF, офисные и текстовые документы, архивы ZIP, RAR, 7Z,
TAR, GZIP, BZIP2, XZ, Zstandard и другие [поддерживаемые форматы](ATTACHMENTS.md).
Ограничения: 10 МиБ на файл, 5 файлов
на сообщение, 20 незавершённых вложений на пользователя в конференции. Сервер
проверяет имя, расширение, MIME, сигнатуру содержимого, размер и SHA-256.
Архивы не распаковываются, документы и макросы не выполняются. Путь генерируется
сервером: `attachments/{conferenceUUID}/{attachmentUUID}/{uploadTokenUUID}`.
В публичный ответ не входят внутренний ключ, токен загрузки и lease.

Одновременно один API принимает не более четырёх файлов; буферы содержат не более
примерно 40 МиБ полезных данных. Nginx пропускает до 11 МиБ на конкретном upload
маршруте, API проверяет точный лимит 10 МиБ. Проксирование запроса потоковое.
Чтение тела ограничено 60 секундами, операция — 75 секундами, lease — 120 секундами.

Незавершённые `pending/ready` истекают через 30 минут. Фоновая очистка раз в минуту
обрабатывает до 100 строк с защитой действующих загрузок и удаляет только точные
серверные префиксы. Привязанный объект сохраняется; проигравшие попытки удаляются.

`GET /attachments/:id/download` повторно проверяет членство и видимость сообщения
и выдаёт ссылку на 5 минут. MinIO остаётся закрытым; публичная политика бакета
приводит к отказу инициализации, а не автоматически переписывается. Ответ скачивания
принудительно `attachment` и `application/octet-stream`, без встроенного просмотра.

## 7 Отметки прочтения

`chat_read_states` хранит последний message ID, sequence и время. Условное
обновление продвигает sequence только вперёд; запоздалая вкладка его не уменьшает.
Непрочитанные считаются по индексированному диапазону, без своих и удалённых
сообщений. UI отмечает прочтение только при видимой странице и последних видимых
сообщениях, с задержкой 800 мс. Запись read state и отправка сообщений имеют
разные лимиты, поэтому частые read updates не блокируют отправку или звонок.

## 8 Реакции

`POST /reactions {emoji}` требует допущенного участника активной встречи.
Реакции ограничены `👍 👏 ❤️ 😂`, не сохраняются в PostgreSQL. Лимит — 5 реакций
за 10 секунд на пользователя; для комнаты — 30 в секунду. Проверка допуска
предшествует расходованию общего лимита комнаты.

У Hub отдельная очередь 128 некритичных событий и отдельный обработчик. У каждого
сокета ещё одна очередь на 8 событий чата и реакций. Переполнение отбрасывает
эти события, но не закрывает звонок. Signaling, модерация и состояние записи
используют прежнюю очередь с приоритетом. UI показывает не более шести реакций
одновременно, примерно на 3,5 секунды.

## 9 Уведомления

Типы версии 1: `conference.soon`, `admission.decided`, `recording.ready`.
Payload содержит только ссылки и состояние, без текста чата, имён файлов или
ссылок на скачивание. Уведомление не даёт права открыть соответствующий ресурс.

API: `GET /api/v1/notifications?cursor=…&limit=30`,
`POST /api/v1/notifications/:notificationId/read`,
`GET /api/v1/notifications/events`. Последний путь — fetch SSE с JWT в заголовке,
не в URL. Query запрещён, `Last-Event-ID` не воспроизводит пропуски.
Список отвечает `{items,nextCursor,unreadCount}`, отметка — `{item}` без поля
`status`. `limit` списка 1–100 (по умолчанию 30). Перед событием и keepalive
проверяется сессия; поток заканчивается при истечении JWT или drain.
На API не более 256 потоков,
на пользователя — 4; попытки подключения ограничены отдельно. Есть keepalive каждые 15 секунд и
буфер 32 события. Клиент восстанавливает поток и перечитывает REST-список;
Redis Pub/Sub не хранит историю. Лимит подключений — 12/минуту на пользователя.

Фоновая обработка выполняется раз в 5 секунд. Напоминание создаётся в пределах
15 минут до встречи. Ключ расписания использует UTC epoch, независимо от timezone
SQL-сессии. Admission jobs сохраняют каждую версию решения, в том числе быстрый
admit → kick. Recording jobs обрабатывают участников порциями по 100 с курсором;
общий бюджет цикла — 1000 получателей. Получатель должен существовать и быть
допущен до готовности записи и сохранять доступ при обработке задания.

Задания выбираются через частичный индекс и `FOR UPDATE SKIP LOCKED`. История
готовых записей не сканируется каждые 5 секунд. При запуске выполняется идемпотентный
backfill старых фактов. Уникальные ключи защищают задания и уведомления от дублей.
Публикация после commit допускает повтор события с тем же ID; клиент его устраняет.
Email/push и внешние календарные интеграции реализованы отдельно и по умолчанию
выключены. Они не заменяют внутренние уведомления; см. [content-integrations.md](content-integrations.md).

## 10 Жизненный цикл расписания

Немедленные встречи сохраняют `created → active → finished`. Запланированные
используют `scheduled → active → finished` либо `scheduled → cancelled`.
`scheduledAt` принимается как RFC3339 с timezone и хранится UTC; необязательная
плановая длительность — от 1 до 1440 минут.

Владелец может изменить время только в `scheduled` через `PUT /schedule` и может
начать встречу раньше назначенного времени. Автоматического запуска или жёсткого
завершения по таймеру нет. До старта join означает включение в список будущих
встреч, но не разрешение на медиа. Обновление расписания и старт используют одну
блокировку конференции, поэтому позднее изменение не перезаписывает активную встречу.

## 11 История и списки встреч

`GET /api/v1/me/conferences` поддерживает `view=upcoming|active|past`,
`scope=all|owned|participating`, `status`, `from`, `to`, `cursor` и `limit`.
Фильтры применяются на сервере до пагинации. Порядок —
`COALESCE(finished_at,scheduled_at,created_at) DESC, id DESC`; from/to относятся
к этой же дате. Ожидающие видят свою будущую или активную встречу, но не её историю.

`GET /api/v1/conferences/:id/history` возвращает закрытую встречу, организатора, время,
длительность, число и первые 100 видимых членств, признак усечения, агрегированные
статусы записей и доступность чата. Остальной список участников доступен по
существующей пагинации. Сводка записей считается из `record`, а не копируется в
конференцию. Воспроизведение использует существующий авторизованный recording API.

## 13 Ограничения

- Антивирусной проверки и встроенного просмотра вложений нет.
- Ранее выданная ссылка на конференционное вложение остаётся действительна
  до пяти минут после изменения прав; уже скачанные байты не отзываются.
- Удаление сообщения закрывает выдачу новых ссылок, но не означает немедленного
  физического уничтожения прикреплённого объекта. Записи имеют отдельную
  политику хранения: [conference-recording.md](conference-recording.md).
- Доставка событий через Redis восстанавливается по REST, без журнала replay.
  При повторной публикации notification ID позволяет устранить дубль.
- Напоминание зависит от фонового обработчика в 15-минутном окне; backlog может
  задержать доставку. Запись не рассылается задним числом участникам, допущенным
  после её готовности, хотя история может разрешать им её чтение.
