# Откат приложения

> При обновлении старой установки сначала выполните [переход на record-worker и миграцию 000037](operations/speech-removal-upgrade.md). Миграция необратимо удаляет данные функций речи; требуются проверенная резервная копия и остановка старых процессов. Простой откат образов после неё не поддерживается.

Откат приложения — это запуск предыдущих **готовых неизменяемых образов**
на совместимой текущей схеме БД. Он не отменяет миграции и не восстанавливает
потерянные данные. При работе Compose на одном сервере возможен перерыв.
Перенос работающей комнаты между SFU не предусмотрен. Возможность отката нужно
проверить заранее для конкретного выпуска.

Команды ниже относятся к общему процессу выпуска (classic либо shared-host).
Для установки мастером нельзя передавать только её env-файл и манифест
в `release.sh`: скрипт выбирает другие дополнительные Compose-файлы.
Сначала сохраните и проверьте полный
[Compose-контекст установки](DEPLOYMENT.md#compose-контекст-установки-мастером),
ID прежних образов и конфигурацию. Убедитесь, что тома, сеть, прокси и TURN
остаются прежними. Автоматической команды отката в `manage.sh` нет.

## Когда остановить продвижение

Не продолжайте выпуск, если версии не совпадают с манифестом, службы не проходят
проверку готовности, массово нарушены вход, WebSocket или медиасвязь, записи
повреждены либо недоступны, растут ошибки, очереди или потребление ресурсов.
Сначала зафиксируйте время, версии, журналы без секретов и метрики.
Не публикуйте JWT, SDP, секреты, пользовательские данные и подписанные URL.
При отдельном сбое дополнительной функции можно временно отключить её.
Это не заменяет исправление повреждённых данных.

## Предварительные условия

- Сохранены предыдущий `release.json`, его контрольная сумма, digest образов
  в реестре либо проверенный архив с неизменяемыми ID образов.
  Доступны сами образы и защищённая конфигурация окружения.
  Старый коммит не нужно пересобирать.
- Старое приложение проверено с **уже применённой текущей** схемой и форматом
  данных. `release_schema_migrations` проверяет целостность SQL, но не совместимость приложения.
- Нет несогласованной смены образов PostgreSQL, Redis, RabbitMQ, S3 или Coturn.
  Скрипт выпуска намеренно не обновляет и не понижает версии этих зависимостей автоматически.
- Есть проверенная согласованная резервная копия. Отдельно определены допустимые
  потери при восстановлении. Обычный откат приложения не должен приводить к потере данных.
- Назначены оператор и ответственный за решение, согласованы окно обслуживания
  и уведомление пользователей. Новые встречи и записи запрещены, текущие завершаются.

Если совместимость не подтверждена, не устанавливайте поля отчёта evidence
в `true`. Возможны исправление в новой совместимой версии, отдельная миграция
вперёд или аварийное восстановление согласованных БД и объектов. В последнем
случае нужно явно принять потерю изменений после резервного копирования.
Автоматической обратной миграции БД и восстановления рабочего сервера здесь нет.

## Последовательность

1. Приостановите выпуск и зафиксируйте фактический образ каждого сервиса.
   После частичного развёртывания могут одновременно работать разные версии.
   Не удаляйте данные, Docker-тома и каталоги записей.
2. Проверьте предыдущий манифест, подтверждения проверок, совместимость схемы,
   конфигурации и токенов. Дождитесь завершения активных встреч и записей.
   Сохраняйте внешний запрет новой нагрузки и записи данных до конца операции.
3. Выполните `validate` и `rollback` с **предыдущим** манифестом.
   Скрипт получает образы, включает режим завершения работы drain, ждёт нулевую
   активность и проверяет готовность. Действия выполняются последовательно
   для каждого приложения. Миграции не запускаются.
4. Вручную проверьте `/version`, `/version.json`, состояние служб, вход,
   WebSocket, медиасвязь, доступ к прежним файлам и очереди по
   [процессу выпуска](RELEASE_PROCESS.md#проверка-и-продвижение).
   Тестовые аккаунты и конференции автоматически не создаются.
5. Запишите начало и конец операции, простой и результаты. Возвращайте нагрузку
   только после решения оператора и наблюдения по [руководству эксплуатации](operations/README.md).

Пример для staging — проверочного окружения перед выпуском.
Пути должны указывать на реальные проверенные файлы:

```bash
PREVIOUS_MANIFEST=/srv/meet/releases/v1.2.2/release.json
bash scripts/release/release.sh validate --environment staging --project recorder-staging --env-file /srv/meet/config/staging.env --manifest "$PREVIOUS_MANIFEST"
bash scripts/release/release.sh rollback --environment staging --project recorder-staging --env-file /srv/meet/config/staging.env --manifest "$PREVIOUS_MANIFEST"
curl --fail --silent --show-error https://meet-staging.example.org/version
curl --fail --silent --show-error https://meet-staging.example.org/version.json
```

Для рабочего окружения production дополнительно нужно разрешение,
привязанное к **возвращаемой** версии:

```bash
export RELEASE_PRODUCTION_APPROVAL=v1.2.2
bash scripts/release/release.sh rollback --environment production --project recorder-production --env-file /srv/meet/config/production.env --manifest /srv/meet/releases/v1.2.2/release.json --evidence /srv/meet/evidence/rollback-to-v1.2.2.json
unset RELEASE_PRODUCTION_APPROVAL
curl --fail --silent --show-error https://meet.example.org/version
curl --fail --silent --show-error https://meet.example.org/version.json
```

Сравните GET-ответы с точными версией и коммитом возвращаемого манифеста.
Одни эти ответы не подтверждают готовность. Через закрытый доступ проверьте
состояние и готовность каждого изменённого сервиса, отсутствие режима drain,
очереди и метрики. Вход и доступ к материалам проверяйте согласованным существующим
аккаунтом, без автоматического создания пользователей и встреч.
Не разрешайте запись данных до завершения проверок.

Отчёт evidence содержит версию, коммит и SHA-256 **предыдущего** манифеста.
Поля `migrationCompatible`, `backupVerified`, `rollbackReady` и
`applicationRollbackCompatible` получают `true` только после подтверждения.
Поля `approvedBy` и `evidenceReferences` должны быть заполнены.
Полная схема отчёта и границы ручной проверки — в [RELEASE_PROCESS.md](RELEASE_PROCESS.md).

## Если операция остановилась

`RELEASE_DRAIN_TIMEOUT` по умолчанию составляет 300 секунд.
Истечение времени не вызывает принудительный перезапуск: процесс остаётся
в режиме drain. Проверьте активные комнаты, WebSocket-соединения, записи и задания.
Дайте им завершиться, затем повторите согласованную операцию.
Для старого выпуска без маршрута drain нужен отдельный план обслуживания;
обход проверки не предусмотрен.

`resume` возобновляет **ту же** версию после намеренного общего drain.
Команда пересоздаёт процессы: снять drain без перезапуска нельзя.
Она не возвращает другую версию и отказывает при несовпадении установленного образа.
Если все приложения уже используют нужный манифест, но остались в drain,
примените `release.sh resume` с этим манифестом и обычными проверками разрешения.

После аварийного завершения скрипта может остаться каталог блокировки проекта.
Перед удалением именно этого пустого каталога убедитесь, что другой оператор
или CI не выполняет операцию. Не удаляйте каталоги блокировок массово.

Восстановление данных — отдельная процедура [backup-restore.md](operations/backup-restore.md),
а не неявная часть отката.
