# Диагностическая сводка пользовательского приложения

Существующая страница «Состояние сервиса» показывает только безопасные агрегаты.
Она сохраняет прежнее право `users.is_admin`, но **не является административной
панелью**. Это право, пользовательский JWT, роли `owner`/`co_host` и учётная запись
пользователя не дают доступа к управлению администраторами, пользователями,
записями или настройками новой панели.

Новая [административная панель](../ADMIN_DEPLOYMENT_RU.md) использует отдельные
таблицы `administrators`, административные сессии и HTTPS listener `:8081`.
Администратор входит по уникальному логину и паролю, независимо от
пользовательского аккаунта.

## Сохранённое диагностическое право

Миграция `000021_admin_capability.up.sql` добавляет
`users.is_admin BOOLEAN NOT NULL DEFAULT FALSE`. Регистрация по-прежнему создаёт
пользователя без диагностического права. Оператор может назначить его по
**проверенному UUID** через доверенную SQL-консоль:

```sql
UPDATE users SET is_admin = TRUE WHERE id = '<user-uuid>';
```

Для снятия права установите `FALSE`. Сервер проверяет текущее значение PostgreSQL
при каждом запросе диагностической сводки. Выданный JWT не сохраняет отозванное
право. Назначить его через пользовательский запрос или роль встречи нельзя.
Изменения через SQL фиксируйте средствами аудита доступа к БД: эта ручная
операция не становится действием независимого административного аккаунта.

## HTTP-контракт и переход со старого маршрута

Маршруты пользовательского приложения требуют пользовательский Bearer JWT.
Административная cookie не принимается вместо него. Ответы имеют
`Cache-Control: private, no-store` и `X-Content-Type-Options: nosniff`.

- `GET /api/v1/capabilities` возвращает `capabilities.recordingModes` и безопасный
  `buildVersion`. Адреса провайдеров и токены не возвращаются.
- `GET /api/v1/platform/summary` дополнительно требует диагностическое право
  `users.is_admin`. Ответ `item` содержит время снимка, число активных встреч,
  участников и записей, размер очереди, количество отказов за 24 часа,
  состояния API/media-worker и зависимостей PostgreSQL, Redis, RabbitMQ, MinIO.
  Список последних ошибок ограничен десятью кодами. Идентификаторы пользователей
  и конференций, содержимое чата, данные заданий, SDP, пароли и токены отсутствуют.

Прежний сырой endpoint `GET /api/v1/admin/summary` больше не доступен на публичном
API: всё пространство `/api/v1/admin` закрыто ответом `404` независимо от JWT,
cookie и заголовков прокси. Это намеренное изменение API для изоляции новой
админки. Встроенный пользовательский frontend обновлён одновременно и использует
`/api/v1/platform/summary`; существующая страница сводки продолжает работать.
Внешним клиентам старой сводки нужно заменить путь. Перенос не расширяет их права
и не открывает операции новой административной панели через публичный порт.

Отказы нового диагностического маршрута: `401` без пользовательского JWT и `403`
без диагностического права. При ошибке проверки БД запрос закрывается ответом
`500` без подробностей. Счётчики приблизительны во время конкурентных изменений.
Проверка media-worker ограничена 1,5 секунды и не раскрывает внутренний адрес.

Полные версия, коммит и время сборки доступны через `/version` и `/version.json`.
Сверяйте их с манифестом. `buildVersion` API задаётся безопасным `BUILD_VERSION`
при сборке; вне Docker допускается версия Go-бинарника или сокращённый SHA VCS,
а при отсутствии метаданных возвращается `dev`.

## LDAP / Active Directory в административной панели

Подключение корпоративного каталога настраивается в отдельной административной
панели: **Настройки → LDAP / Active Directory**. Пользовательское диагностическое
право, описанное выше, не даёт доступа к этим параметрам.

1. Выберите тип каталога: **Active Directory** или **LDAP (OpenLDAP / LLDAP)**.
   При смене типа форма подставляет соответствующие атрибуты логина, постоянного
   идентификатора, имени и фильтр пользователей. Адрес сервера, DN и пароль
   сохраняются. Проверьте подставленные значения перед сохранением.
2. Укажите адрес сервера, базовый DN, область поиска пользователей и служебную
   учётную запись. `ldaps://` использует TLS, `ldap://` требует STARTTLS.
   При необходимости вставьте доверенный CA-сертификат в формате PEM и ограничьте
   вход членством в выбранной группе. Задайте интервал синхронизации и тайм-аут.
3. Нажмите **«Сохранить изменения»**, затем **«Проверить подключение»**. Проверка
   использует сохранённые параметры и показывает число проверенных записей в
   первой странице поиска (до 500, без подсчёта всего каталога);
   она не импортирует и не изменяет учётные записи. Подключение можно проверить
   до включения корпоративного входа.
4. Включите LDAP, сохраните настройки и нажмите **«Синхронизировать сейчас»**.
   Задание выполняется в фоне. В блоке проверки отображаются состояние,
   последний запуск, последняя успешная синхронизация и число найденных,
   добавленных, обновлённых и отключённых пользователей. При включённом LDAP
   последующие запуски происходят с заданным интервалом.

Пароль служебной учётной записи не возвращается в форму. Пустое поле при
сохранении оставляет прежний пароль. Проверка и запуск синхронизации недоступны
при несохранённых изменениях. Если другой администратор изменил конфигурацию,
обновите её перед повторным действием. Кнопка **«Обновить статус»** обновляет
результат вручную; автоматический опрос выполняется только для ожидающего или
работающего задания на открытой вкладке LDAP.

При включённом LDAP на странице входа и в форме добавления аккаунта появляется
выбор **«Корпоративный вход»**. Пользователь вводит логин каталога и свой
корпоративный пароль. Вход **«По email»** остаётся доступным для локальных
аккаунтов. Неверный корпоративный пароль не переключает попытку входа на
локальную авторизацию.

В профиле LDAP-пользователя имя и email управляются каталогом; аватар можно
менять в MeetSpace. Для изменения пароля или удаления корпоративной учётной
записи пользователь обращается к администратору организации. Правила
синхронизации, TLS и проверки совместимости описаны в [руководстве LDAP](../LDAP.md).
