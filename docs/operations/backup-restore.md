# Резервная копия и проверка восстановления

> При обновлении старой установки сначала выполните [переход на record-worker и миграцию 000037](speech-removal-upgrade.md). Миграция необратимо удаляет данные функций речи; требуются проверенная резервная копия и остановка старых процессов. Простой откат образов после неё не поддерживается.

Сохраняются логический дамп PostgreSQL и **текущие версии** объектов одного
настроенного бакета S3. Окружение разработки/classic использует MinIO;
текущий hardened и отдельная установка через мастер — SeaweedFS под именем службы
`minio` и с параметрами `MINIO_*`. Это не атомарный снимок двух хранилищ:
для согласованности на время копирования нужно остановить все операции изменения
данных. Создание копии без проверки восстановления не подтверждает её пригодность.

## Что входит и что не входит

| Данные | Покрытие |
| --- | --- |
| PostgreSQL | `pg_dump` в формате custom, схема, данные и журнал миграций; без владельцев и ACL |
| S3 (MinIO/SeaweedFS) | Текущий ключ объекта, содержимое, размер, SHA-256 и `ContentType`; приватность проверяется при восстановлении |
| Выпуск | Копия `release.json`, его хеш, версия, коммит и время резервного копирования |
| История S3 | Идентификаторы версий, старые версии, маркеры удаления, теги и произвольные метаданные не переносятся |
| Настройки инфраструктуры | IAM/ACL, жизненный цикл, репликация, конфигурация политики бакета, TLS, env-файлы, секреты и Grafana не архивируются этим скриптом |
| Обмен событиями в реальном времени | Статусы присутствия, права владения и PubSub Redis не восстанавливаются из старого состояния |
| RabbitMQ и рабочий каталог записи | Полное состояние брокера и незавершённые фрагменты не входят в копию; для них нужен отдельный план согласованного сохранения |

Для аварийного восстановления отдельно сохраняйте проверенные настройки,
учётные данные, ключ шифрования токенов провайдеров, TLS, политики инфраструктуры и нужные
операционные данные в защищённом хранилище. Дамп содержит личные данные, сообщения
и зашифрованные токены провайдеров. Для чтения последних нужен
исходный `PROVIDER_TOKEN_ENCRYPTION_KEY`; потеря ключа не устраняется восстановлением БД.
Срок хранения/удаления, RPO/RTO и доступ к резервным копиям утверждает владелец системы:
проект не устанавливает юридическую политику автоматически.

## Сначала выберите установленный Compose-контекст

`scripts/release/backup.sh` и `restore-check.sh` используют `common.sh` с
дополнительными файлами classic/shared-host и ограничениями имён проектов. Они не подключают
`config/compose.json` и `config/turn.yml`, созданные `install.sh`.
Указание только `meetspace.env` для скрипта не делает его совместимым с
установкой мастером. Полная матрица —
[DEPLOYMENT.md](../DEPLOYMENT.md#выбор-процедуры-по-типу-установки).

Для отдельной установки через мастер используйте процедуру ниже с её функцией
`compose`; для общего процесса выпуска — `backup.sh` и `restore-check.sh`.
Формат логической копии одинаков, S3-хранилище определяется настройками клиента.
Нельзя напрямую восстанавливать файловый том MinIO в SeaweedFS и наоборот.

## Подготовка согласованной резервной копии

1. Выберите новый абсолютный путь к каталогу вне Git. Защитите родительский
   каталог, проверьте свободное место и подготовьте шифрование и перенос копии
   на другой сервер. Скрипт использует `umask 077`, но сам копию не шифрует.
2. Зафиксируйте установленный манифест и конфигурацию. Запретите параллельные
   развёртывание, миграции и обслуживание на всё окно. Резервное копирование
   и проверка восстановления удерживают общую блокировку проекта только во время
   своей операции, но не между отдельными этапами завершения работы, копирования и возобновления (drain/backup/resume).
3. Ограничьте новую нагрузку во внешнем прокси или балансировщике, уведомите
   пользователей и завершите встречи и записи. Прекратите новые `record.start`
   и дождитесь обработки ожидающих запусков и завершения записей, пока штатная
   остановка через API ещё доступна. Только затем включите общий режим завершения
   работы и убедитесь, что активных операций нет. `active=0` не подтверждает пустоту
   очереди: сервис записи в этом режиме возвращает запуск в очередь с задержкой
   250ms, что может задержать остановку. Остановка composite сохраняется в SQL,
   но завершение обработки всё равно нужно проверить. Учтите прямое изменение
   БД/MinIO, загрузки по подписанным ссылкам, внешние задания cron и административные
   операции: режим завершения процесса не запрещает им менять данные.
4. Проверьте завершение записи, финализации, загрузок и фоновых заданий.
   Ожидающие команды RabbitMQ не сохраняются этой копией. Не разрешайте изменение
   данных до успешного завершения копирования обоих хранилищ.
5. Только после этой проверки установите `RELEASE_BACKUP_QUIESCED=1`. Переменная —
   утверждение оператора; скрипт не способен доказать глобальную остановку записи.

## Общий процесс выпуска

Пример для проверочного стенда (из корня репозитория); только для соответствующей топологии:

```bash
INSTALLED_MANIFEST=/srv/meet/releases/v1.2.3/release.json
BACKUP_DIRECTORY="/srv/meet/private-backups/$(date -u +%Y%m%dT%H%M%SZ)"
bash scripts/release/release.sh drain --environment staging --project recorder-staging --env-file /srv/meet/config/staging.env --manifest "$INSTALLED_MANIFEST"
export RELEASE_BACKUP_QUIESCED=1
bash scripts/release/backup.sh --environment staging --project recorder-staging --env-file /srv/meet/config/staging.env --manifest "$INSTALLED_MANIFEST" --output "$BACKUP_DIRECTORY"
unset RELEASE_BACKUP_QUIESCED
bash scripts/release/release.sh resume --environment staging --project recorder-staging --env-file /srv/meet/config/staging.env --manifest "$INSTALLED_MANIFEST"
```

`resume` выполняют после успешного резервного копирования, если нужно вернуть тот
же выпуск. При подготовке миграции или развёртывания сохраняют окно обслуживания.
В рабочем окружении `drain` и `resume` дополнительно требуют разрешение
на конкретную версию и
`--evidence` из [RELEASE_PROCESS.md](../RELEASE_PROCESS.md). Сам `backup.sh`
проверяет целевое окружение, манифест и флаг приостановки изменения данных,
но не требует разрешения на выпуск в рабочее окружение:
это не отменяет организационное согласование окна и запрет конкурентных операций.
Все операторы должны использовать один `RELEASE_LOCK_DIR` на выбранном Docker-хосте.

Каждый PostgreSQL-подпроцесс ограничен `RELEASE_DATABASE_TIMEOUT` (по умолчанию
600 секунд), `pg_dump` дополнительно использует `--lock-wait-timeout=5s`.
Лимит действует отдельно на создание БД, восстановление, дамп и проверку журнала
миграций, а не на всю процедуру сразу. Операции с объектами имеют отдельный срок.
При превышении лимита скрипт останавливается и не объявляет копирование или
восстановление успешным. Изменение лимита должно опираться на замер объёма данных
и согласованное окно обслуживания.

Выход: `postgres.dump`, `objects/manifest.json` и файлы объектов, `release.json`,
`backup.json`. Последний содержит SHA-256 дампа и манифеста объектов и
`restoreVerified:false`; он не превращается автоматически в `true` при проверке.
Неполный каталог после ошибки не используйте как готовую копию. Сохраните его
для диагностики либо удалите адресно после решения оператора.

## Резервная копия установки через мастер

В оболочке с правами root задайте функцию `compose` из
[DEPLOYMENT.md](../DEPLOYMENT.md#compose-контекст-установки-мастером) с фактическими
именем проекта и путём. Приостановите изменение данных и завершите активную работу
по инструкции выше. Общая блокировка скрипта выпуска здесь не используется:
на всё окно обеспечьте единственного
оператора и запрет параллельных обслуживаний. Только после прекращения всех
записей выполните блок, выбрав новый каталог:

```bash
(
  set -eu
  umask 077
  BACKUP_DIRECTORY="/var/backups/meetspace/$(date -u +%Y%m%dT%H%M%SZ)"
  INSTALLED_MANIFEST=/opt/meetspace/bundle/release/release.json
  test ! -e "$BACKUP_DIRECTORY"
  mkdir -p "$BACKUP_DIRECTORY"
  cp "$INSTALLED_MANIFEST" "$BACKUP_DIRECTORY/release.json"
  compose exec -T postgres timeout 600 sh -ec \
    'PGPASSWORD="$POSTGRES_PASSWORD" exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom --no-owner --no-acl --lock-wait-timeout=5s' \
    > "$BACKUP_DIRECTORY/postgres.dump"
  test -s "$BACKUP_DIRECTORY/postgres.dump"
  compose run --rm --no-deps --user "$(id -u):$(id -g)" \
    --entrypoint /app/object-backup -v "$BACKUP_DIRECTORY:/backup" \
    api backup --dir /backup/objects
  jq -n \
    --arg version "$(jq -er .version "$INSTALLED_MANIFEST")" \
    --arg commit "$(jq -er .commit "$INSTALLED_MANIFEST")" \
    --arg releaseSHA "$(sha256sum "$BACKUP_DIRECTORY/release.json" | cut -d ' ' -f1)" \
    --arg databaseSHA "$(sha256sum "$BACKUP_DIRECTORY/postgres.dump" | cut -d ' ' -f1)" \
    --arg objectsSHA "$(sha256sum "$BACKUP_DIRECTORY/objects/manifest.json" | cut -d ' ' -f1)" \
    --arg createdAt "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
    '{schemaVersion:1,version:$version,commit:$commit,releaseManifestSHA256:$releaseSHA,databaseSHA256:$databaseSHA,objectsManifestSHA256:$objectsSHA,createdAt:$createdAt,scope:"quiesced PostgreSQL and current object versions",restoreVerified:false}' \
    > "$BACKUP_DIRECTORY/backup.json"
)
```

Этот блок повторяет логические шаги скрипта с правильными файлами Compose
отдельной установки. Проверка `RELEASE_BACKUP_QUIESCED` в нём не выполняется:
за приостановку изменения данных отвечает оператор. Время ожидания утилиты S3
по умолчанию — 1 час; отдельный `--timeout` должен
быть положительным и не больше 24 часов. При ошибке блок прерывается, частичная
копия не считается завершённой. Успешный `backup.json` сохраняется последним.

Отдельно защищённо сохраните `config/`, `secrets/`, `certs/`, `installation.json`,
`manage.sh`, манифест, пакет выпуска и исходный ключ шифрования провайдеров,
если он настроен.
Эти материалы содержат секреты; храните их шифрованными вне исходного хоста.
Каталог `storage/` и RabbitMQ нужны отдельно, если в согласованную точку входят
незавершённые работы; их копия не заменяет PostgreSQL/S3. После успешной копии
возобновите **те же** образы и конфигурацию по руководству по эксплуатации либо
сохраните запрет изменения данных для последующего обновления. `manage.sh`
не предоставляет команды резервного копирования и обновления.

## Изолированная проверка восстановления

В примере ниже замените `BACKUP_ID` на каталог готовой резервной копии.

Целевое окружение — отдельный локальный или проверочный стенд с работающими
PostgreSQL и S3, достаточным местом, подходящей версией PostgreSQL и совместимым
манифестом выпуска. Нельзя направлять проверку в рабочее окружение: скрипт это
запрещает. Он создаёт новые БД и бакет, не перезаписывая рабочие данные.
Наличие проверочного стенда само по себе не разрешает использовать его зависимости
для восстановления: назначьте отдельный проект и env-файл с независимыми данными.

```bash
bash scripts/release/restore-check.sh --environment staging --project recorder-staging-restore --env-file /srv/meet/config/restore.env --manifest /srv/meet/releases/v1.2.3/release.json --backup /srv/meet/private-backups/BACKUP_ID
```

Приведённый `restore-check.sh` запускают из совместимой рабочей копии общего
процесса выпуска с **целевыми**, а не исходными дополнительными файлами Compose.
Он может прочитать описанную выше логическую копию отдельной установки, но не
меняет работающие службы исходного сервера. Если целевое окружение — отдельная
установка через мастер, нужен её Compose-контекст и ручное выполнение тех же
шагов: проверка хешей, создание новой БД, `pg_restore`, проверка журнала миграций,
создание пустого бакета S3 и `object-backup restore`. Совместимость политик S3
и условной записи проверяют при фактическом восстановлении.

Для локальной репетиции допустим `--environment local --project
recorder-release-rehearsal-restore` с собственным `.env.local` и отдельными
портами/хранилищами. `restore-check.sh` сам зависимости не поднимает: сначала
подготовьте целевое окружение согласно [DEPLOYMENT.md](../DEPLOYMENT.md), исключив пересечение
портов с другими стендами.

Проверка включает:

- Проверку хешей дампа, манифеста объектов и скопированного `release.json`
  по `backup.json`, а также совпадения версии и коммита исходного манифеста.
- `pg_restore --exit-on-error --single-transaction` в новую БД;
  полный повторный дамп для чтения каталога и непустой `release_schema_migrations`.
- Восстановление объектов в новый бакет без перезаписи существующего ключа,
  проверку размеров, контрольных сумм и закрытой политики бакета.
- Для непустого бакета — чтение первого объекта по подписанному URL и запрет
  анонимного GET. Для пустого бакета записывается `signedAccessVerified:false`:
  скачивание в этом случае не проверено.

Отчёт `restore-check-<timestamp>_<pid>.json` сохраняется рядом с резервной копией. Он
содержит хеши исходного и целевого манифестов выпуска, имена созданных БД и бакета,
числа объектов/миграций, длительности этапов
и результаты проверок. `productionRPO`/`productionRTO` остаются `null`: локальные
секунды — не гарантия восстановления рабочего окружения. Не меняйте исходный
манифест резервной копии, чтобы добавить неподтверждённые утверждения.

Тестовые БД и бакет **сохраняются**, в том числе при частичном отказе. Осмотрите
их и отчёт, затем удаляйте только записанные точные имена после согласования.
Автоматической очистки по префиксу и команды удаления всех томов нет.

## Пределы проверки и аварийное восстановление

Хеш подтверждает целостность относительно манифеста, но не доверие к его источнику.
Храните защищённый манифест отдельно от потенциально изменяемой копии.
Проверка восстановления не охватывает все связи между PostgreSQL и ключами
объектов, не запускает восстановленное приложение на временной БД и не воспроизводит
каждую запись. После неё отдельно сопоставьте файлы, записи и чаты. Проверьте
доступ, просмотр MP4/JPEG и ZIP для соответствующего режима, авторизацию
и отсутствие утечек между пользователями.

Для реального восстановления оператор утверждает точку данных и допустимую
потерю изменений, сохраняет текущее повреждённое состояние для разбора, готовит
новое изолированное окружение, восстанавливает PostgreSQL, объекты, конфигурацию
и ключи, проверяет приложение и только затем переключает трафик. Повторную
доставку сообщений брокера, повторы заданий и права владения активными сессиями
рассматривают отдельно. Копия PostgreSQL без согласованных объектов и наоборот
не обеспечивает согласованного восстановления. Нельзя использовать тренировочную
команду для скрытой перезаписи данных рабочего окружения.
