# Эксплуатация MeetSpace

> При обновлении старой установки сначала выполните [переход на record-worker и миграцию 000037](speech-removal-upgrade.md). Миграция необратимо удаляет данные функций речи; требуются проверенная резервная копия и остановка старых процессов. Простой откат образов после неё не поддерживается.

Руководство по эксплуатации на одном сервере Docker Compose: проверка служб, сеть, управление
нагрузкой, диагностика, резервное копирование и восстановление.

Для установки через `install.sh` используйте `manage.sh` и её полный
[Compose-контекст](../DEPLOYMENT.md#compose-контекст-установки-мастером). Общие
скрипты выпуска выбирают classic/shared-host и автоматически не читают
`config/compose.json` и `config/turn.yml` мастера. Обновление отдельной установки требует
плана с сохранением её томов, сети, прокси, TURN и образов. `--resume` продолжает
установку, но не обновляет приложение.

Сборка для разработки описана в [корневом README](../../README.md). На сервере
выпуска используются закреплённые образы и `AUTO_MIGRATE=false`. Миграцию запускают
отдельно до развёртывания, а не изменяют схему при старте приложения.
Применённые SQL-файлы и комментарии в них не редактируют: журнал миграций
проверяет точное содержимое файлов.
В частности, индексы `000021_admin_capability.up.sql` требуют замера времени и
блокировок на репрезентативной копии, а не предположения по локальному запуску.

Внутренний транспорт на одном доверенном Compose-хосте — HTTP/AMQP/Redis без
TLS, не опубликованный наружу. Между отдельными хостами нужны TLS/mTLS/VPN и
отдельная проверка безопасности. Значения CPU/RAM в Compose — начальные защитные
ограничения, а не результат расчёта производительности рабочего окружения.

## Порты и границы сети

| Назначение | Порт | Доступ |
|---|---|---|
| HTTPS/WSS | 443/TCP | Браузеры → Nginx |
| API | 8085/TCP | Только Compose/LB внутри доверенной сети |
| Управление media-worker | 8091/TCP | Только API/recorder, служебный секрет Bearer |
| Управление сервисом записи | 8090/TCP | Внутренняя сеть, служебный секрет Bearer |
| product-worker | 8092/TCP | Проверка состояния и управление только внутри сети |
| SFU ICE mux | 50010/UDP и TCP по умолчанию | Публичное назначение `MEDIA_NAT_IPS`, прямой RTP |
| TURN | 3478/UDP + TCP | Браузеры → Coturn |
| TURNS | 5349/TCP | Резервное подключение по TLS, отдельный действительный сертификат |
| TURN relay | 49160–49259/UDP по умолчанию | Coturn → SFU; диапазон должен совпадать с правилами межсетевого экрана |
| PostgreSQL / Redis / Rabbit / S3 | 5432 / 6379 / 5672 / 9000 | Не опубликованы в рабочем окружении |
| ACME | 80/TCP | Выпуск/продление Let’s Encrypt в установке мастером; постоянного перенаправления с HTTP нет |
| Metrics / pprof | `/metrics` / loopback `PPROF_PORT` | Метрики требуют Bearer; pprof выключен по умолчанию |

RTP не проходит через обратный HTTP-прокси. Резервное подключение по TCP означает
TCP между браузером и TURN; участок TURN→SFU обычно остаётся UDP. Не закрывайте
этот внутренний UDP-маршрут. Настройте перенаправление мультиплексированного порта
SFU через NAT в соотношении 1:1, без изменения внешнего порта.
При использовании `MEDIA_UDP_MIN_PORT/MAX_PORT` вместо одного порта явно задайте
соответствующий диапазон в Compose и межсетевом экране. Пример рабочего
окружения использует один мультиплексированный порт.

В рабочем окружении Coturn запрещает адреса узлов из частных, loopback,
link-local и multicast-диапазонов, чтобы не стать прокси к внутренним сервисам. Если TURN и SFU на одном хосте и
hairpin NAT недоступен, разрешите **только конкретный** адрес SFU через
`allowed-peer-ip`, а не всю частную подсеть CIDR. Тестовый стенд имеет отдельные
послабления для loopback; его конфигурацию нельзя использовать в рабочем окружении.

По умолчанию `HTTP_TRUSTED_PROXIES` пуст: адреса из заголовков прокси не считаются
достоверными. В рабочем окружении задайте только фактические IP/CIDR Nginx или
балансировщика. Иначе ограничитель запросов по IP может считать весь трафик
запросами одного клиента-прокси. Для внешнего балансировщика согласуйте цепочку
доверия. В примере Nginx сам устанавливает `X-Forwarded-For=$remote_addr`.

## TURN и ICE

`GET /api/v1/webrtc/config` доступен только с пользовательским JWT. Ответ содержит
`iceServers`, `iceTransportPolicy` и время Unix `expiresAt`, но не общий секрет.
Имя пользователя имеет вид `expiry:random UUID`; пароль — Base64(HMAC-SHA1(shared secret, username)),
совместимый с [Coturn REST](https://github.com/coturn/coturn/blob/master/README.turnserver).
Это не алгоритм хеширования паролей пользователей. TTL по умолчанию 10 минут,
допустимый диапазон 1–60 минут. Часы API/media-worker/Coturn должны быть
синхронизированы. Для нового или пересозданного PeerConnection браузер получает новые
учётные данные через `media.joined`. Автоматического перезапуска ICE или обновления
учётных данных TURN в уже активном PeerConnection пока нет. Для длительных встреч
проверьте полный цикл продления выделенного TURN-соединения в целевой сети.

ICE-кандидат `host` — локальный адрес, `srflx` — адрес после STUN/NAT, `relay` —
выделенный Coturn адрес. При диагностике смотрите **выбранную** пару, а не только
наличие кандидата relay. `TURN_FORCE_RELAY=true` применяется к новым соединениям.
Общий секрет никогда не передаётся браузеру. При ротации ключа согласуйте
перекрытие старого/нового секрета на Coturn и TTL на API, иначе новые подключения
или продление соединений могут прекратиться. Синхронная ротация без перекрытия — операция с
возможным разрывом соединения, не бесшовная.

При `401/438` проверьте часы, общий ключ, realm, TTL и URI транспорта. При истечении
времени ожидания проверьте DNS, порты 3478/5349, диапазон ретрансляции, публичный
адрес, Docker NAT и разрешённый маршрут relay→SFU. TURNS требует доверенную цепочку и соответствие имени
сертификата. Принудительный режим ретрансляции проверен локально по UDP/TCP; WAN, мобильная и
корпоративная сети, реальный TLS сертификат проверяются оператором отдельно.

## Проверка состояния и завершение работы

`/health/live` отвечает 200, пока процесс работает; сбой БД не меняет этот признак.
`/health/ready` отвечает 200 или 503. Пробы выполняются каждые 2 секунды с общим
предельным временем 1 секунда, а не при каждом запросе состояния. Тексты ошибок/адреса/ключи
не публикуются. Готовность API зависит от PostgreSQL, Redis, RabbitMQ и MinIO; media — от Redis
и права владения комнатой; recorder/compositor — от PostgreSQL, Redis, потребителя
RabbitMQ, MinIO и локального диска. Компонент композиции встроен в сервис записи
и не имеет отдельного процесса или порта проверки состояния.
Product Worker проверяет PostgreSQL. Эти проверки не подтверждают
работоспособность внешних провайдеров.

Для установки мастером сначала задайте функцию `compose` из
[DEPLOYMENT.md](../DEPLOYMENT.md#compose-контекст-установки-мастером), затем
выполняйте только строки `compose ps`/`compose exec` ниже.

Следующий блок предназначен для общего процесса выпуска. Запустите отдельный Bash
из корня рабочей копии после выбора **установленного** манифеста. Вспомогательный
скрипт читает env-файл как данные Compose, не исполняет его как shell-код
и не выводит конфигурацию с секретами:

```bash
bash
source scripts/release/common.sh
parse_release_args --environment production --project recorder-production --env-file /srv/meet/config/production.env --manifest /srv/meet/releases/v1.2.3/release.json
validate_release
compose ps
compose exec -T api wget -qO- http://127.0.0.1:8085/health/ready
compose exec -T media-worker wget -qO- http://127.0.0.1:8091/health/ready
compose exec -T record-worker wget -qO- http://127.0.0.1:8090/health/ready
compose exec -T product-worker wget -qO- http://127.0.0.1:8092/health/ready
```

Замените пути и версию на фактические. Для локального и проверочного окружений выберите отдельные проект,
env-файл и манифест. После диагностики `exit` закрывает этот Bash. Команды только
читают состояние и не заменяют разрешение на развёртывание, миграцию,
завершение работы или возобновление служб.

Перед заменой процесса скрипт выпуска вызывает закрытый `/operations/drain`,
запрещает новую работу и ждёт `active=0`. В счётчик входят прикладные HTTP и
работа конкретного сервиса: WebSocket, комнаты, записи или задания. При истечении
времени ожидания процесс остаётся в режиме завершения работы (draining);
принудительного перезапуска нет. Для возврата к готовности процесс пересоздают
через `resume` с тем же манифестом. Ограничьте новую нагрузку и на внешнем балансировщике.
SIGTERM включает режим завершения и снимает признак готовности. API перестаёт
принимать новые запросы и закрывает переданные обработчикам WebSocket-соединения,
media освобождает комнаты, PeerConnection и права владения, а сервис записи
завершает обработку в отведённое время. `SHUTDOWN_TIMEOUT=20s`, Compose
даёт 45s на штатную остановку. После этого срока процесс может завершиться без полной финализации,
закрытые фрагменты сохраняются. Бесшовный перенос активных комнат между SFU не реализован: при замене media-worker
нужны повторное подключение, новый билет подключения и новые PeerConnection.
Redis PubSub не хранит историю; после повторного подключения клиент получает
снимок состояния и историю через HTTP.

### Возобновление отдельной установки после завершения активной работы

В установке мастером используйте её функцию `compose`, не `release.sh resume`.
Перед перезапуском завершите встречи/записи и фоновые работы, включите режим завершения работы (drain) и
проверьте `draining=true`, `active=0` у всех заменяемых процессов. Управляющий
POST и GET для API выполняются внутри контейнера без вывода секрета:

```bash
compose exec -T api sh -c 'wget -qO- --post-data="" --header="Authorization: Bearer $METRICS_SECRET" http://127.0.0.1:8085/operations/drain'
compose exec -T api sh -c 'wget -qO- --header="Authorization: Bearer $METRICS_SECRET" http://127.0.0.1:8085/operations/drain'
```

Повторите для служб и портов `media-worker:8091`, `record-worker:8090`,
`product-worker:8092`. Только после нулевой активности,
проверки очередей и завершения резервного копирования или обслуживания верните
те же ID образов:

```bash
compose up -d --no-build --no-deps --force-recreate --wait --wait-timeout 240 \
  media-worker record-worker product-worker api frontend
```

Этот блок возобновляет установленную версию: он не собирает новый выпуск и не
обновляет инфраструктуру. Если env/образы уже менялись, сначала сверяйте план
обновления. Повторно проверьте готовность и версию, очереди и пользовательские
сценарии, затем снимайте внешнее ограничение нагрузки. Перезапуск SFU прерывает
соединения, поэтому его выполняют после завершения встреч.

До перевода сервиса записи в режим завершения прекратите новые `record.start`
и дождитесь обработки уже ожидающих запусков. Сопоставляйте очередь и Outbox
со статусами записей. Активные записи остановите штатно и дождитесь финализации.
Сделайте это до перевода API в режим завершения: в нём API отклоняет новые
прикладные запросы.
`active=0` — счётчик процесса, не доказательство пустой Rabbit-очереди.
В режиме завершения потребитель возвращает новые команды запуска в очередь
через `Nack(requeue=true)` с паузой 250ms. Запуск и остановка используют одну очередь:
повторяемая команда запуска может задерживать остановку. Отдельной очереди
повторных попыток или приоритета остановки пока нет.
У composite остановка сохраняется в SQL и замечается владельцем при опросе,
но это не заменяет проверку завершения. Если активность сохраняется, по истечении времени ожидания
развёртывание прекращается, а процесс остаётся в режиме завершения работы.
Не обходите эту защиту принудительным перезапуском.

## Диагностика и метрики

Журналы JSON содержат `service`, `instance_id` и `event_type`. HTTP-запрос получает
UUID в `X-Request-ID`; внутренние команды медиа и сообщения RabbitMQ сохраняют
идентификатор связи там, где это применимо. Для медиасообщений WebSocket таким
идентификатором служит UUID конверта, а не идентификатор начального HTTP-запроса.
Идентификаторы сущностей допустимы в ограниченных журналах, но **не** в метках
метрик. Запись SQL-запросов отключена, чтобы не сохранять текст чата.
Не включайте в журналы SDP, JWT, билеты подключения, параметры ссылок загрузки
и скачивания или содержимое чата.

`/metrics` без `Authorization: Bearer METRICS_SECRET` возвращает 404. Публичный
Nginx рабочего окружения закрывает доступ к метрикам, внутреннему управлению,
отладке, проверке состояния и завершению работы. `release.sh
deploy` запускает профиль наблюдаемости из того же неизменяемого манифеста.
Отдельная пересборка или запуск изменяемых образов мониторинга не нужны.

Заранее сохраните токен в `METRICS_TOKEN_FILE`, совпадающий с METRICS_SECRET.
Для classic-варианта нужен отдельный пароль Grafana в `GRAFANA_PASSWORD_FILE`.
Мастер создаёт токен автоматически; hardened не запускает Grafana. Храните файлы
вне Git и предоставьте доступ пользователю контейнера. Не сохраняйте секреты
в панелях мониторинга или YAML Prometheus. Prometheus доступен только на loopback
19090, Grafana classic — на 13001; подключайтесь через SSH-туннель.
`dockers/observability/` содержит начальную панель мониторинга и правила оповещений.
Порог БД 18 рассчитан на пул из 20 соединений; при изменении пула скорректируйте
правило. Общие пороги CPU/RAM настройте под роль службы. Доставка через
Alertmanager не настроена: подключите собственный канал уведомлений.

Основные серии: `recorder_http_requests_total{route,method,status}` (401/403 auth,
429 limits), `recorder_http_duration_seconds`, `recorder_ws_active`,
`recorder_ws_messages_total{class}`, `recorder_dependency_up{dependency}`,
`recorder_events_total{event}`, `recorder_work_duration_seconds{operation}`,
`recorder_state{resource}`, сборщики Go и процесса. Route содержит шаблон маршрута, а не URL с ID.
State содержит состояние пула БД, медиакомнат, подключений, дорожек, подписок
и RTP, активных записей и FFmpeg, свободное место и последнюю задержку очереди.
Счётчики SFU представлены как снимки монотонных значений gauge и обнуляются
при перезапуске. При использовании `increase` учитывайте этот сброс.
Число неудачных проверок зависимости не равно числу всех ошибочных запросов к ней. `media_relay_total` / `media_direct_total` учитывают
первую выбранную пару физического подключения: TURN на любой стороне — relay,
host/srflx/prflx — direct. Это не статистика переключений пары внутри одного PC.
Общее число ожидающих и находящихся в сети пользователей, а также длина очереди
RabbitMQ пока не экспортируются. Длину очереди смотрите в брокере.

Продуктовые задания имеют `recorder_product_queue`, `recorder_product_jobs_total`
и метрики провайдеров. Они не показывают длину очереди RabbitMQ. Необязательная
телеметрия интерфейса добавляет
`recorder_client_errors_total{code,browser,route}` с ограниченными значениями;
она не содержит пользовательский контент и не измеряет всех пользователей:
отключение функции, ограничения частоты и ошибки доставки уменьшают наблюдаемую выборку.

Pprof: `PPROF_PORT=0` по умолчанию; ненулевой порт слушает `127.0.0.1` **внутри**
контейнера. Не публикуйте порт и не добавляйте публичный маршрут прокси. Временный
административный доступ выполняйте через `docker compose exec`/внутреннее пространство имён. Сервер отклоняет
`seconds` вне (0,60], включая NaN/Inf; ограничивайте запросы 30–60 секундами.
Отключите порт после диагностики.

## Лимиты и хранилище

Лимит физических WebSocket-соединений — 1000 на процесс. Ограничения очереди,
сообщений, SDP и ICE задаются через `WS_*`. Для SFU используются:
`MEDIA_MAX_PEERS/ROOMS/PUBLISHED_TRACKS/AUDIO_TRACKS/VIDEO_TRACKS/SCREEN_SHARERS`,
очереди RTP и предельное время операций — `MEDIA_*`. Для сервиса записи: `RECORDING_MAX_ACTIVE`,
`RECORDING_FFMPEG_CONCURRENCY`, `MAX_DURATION`, `MAX_MIB`, `DISK_RESERVE_MIB`.
Прежний прямой приём потока также ограничен MaxActive. Максимальный JSON — 1 МиБ,
время чтения API — 60s. Маршрут загрузки имеет отдельный лимит 10 МиБ и собственный
срок выполнения. У SSE/WS отдельные сроки heartbeat и записи, поэтому общий
HTTP WriteTimeout не используется.

Шаблон пула PostgreSQL: 20 открытых и 10 простаивающих соединений,
срок жизни — 30m. Текущий мастер задаёт 10 открытых и 2 простаивающих.
Перед настройкой оповещений сверяйте фактические DB_MAX_OPEN/DB_MAX_IDLE.
Подключение ограничено 5s, запрос — 10s, ожидание блокировки — 5s.
Миграция использует отдельные транзакцию и advisory lock,
`lock_timeout=15s` и срок выполнения 5 минут. Не увеличивайте лимит всех
пользовательских запросов ради DDL: тяжёлую миграцию проектируйте и проверяйте отдельно.
Для Redis подключение, чтение, запись и ожидание пула ограничены 3s; поддерживается
отмена контекста. RabbitMQ: heartbeat 5s, ограниченное время подключения,
подтверждение публикации и переподключение, QoS потребителя — 1 с переподключением.
Команда доставляется повторно один раз, затем попадает в сохраняемую очередь
`.failed` (7 суток, 10000 сообщений и 64 МиБ). Повторный запуск или остановка
должны оставаться идемпотентными. Ошибки бизнес-логики также проходят повторную
попытку и карантин. Не переотправляйте очередь неудачных сообщений вслепую:
сначала устраните причину и проверьте состояние record в PostgreSQL.

Для оповещений о накоплении очереди подключите собственный интерфейс управления
или экспортёр RabbitMQ в закрытой сети. Следите за messages_ready/unacknowledged,
consumers=0 и возрастом команды.
Начальный рекомендационный порог messages_ready>100 в течение 5m требует
пересмотра по длительности записей и нагрузке; он не включён как «работающий»
правило Prometheus без соответствующей серии и экспортёра.

В окружении разработки/classic работает MinIO; в hardened и текущей установке
через мастер — SeaweedFS под тем же именем службы `minio` и `MINIO_*`. S3-клиент общий,
но форматы томов различаются: подключать том данных MinIO к SeaweedFS нельзя.
`S3_MAX_VOLUMES=16` — значение SeaweedFS по умолчанию; начальный скрипт задаёт размер тома
128 МиБ; ёмкость планируется отдельно от размера диска хоста.

Операции S3 имеют ограниченное время сетевых запросов и число повторов SDK.
Загрузка ограничена 10m; размер сохранённого объекта проверяется. При неполном
завершении composite выполняется попытка удалить префикс token, не зафиксированный
в БД, с лимитом 5s. При недоступности хранилища очистка может не завершиться.
Перед удалением сверяйте оставшиеся объекты с PostgreSQL. Повторная загрузка по
одному ключу идемпотентна; статус ready устанавливается только после подтверждения
готовых файлов. Бакет закрыт: не включайте анонимный доступ. Ссылки имеют срок
действия и проверку прав.

FFmpeg вызывается напрямую, без shell. Новые обёртки выполнения сохраняют
не более 64 КиБ вывода. При отмене отправляется SIGTERM, через 3s — SIGKILL.
Прежняя штатная остановка сначала отправляет `q`, затем TERM/KILL с ограниченным
ожиданием. Параметр контейнера `init: true` помогает корректно завершать дочерние
процессы. Входные кодеки — VP8/Opus. Режимы composite/screen_focus создают
MP4 с H.264/AAC и превью JPEG; audio_only — AAC в MP4 без превью;
individual_tracks — аудио MP4 и ZIP исходных IVF/OGG с манифестом.
Установленный FFmpeg должен содержать libvpx/libx264/libopus/AAC. Конференционный путь: SFU → HTTP NDJSON egress →
recorder → FFmpeg → S3; RabbitMQ передаёт команды, а не RTP.
Недостаток места снимает признак готовности, но не ограничивает полностью размер
уже выполняющейся записи. Следите за диском и заранее прекращайте приём новой нагрузки. Приложение не удаляет чужие
или неопознанные каталоги при запуске; закрытые фрагменты нужны для восстановления.
Composite очищает рабочий каталог после загрузки и фиксации статуса ready, если
`RECORDING_KEEP_LOCAL=false`. Артефакты сохраняются под
`recordings/{conferenceId}/{recordId}/artifacts/{token}/`; устаревшие ключи
`records/{recordId}/final.mp4` не описывают текущий конференционный путь.

## Аварии и восстановление

[Матрица отказных проверок](FAILURE_TESTS.md) описывает, как проверить
восстановление на изолированном стенде.

При ошибке записи не подменяйте её статус успешным. Проверьте готовность
record-worker, lease/token, свободное место, сохранённые фрагменты, stderr FFmpeg,
MinIO и Outbox. Перезапуск может завершить обработку закрытых фрагментов, но не
восстановит потерянный RTP или незакрытый последний фрагмент. Не копируйте файлы
между каталогами record/token без проверки права владения. Проверка очереди RabbitMQ:

```bash
compose exec -T rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
```

При перегрузке PostgreSQL проверьте метрики пула, ожидание блокировок,
`pg_stat_activity` в закрытом административном сеансе без вывода приватного
содержимого SQL, а также длительные активные транзакции. Не начинайте с резкого
увеличения числа соединений max_connections. При отказе Redis восстановите сервис и дождитесь
новых прав владения; клиенты должны переподключиться и получить снимок состояния.
История PubSub не воспроизводится. При отказе MinIO восстановите хранилище,
диск и учётные данные, затем сверьте статусы PostgreSQL и объекты.

## Резервное копирование, восстановление и откат

Актуальные команды и границы — [backup-restore.md](backup-restore.md) и
[ROLLBACK.md](../ROLLBACK.md). Общий скрипт резервного копирования связан с процессом выпуска;
для отдельной установки через мастер используйте её контекст и инструкции.
Сохраняются PostgreSQL и текущие объекты S3 с `ContentType`, но не история версий,
произвольные метаданные или всё содержимое брокера и рабочего каталога записи.
Обязательна общая приостановка изменения данных: копия не является атомарным
снимком нескольких хранилищ. Секреты, конфигурацию, TLS и ключ токенов провайдеров
сохраняйте отдельно в защищённом виде. Старые статусы присутствия, права владения
и PubSub Redis не восстанавливают как действующие.

Проверка восстановления создаёт отдельные БД и бакет и оставляет их для осмотра.
Проверяются хеши, закрытость данных и доступ по подписанным ссылкам; связи данных
приложения и воспроизведение требуют дополнительной приёмки. Локальные замеры
времени не определяют RPO/RTO рабочего окружения. Откат приложения запускает
предыдущие неизменяемые образы на совместимой текущей схеме, без обратных миграций
и пересборки старого коммита. При несовместимой схеме требуется отдельное решение.

## Ручная проверка после выпуска

Сверить `/version` и `/version.json` с выбранным манифестом; через закрытый доступ
проверить состояние, готовность, режим завершения и очереди каждого изменённого сервиса.
С согласованными существующими аккаунтами проверить вход, WebSocket, повторное подключение и доступ
к материалам. Медиа и TURN/TURNS проверить отдельно на целевых сетях с согласия
участников. Новые встречи/записи не создаются автоматически при публикации.
Сохранить реальные результаты и ограничения; состояние и версия не подтверждают
работу RTP, FFmpeg или воспроизведения. Не удаляйте пользовательские данные и тома.

Актуальные задания CI, обязательные проверки безопасности, резервных копий,
отката и ручные проверки описаны в
[RELEASE_PROCESS](../RELEASE_PROCESS.md) и [чеклисте](RELEASE_CHECKLIST.md).

## Предлагаемые SLI/SLO и окно наблюдения

Выберите SLI и измерьте их при ожидаемой нагрузке целевого окружения. На основе
этих данных определяются SLO и допустимое число одновременных встреч.

| Область SLI | Что измерять перед назначением SLO |
| --- | --- |
| HTTP и авторизация | Число реальных запросов и 5xx, p95 по маршрутам без долгоживущих WS/SSE; отдельно ожидаемые 401/403/429 |
| WebSocket и медиа | Попытки входа, повторные и успешные подключения; время до выбора ICE-пары и получения медиа. Общее число попыток фиксируйте в проверочном сценарии браузера, а не выводите из одной метрики текущего значения (gauge) |
| Записи | Запуск, остановка, завершение обработки, ошибки и готовность; время до доступного проверенного MP4 и превью, длина очереди и число завершённых записей |
| Фоновые функции | Задания в очереди, ошибки и повторы, возраст заданий, ошибки и ограничения провайдеров, потери аудио в реальном времени. Отличайте отключённую функцию от неисправной |
| Ресурсы и зависимости | Готовность, пул и блокировки БД, CPU/RSS/goroutines/FD, диск и рабочий каталог записи, PostgreSQL/MinIO/RabbitMQ, выбранные прямые и ретранслируемые соединения |
| Интерфейс | Коды из ограниченного набора ошибок и версии с фактическим числом проверенных сценариев браузера; отсутствие событий не доказывает отсутствие ошибок |

До запуска задайте окно наблюдения, минимальный объём сценариев и условия
остановки. Сохраните фактическое число HTTP-запросов, входов, операций WebSocket, медиа и записи
за период. При недостаточном трафике продлите наблюдение или выполните
контролируемые проверки на стенде.

Начальные правила оповещений находятся в `dockers/observability/alerts.yml`:

- Критичные: стойкая недоступность зависимостей или метрик, опасно низкий запас диска.
  Оператор также немедленно разбирает системную недоступность авторизации, WebSocket или медиасвязи и потерю данных.
- Предупреждения: HTTP 5xx/p95, исчерпание или рост ресурсов, ошибки SFU/FFmpeg,
  повторные задания, очередь неудачных сообщений и ошибки провайдеров.
  Одиночная ошибка FFmpeg сейчас вызывает предупреждение, а не автоматический
  срочный вызов дежурного и не подтверждает общую недоступность.
- Информационные: всплеск ошибок интерфейса — повод проверить версию и сценарий,
  а не точное число пострадавших пользователей.

Порог HTTP 5xx >5%/p95 >1s, DB in-use ≥18 и другие значения начальных правил —
начальные защитные настройки, не обещанный SLO; пересмотреть под реальную выборку,
лимиты и роль сервиса. Настроить доставку, группировку, ответственных и проверку
уведомлений. До этого наличие панели или правила оповещения не означает, что организовано дежурство.
