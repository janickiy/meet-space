# Переход на record-worker и миграция 000037

Этот выпуск удаляет распознавание речи, субтитры, ИИ-сводки, речевую аналитику
и поиск по расшифровкам. Сервис записи `worker` переименован в `record-worker`.
Встречи, сообщения, файлы, записи, поиск названий встреч и поиск сообщений сохраняются.

**Миграция `000037_remove_speech_features.up.sql` необратимо удаляет данные.**
Она удаляет таблицы `transcripts`, `transcript_segments`, `meeting_summaries`,
`live_caption_segments`, `live_transcription_sessions`, `participant_analytics`,
`conference_analytics`, `content_search_indexes`, `content_embeddings` и
`embedding_cache`. Также удаляются связанные задания, записи доставки,
уведомления, триггеры и поле `notification_preferences.summary`.
Расширение PostgreSQL `vector` не удаляется: его могут использовать другие объекты.

Прежние миграции сохраняются без изменения контрольных сумм. Новая установка
применяет всю последовательность и получает схему без функций речи. Down-скрипт
000037 намеренно завершает работу ошибкой: он не может восстановить удалённые данные.
Возврат к старым образам требует восстановления согласованной резервной копии.

## Подготовка

1. Выберите Compose-контекст именно установленного проекта по
   [инструкции развёртывания](../DEPLOYMENT.md#выбор-процедуры-по-типу-установки).
   Команды ниже используют определённую там функцию `compose`. Не заменяйте
   конфигурацию установки мастером произвольным файлом из репозитория.
2. Сохраните прежние image digests и закрытую конфигурацию. Подготовьте и проверьте
   новый комплект: в нём должен быть `record-worker`, а не `worker`/`live-worker`.
   Проверьте состав без вывода секретов:

   ```bash
   compose config --services
   compose config --quiet
   ```

   Результат: конфигурация корректна; сервис записи присутствует под новым именем.
3. Согласуйте окно обслуживания, остановите приём новой работы, дождитесь
   завершения встреч и записи. Проверьте очередь RabbitMQ, `recording_outbox`
   и задания: одного `active=0` недостаточно при ожидающих командах записи.
4. Выполните drain по [операционному runbook](README.md#health-и-завершение).
   Сначала используйте **старый** Compose-контекст. После подтверждения
   `draining=true`, `active=0` остановите старые прикладные службы:

   ```bash
   compose stop api media-worker worker product-worker frontend
   ```

   Если в старом проекте есть запущенный `live-worker` или отладочные службы,
   отдельно дождитесь их drain и остановите их в том же старом контексте.
   PostgreSQL и объектное хранилище оставьте доступными для резервирования.
5. Создайте согласованную резервную копию PostgreSQL и S3, конфигурации и ключей
   по [процедуре резервирования](backup-restore.md). Проверьте восстановление
   в изолированном окружении. Не продолжайте без читаемой копии и принятого RPO/RTO.

## Применение

1. Перейдите в проверенный **новый** Compose-контекст. Отключите автоматический
   перезапуск старых служб и проверьте остановку перед миграцией:

   ```bash
   python3 scripts/install/retire-legacy-services.py --check-migration --compose docker compose --env-file /path/to/private.env -p meetspace -f docker-compose.production.yml
   ```

   Это пример для обычного production Compose. Для установки мастером передайте
   **все** его env-файлы и overlays из выбранного контекста. Имя проекта и пути
   должны соответствовать вашей установке. Helper выбирает контейнеры по точным
   меткам проекта, останавливает старые `worker`/`live-worker`, сохраняет контейнеры
   и тома и запрещает миграцию, пока прикладные процессы ещё работают.
2. Запустите явную миграцию с новыми проверенными образами:

   ```bash
   compose --profile migration run --rm --no-deps migrate
   ```

   Результат: мигратор завершился с кодом 0. При ошибке не включайте приложения
   и не редактируйте журнал контрольных сумм вручную.
3. Проверьте журнал и итоговую схему:

   ```bash
   compose exec -T postgres sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
   SELECT name FROM release_schema_migrations
   WHERE name = '000037_remove_speech_features.up.sql';
   SELECT to_regclass('public.transcripts') IS NULL AS speech_tables_removed,
          to_regclass('public.record') IS NOT NULL AS recordings_preserved,
          to_regclass('public.chat_messages') IS NOT NULL AS messages_preserved;
   SQL
   ```

   Результат: одна строка с именем миграции; три проверки возвращают `t`.
4. Запустите прикладные службы без сборки и проверьте готовность:

   ```bash
   compose up -d --no-build --no-deps --wait --wait-timeout 240 media-worker record-worker product-worker api frontend
   compose ps
   compose exec -T record-worker wget -qO- http://127.0.0.1:8090/health/ready
   compose exec -T product-worker wget -qO- http://127.0.0.1:8092/health/ready
   compose exec -T api wget -qO- http://127.0.0.1:8085/health/ready
   ```

   Результат: службы готовы; старые `worker`/`live-worker` не запущены.
   Затем проверьте HTTPS, вход, сообщения, воспроизведение прежней записи,
   создание новой записи и её переход в `ready`, уведомления и поиск встреч.
   Только после этого снимайте ограничение на новые подключения.

## Откат

До применения миграции можно вернуть согласованный старый комплект. После
применения — остановить новую версию и восстановить PostgreSQL и согласованное
состояние S3 из копии **до** миграции, затем вернуть старые образы и конфигурацию.
Это может удалить изменения, появившиеся после резервирования; решение принимает
владелец данных. Команды выше не выполняют очистку Docker, удаление томов или
развёртывание на какой-либо удалённый сервер автоматически.
