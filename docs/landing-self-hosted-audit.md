# Аудит самостоятельного размещения для публичного сайта

> Исторический отчёт: отражает состояние проекта на дату проверки. После удаления распознавания речи и переименования сервиса записи его перечень компонентов не является описанием текущей версии. Актуальные сведения: [архитектура](ARCHITECTURE.md).

Дата: 18 октября 2026. Проверяемый коммит исходного кода: `893566bb90f07bdcec4542eec5e00116c423e852`.

Область: фактические Compose, примеры файлов окружения, скрипты выпуска и эксплуатационные документы. Аудит выполнен чтением исходного дерева; Docker-окружения не запускались, удалённые серверы не изменялись, готовность к рабочей эксплуатации не подтверждалась.

## Итог

В проекте существует процесс выпуска через Docker Compose на одном сервере с отдельной миграцией, неизменяемыми ссылками на образы, инструментами резервного копирования и восстановления и блокирующей проверкой материалов приёмки рабочего выпуска. Это не однокомандный инсталлятор для произвольного VPS. Текущий коммит исходного кода не равен автоматически подготовленному серверному релизу.

Страница `/docs/self-hosted` объясняет подготовку сервера. Она содержит команды подключения по SSH, получения закреплённой версии исходников и запуска скриптов выпуска на отдельном испытательном стенде (staging). Указано, что удалённая проверка не гарантируется. Ссылки на исходники закреплены на полном SHA коммита.

## Две поддерживаемые конфигурации

### `classic`

`common.sh` выбирает `docker-compose.production.yml` и `docker-compose.grafana.yml`. Сервисы приложений: `api`, `media-worker`, `worker`, `product-worker`, `live-worker`, `frontend`. Зависимости: PostgreSQL, Redis, RabbitMQ, MinIO, Coturn, proxy; мониторинг: Prometheus/Grafana.

- Nginx публикует `443/TCP`, читает сертификаты из `TLS_CERT_DIR`.
- SFU: `MEDIA_UDP_PORT` / `MEDIA_TCP_PORT`, по умолчанию `50010`.
- Coturn: `3478/UDP+TCP`, `5349/TCP`, relay `49160–49259/UDP`.
- БД, брокер, Redis, консоль MinIO и внутренние HTTP-адреса не опубликованы.
- Prometheus `127.0.0.1:19090`, Grafana `127.0.0.1:13001`.
- Том PostgreSQL `postgres`, RabbitMQ `rabbitmq`, MinIO `minio`; отдельное подключение каталога рабочих файлов сервиса записи (spool).
- Redis в production не использует постоянное сохранение AOF/RDB: состояние краткоживущее.

### `hardened-shared-host`

`common.sh` выбирает production + hardened + shared-host. Используется SeaweedFS, но DNS-имя сервиса `minio` и `MINIO_*` сохранены для совместимого клиента S3. Новый том `objects` несовместим со старым томом MinIO; автоматический перенос не происходит.

Прокси публикуется только на `127.0.0.1:${REVERSE_PROXY_PORT:-19080}`. Требуется внешний обратный прокси с TLS, например Apache из описанной истории развёртывания. Coturn использует `network_mode: host` и привязывается к публичному IP. За правила межсетевого экрана отвечает оператор. Подсеть `172.31.242.0/24` нужно проверить на конфликты. Grafana исключена из этой конфигурации. Ресурсные лимиты существенно ниже, чем в classic, и рассчитаны на ограниченный стенд, а не на произвольную нагрузку.

## Конфигурация и безопасность

Источники: `.env.production.example`, `internal/config/operations.go`, `internal/config/product.go`, `dockers/turn/entrypoint.sh`, production Compose.

- `JWT_SECRET`, `MEDIA_TICKET_SECRET`, `MEDIA_INTERNAL_SECRET`, `WORKER_INTERNAL_SECRET`, `METRICS_SECRET`, `TURN_SHARED_SECRET` должны быть независимыми, не менее 32 байт; production отклоняет повторяющиеся значения и значения по умолчанию.
- `POSTGRES_PASSWORD`, `RABBIT_MQ_PASSWORD`, `MINIO_ROOT_PASSWORD`, `REDIS_PASSWORD` должны отличаться от стандартных значений и иметь длину не менее 16 байт.
- `PUBLIC_FRONTEND_URL`, `MINIO_PUBLIC_ENDPOINT`, `WS_ALLOWED_ORIGINS` — фактические HTTPS origins; доверенные прокси задаются явно.
- `MEDIA_NAT_IPS`, `TURN_PUBLIC_IP`, `TURN_REALM`, `TURN_URLS` должны соответствовать публичной сети и DNS.
- Сертификаты готовятся отдельно; автоматических ACME-клиента или гарантии сертификата для IP нет.
- `RECORDER_STORAGE_DIR` должен принадлежать `1000:1000`, права `0750`; запас диска определяется измерением нагрузки и политикой записи.
- Файлы окружения и секреты хранятся вне Git; полный `docker compose config` может раскрывать секреты, поэтому в инструкции он не предлагается. `release.sh validate` использует проверку без вывода полной конфигурации.
- `METRICS_TOKEN_FILE` соответствует `METRICS_SECRET`; classic требует `GRAFANA_PASSWORD_FILE`.
- Все операторы используют один абсолютный `RELEASE_LOCK_DIR` на Docker-хосте.
- Для email/push/calendar/STT/AI/live/embeddings по умолчанию выбраны режимы noop/disabled. Нельзя обещать, что эти возможности уже включены. Ключ шифрования данных провайдера задаётся отдельно в формате base64 AES-256; он нужен для согласованного восстановления токенов. Для embeddings необходимы совместимые образ и расширение pgvector.

## Процесс выпуска

`release.sh` принимает команды `validate|pull|migrate|drain|resume|deploy|rollback`. Нужно явно указать среду, соответствующее имя проекта и абсолютные пути к файлу окружения и манифесту. Перед изменениями в рабочем окружении проверяются `RELEASE_PRODUCTION_APPROVAL`, `--evidence`, совпадение версии, коммита и SHA-256 манифеста, а также утверждения о совместимости, резервной копии, откате, испытательном стенде, медиа и безопасности. Эта проверка оценивает структуру утверждений, но не доказывает истинность отчёта оператора.

`migrate` отдельно запускает зависимости и применяет SQL; `deploy` не выполняет сборку и миграции. Идентификаторы существующих инфраструктурных образов защищены от незаметной подмены. Приложения запускаются в порядке media-worker → worker → product-worker → live-worker → api → frontend, затем прокси и мониторинг. При истечении времени drain процесс остаётся в состоянии draining; принудительного перезапуска нет. Для frontend/proxy без проверки состояния Docker функция `wait_healthy` видит только running, поэтому дополнительно нужны HTTP-проверки.

`package.sh` поддерживает registry/archive/local. Режим archive допустим в рабочем окружении, если подтверждено происхождение из чистых исходников, совпадают идентификаторы образов и предоставлены результаты сканирования и SBOM. Утверждение «для production подходит только registry» неверно. `scripts/ci-deploy.sh` — прежний механизм синхронизации, сборки и запуска для разработки, а не переноса выпуска в рабочее окружение; на публичном сайте он не предлагается.

## Резервное копирование и откат

Источники: `docs/operations/backup-restore.md`, `docs/ROLLBACK.md`, `scripts/release/backup.sh`, `restore-check.sh`.

Резервная копия включает дамп PostgreSQL в формате custom и текущие объекты S3: ключи, байты, хеши и ContentType. Копирование разных хранилищ не атомарно. Поэтому нужно остановить все изменения данных, включая загрузку по подписанным ссылкам, задания cron и прямую запись в хранилища. `RELEASE_BACKUP_QUIESCED=1` — утверждение оператора, а не автоматическое доказательство остановки.

В копию не входят история версий S3, метки удаления, теги и произвольные метаданные, снимок брокера, рабочие файлы незавершённых записей, файлы окружения, ключи, TLS, настройки IAM/ACL и политики доступа, конфигурация Grafana. Проверка восстановления работает на отдельной локальной или испытательной установке, создаёт отдельные БД и bucket и не заменяет данные рабочей установки. Проверка хешей и подписанных ссылок не заменяет проверку связей между данными приложения.

Откат приложения не откатывает SQL и не восстанавливает данные. Требуются прежний готовый пакет и доказанная совместимость со схемой. Смена инфраструктуры требует собственного окна обслуживания.

## Противоречия и устаревшие сведения в исходной документации

1. В `DEPLOYMENT.md`, `ROLLBACK.md` и `PRODUCTION_LAUNCH_CHECKLIST.md` указано, что реальный испытательный стенд ещё не предоставлен. При этом `docs/operations/meeting-host-deployment.md` содержит историю удалённой пилотной установки и отличает её от приёмки рабочего выпуска. Нельзя утверждать ни отсутствие любого реального размещения, ни готовность этого коммита к рабочей эксплуатации.
2. `DEPLOYMENT.md` требует учётные данные для синтетической проверки. Более актуальный `RELEASE_PROCESS.md` сообщает об удалении этой проверки и о ручной проверке через существующий согласованный аккаунт. Страница следует фактическому процессу и не предлагает скрипты, уже удалённые из кода.
3. Исторический `launch-readiness-report.md` и контрольный список перечисляют старые автоматизированные тесты. На дату аудита `RELEASE_PROCESS.md` описывает удаление тестов Go/frontend/e2e по решению владельца. Старые результаты не выдавались за проверку нового сайта.
4. В удалённой истории встречаются разные версии отдельных сервисов и последующие правки веб-клиента. Их нельзя считать согласованным пакетом нынешнего HEAD.
5. Исторические сведения о CVE и сканировании относятся к конкретным пакетам и датам. Повторное сканирование в этом аудите не выполнялось. Страница не заявляет отсутствие уязвимостей в текущем выпуске по результатам нового сканирования.
